Chapter 04 Autograd

You already wrote an autograd engine: the Value class in microgpt_scalar.py. PyTorch's autograd is the same idea, one graph node per tensor operation instead of per number. This chapter maps every piece of your engine onto PyTorch's, then covers the parts you never needed in a scalar engine: gradient accumulation across calls, freeing the graph, turning tracking off for inference, and writing your own backward.

Your engine, in four ideas

Here is the backward pass you wrote. Read it once more, because every PyTorch concept in this chapter is one of its lines.

pythonmicrogpt_scalar.py (excerpt)
class Value:
    def __init__(self, data, children=(), local_gradients=()):
        self.data = data
        self.grad = 0.0
        self._children = children
        self._local_gradients = local_gradients

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        return Value(
            self.data * other.data,
            children=(self, other),
            local_gradients=(other.data, self.data),
        )

    def backward(self):
        ...                                  # build topological_order
        self.grad = 1.0
        for value in reversed(topological_order):
            for child, local_gradient in zip(value._children, value._local_gradients):
                child.grad += local_gradient * value.grad
  1. Children. Every result remembers the values it was computed from. That set of links is the computation graph: a directed acyclic graph (DAG) whose edges point from a result back to its inputs.
  2. Local gradients. At creation time, each result stores the derivative of itself with respect to each child. For a * b that is (b, a).
  3. Topological order. Walk the graph so that a node is processed only after every node that uses it. Then its .grad is complete before it passes gradient on.
  4. Chain rule with +=. child.grad += local_gradient * value.grad. The += matters: when a value is used twice, both paths contribute.

Your engine kept a gradient on every node. PyTorch, by default, only keeps gradients on leaf tensors: tensors you created directly, not results of operations. Intermediates like m can be huge (a (batch, seq, 4096) activation), and nobody updates them, so storing their gradients would waste memory. If you do want one, ask:

Walking the graph

Each backward node has next_functions: a tuple of (node, index) pairs, one per input of the forward operation. Following them from the output is the same recursion as your build_topological_order:

def walk(fn, depth=0):
    print("    " * depth + fn.name())
    for child, _ in fn.next_functions:
        if child is not None:          # None = input that doesn't need grad
            walk(child, depth + 1)

walk(c.grad_fn)

The leaves show up as AccumulateGrad nodes. Each one holds a reference to its leaf tensor (.variable), and its whole job is leaf.grad += incoming_gradient: your +=, moved into a node. The diamond is visible too: a's AccumulateGrad is reached twice, once directly from AddBackward0 and once through MulBackward0.

Saved tensors: lazy local gradients

Your __mul__ computed the local gradients (other.data, self.data) eagerly. PyTorch instead saves the tensors it will need and computes the local gradient during backward. For a multiply that is the two inputs; for exp it is the output (since d/dx ex = ex, exactly like your exp() stored result):

m = a * b

Under the hood: how the engine orders work

Instead of a depth-first topological sort, the engine first counts, for every node reachable from the output, how many gradients it must wait for. Then it runs a ready queue: a node executes only once all its incoming gradients have arrived and been summed. That gives the same guarantee as your reversed topological order. The graph is also dynamic ("define-by-run"): it is rebuilt from scratch on every forward pass, exactly like your calculate_document_loss creates fresh Value objects for each document. That is why Python if and for inside a model just work.

backward(): scalars, accumulation, zeroing

t.backward() starts the chain rule at t with an initial gradient of 1 (your self.grad = 1.0) and runs back to every leaf. It returns nothing; results land in each leaf's .grad.

Gradients accumulate across calls

Since leaves receive gradient with +=, calling backward() again adds to what is already there:

x = torch.tensor(3.0, requires_grad=True)

for step in range(3):
    y = x * x            # build a fresh graph each time
    y.backward()         # dy/dx = 2x = 6
    print(step, x.grad)
0 tensor(6.)
1 tensor(12.)
2 tensor(18.)

This is deliberate. It lets you split a big batch into small pieces, call backward() on each, and end up with the gradient of the whole batch (gradient accumulation, used when a batch doesn't fit in memory). But in a normal training loop you must clear gradients before each backward. You did this in microgpt with for parameter in parameters: parameter.grad = 0.0. PyTorch's version:

x = torch.tensor(3.0, requires_grad=True)

for step in range(3):
    x.grad = None        # what optimizer.zero_grad(set_to_none=True) does
    y = x * x
    y.backward()
    print(step, x.grad)  # 6. every time

In practice you call optimizer.zero_grad() (or model.zero_grad()), which does that for every parameter. Since PyTorch 2.0 its default is set_to_none=True: .grad becomes None instead of a tensor of zeros, which saves a memory write and lets the next backward simply assign. zero_grad(set_to_none=False) keeps the old zero-fill. microgpt's training loop spells the default out: optimizer.zero_grad(set_to_none=True), then loss.backward().

Forgetting zero_grad doesn't crash

It trains on the running sum of every gradient since the start. Loss usually still goes down for a while, then the steps get huge and it diverges. If a loop "almost works", check that zero_grad() runs once per optimizer step.

Non-scalar outputs need a gradient

Your engine always started from one number, the loss. If the output is a vector, "the gradient" is ambiguous: of which number? PyTorch refuses to guess:

x = torch.tensor([1.0, 2.0, 3.0], requires_grad=True)
y = x * x                     # shape (3,), not a scalar

try:
    y.backward()
except RuntimeError as e:
    print("RuntimeError:", e)

print(x.grad)

RuntimeError: grad can be implicitly created only for scalar outputs

tensor([ 2.,  0., 60.])

The gradient argument is the starting .grad for each element of y: the vector you would have put in self.grad if it were a list. It must have y's shape. Passing weights v computes the gradient of (v * y).sum(); mathematically that is a vector-Jacobian product, which is all reverse-mode autodiff ever computes.

The graph is freed after backward

Your engine kept every Value alive until Python garbage-collected it. PyTorch frees the saved tensors as soon as backward has used them, because in a real model they are most of the memory. Go through the same graph twice and you hit this:

a = torch.tensor(2.0, requires_grad=True)
b = torch.tensor(-3.0, requires_grad=True)
c = a * b + a

c.backward()
c.backward()
RuntimeError: Trying to backward through the graph a second time (or directly access saved tensors after they have already been freed). Saved intermediate values of the graph are freed when you call .backward() or autograd.grad(). Specify retain_graph=True if you need to backward through the graph a second time or if you need to access saved tensors after calling backward.

If you really need two passes over one graph (two losses sharing a trunk, for example), keep it alive on every pass except the last:

a = torch.tensor(2.0, requires_grad=True)
b = torch.tensor(-3.0, requires_grad=True)
c = a * b + a
c.backward(retain_graph=True)   # keep saved tensors alive
print(a.grad)                   # tensor(-2.)
c.backward()                    # second pass works; frees the graph now
print(a.grad)                   # tensor(-4.)  accumulated

Usually the better fix is to add the losses and call backward once: (loss1 + loss2).backward().

Turning tracking off

Recording a graph costs time and, more importantly, memory: every saved tensor stays alive until backward. Sometimes you know you will never call backward. There are four tools, each for a different job.

torch.no_grad(): for the weight update

Your SGD step was parameter.data -= learning_rate * parameter.grad. Try that on a tensor leaf directly:

w = torch.tensor([0.5, -1.0], requires_grad=True)
loss = (w * w).sum()
loss.backward()

try:
    w -= 0.1 * w.grad
except RuntimeError as e:
    print("RuntimeError:", e)

with torch.no_grad():
    w -= 0.1 * w.grad          # the update itself is not recorded
print(w, w.is_leaf)
RuntimeError: a leaf Variable that requires grad is being used in an in-place operation.
tensor([ 0.4000, -0.8000], requires_grad=True) True

Autograd refuses because recording "w was modified using w" would make w a non-leaf whose history includes itself. Inside torch.no_grad(), nothing is recorded and results have requires_grad=False. Every optimizer's step() runs under it.

torch.inference_mode(): for serving

A stricter, faster no_grad. Tensors created inside are marked as inference tensors, which skips some bookkeeping (version counters, view tracking) that autograd needs. The price: they can never be used in autograd later.

w = torch.tensor([0.5, -1.0], requires_grad=True)

with torch.no_grad():
    y = w * 2
print(y.requires_grad, y.grad_fn)        # False None

with torch.inference_mode():
    z = w * 2
print(z.requires_grad, z.is_inference())  # False True

(z * w).sum().backward()
RuntimeError: Inference tensors cannot be saved for backward. To work around you can make a clone to get a normal tensor and use it in autograd.

microgpt uses it as a decorator on evaluate_model, predict_next_character and generate_name. That is the right choice: nothing in those functions will ever be backpropagated. Every serving engine does the same.

.detach(): cut one tensor out of the graph

t.detach() returns a new tensor that shares t's memory but has no grad_fn and requires_grad=False. Gradient will not flow back through it. Use it when one value should be treated as a constant (a target computed from the model itself, a value you want to log or plot).

w = torch.tensor([0.5, -1.0], requires_grad=True)
h = w * 3
d = h.detach()

print(d.requires_grad, d.grad_fn)        # False None
print(d.data_ptr() == h.data_ptr())      # True: same memory, no copy

d[0] = 100.0                             # writes through to h
print(h)                                 # tensor([100.,  -3.], grad_fn=<MulBackward0>)

Shared memory means writes go through. Use h.detach().clone() if you need an independent copy. .item(), .tolist() and .numpy() also leave the graph, since they produce plain Python or NumPy values.

requires_grad_(False): freeze a parameter

To stop training some weights (pretrained embeddings, a frozen backbone while you fine-tune a head), switch the flag off on the leaf. The trailing underscore is PyTorch's convention for "modifies in place".

emb = torch.randn(4, 2, requires_grad=True)     # pretend: pretrained embeddings
head = torch.randn(2, 3, requires_grad=True)     # trainable head

emb.requires_grad_(False)                        # freeze

x = emb[torch.tensor([0, 2])]                    # look up two rows
loss = (x @ head).sum()
loss.backward()

print(emb.grad, head.grad is not None)           # None True
ToolScopeUse it for
torch.no_grad()a block of codeoptimizer updates, weight init, evaluation inside a training script

Why an inference engineer cares

In training, the saved tensors of every layer stay alive from the forward pass until backward reaches that layer. That "activation memory" is often larger than the weights. Under inference_mode nothing is saved, so each activation can be freed as soon as the next layer has consumed it. Forgetting the decorator in a serving path is a classic way to run out of GPU memory at a fraction of the batch size you expected.

torch.autograd.grad: gradients without .grad

backward() writes into .grad of every leaf it reaches. torch.autograd.grad(outputs, inputs) instead returns the gradients for the inputs you name and leaves every .grad alone. Use it for quick checks, for gradient penalties, and for anything where accumulating into .grad would be a side effect you don't want.

a = torch.tensor(2.0, requires_grad=True)
b = torch.tensor(-3.0, requires_grad=True)
c = a * b + a

ga, gb = torch.autograd.grad(c, [a, b])
print(ga, gb)                  # tensor(-2.) tensor(2.)
print(a.grad, b.grad)          # None None: untouched

x = torch.tensor(2.0, requires_grad=True)
y = x ** 3
(dy,) = torch.autograd.grad(y, x, create_graph=True)   # 3x^2 = 12, itself differentiable
(d2y,) = torch.autograd.grad(dy, x)                    # 6x = 12
print(dy, d2y)
tensor(-2.) tensor(2.)
None None
tensor(12., grad_fn=<MulBackward0>) tensor(12.)

create_graph=True records the backward pass itself as a graph, so the gradient has a grad_fn and can be differentiated again. Your Value engine could not do that: its local gradients were plain floats, not Values.

Writing your own autograd.Function

Sometimes you need an operation whose backward you write yourself: a fused CUDA kernel, a numerically safer formula, a straight-through estimator. You subclass torch.autograd.Function with two static methods. This is the closest PyTorch gets to your Value methods.

pythonsquare.py
import torch

class Square(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)        # like local_gradients, but saved lazily
        return x * x

    @staticmethod
    def backward(ctx, grad_output):     # grad_output = dLoss/d(output)
        (x,) = ctx.saved_tensors
        return grad_output * 2 * x      # dLoss/dx = dLoss/dout * dout/dx

x = torch.tensor([1.0, -2.0, 3.0], requires_grad=True)
y = Square.apply(x)
print(y)
y.sum().backward()
print(x.grad)

torch.manual_seed(0)
x64 = torch.randn(5, dtype=torch.float64, requires_grad=True)
print(torch.autograd.gradcheck(Square.apply, (x64,)))
tensor([1., 4., 9.], grad_fn=<SquareBackward>)
tensor([ 2., -4.,  6.])
True
  • ctx is a per-call context object. ctx.save_for_backward(...) stores tensors for backward; read them back with ctx.saved_tensors. (Always use this for tensors, not ctx.x = x; it lets autograd detect in-place modification and free memory correctly.)
  • backward receives one gradient per forward output and returns one gradient per forward input. The multiply by grad_output is your local_gradient * value.grad.
  • You call it as Square.apply(x), never Square()(x) or Square.forward.

gradcheck: test your backward against finite differences

torch.autograd.gradcheck nudges each input element by a small eps, measures how the output moves (the numerical Jacobian), and compares that with what your backward returns (the analytical Jacobian). A wrong backward fails loudly:

class BadSquare(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x * x

    @staticmethod
    def backward(ctx, grad_output):
        (x,) = ctx.saved_tensors
        return grad_output * x          # forgot the 2

torch.manual_seed(0)
x64 = torch.randn(3, dtype=torch.float64, requires_grad=True)
try:
    torch.autograd.gradcheck(BadSquare.apply, (x64,))
except RuntimeError as e:
    print(type(e).__name__)
    print(e)

gradcheck needs float64

Finite differences divide a tiny output change by a tiny eps (default 1e-6). In float32, which has about 7 significant digits, that difference is mostly rounding noise. Run the correct Square on a float32 input and gradcheck warns "Input #0 requires gradient and is not a double precision floating point or complex", then fails with numerical 2.9802 against analytical 3.0820. Always build gradcheck inputs with dtype=torch.float64.

Bug 1: torch.randn(..., requires_grad=True) * 0.08 is an operation, so w1 is its result, a non-leaf. The real leaf (the unscaled random tensor) did get a gradient, but you threw away your only reference to it. microgpt's make_parameter gets this right: it builds the values first, then wraps them in nn.Parameter. Bug 2: scale.item() turns the tensor into a Python float, which is a constant to autograd.

Other causes of a None gradient worth checking in this order: the tensor isn't a leaf; the forward ran under no_grad/inference_mode; a .detach(), .item(), .numpy() or .tolist() sits on the path; the parameter simply isn't used in the loss.

import torch

class MyReLU(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x.clamp(min=0)

    @staticmethod
    def backward(ctx, grad_output):
        (x,) = ctx.saved_tensors
        return grad_output * (x > 0).to(grad_output.dtype)   # Value.relu: float(data > 0)

EX 4.7 hard PyTorch as a test oracle for your engine

Copy the Value class (plus import math) from microgpt_scalar.py into value_engine.py. Write a script that evaluates several two-input expressions with both Value and float64 tensors at a = 2, b = -3 and compares the gradients. Show solution

import math
import torch
from value_engine import Value      # your Value class, copied into value_engine.py

expressions = {
    "a*b + a":            lambda a, b: a * b + a,
    "(a+b)*(a-b)":        lambda a, b: (a + b) * (a - b),
    "a/b - b**2":         lambda a, b: a / b - b ** 2,
    "(a*a).exp().log()+b": lambda a, b: (a * a).exp().log() + b,
    "(a*b).relu()*a":     lambda a, b: (a * b).relu() * a,
}

def close(u, v):
    return math.isclose(u, v, rel_tol=1e-9, abs_tol=1e-12)

all_ok = True
for name, f in expressions.items():
    va, vb = Value(2.0), Value(-3.0)
    f(va, vb).backward()

    ta = torch.tensor(2.0, dtype=torch.float64, requires_grad=True)
    tb = torch.tensor(-3.0, dtype=torch.float64, requires_grad=True)
    f(ta, tb).backward()

    ok = close(va.grad, ta.grad.item()) and close(vb.grad, tb.grad.item())
    all_ok = all_ok and ok
    print(f"{name:20s} Value=({va.grad:+.4f}, {vb.grad:+.4f}) "
          f"torch=({ta.grad.item():+.4f}, {tb.grad.item():+.4f}) "
          f"{'ok' if ok else 'MISMATCH'}")

Every expression where a value feeds into two places (a in a*b + a, b used twice in a/b - b**2, a as both operands of a*a) loses one path: the later write overwrites the earlier one. The ReLU case passes by luck, since a*b = -6 makes every gradient 0, and 0 overwritten by 0 is still 0. Your original assert a.grad == -2.0 would fail with -3.0: the reversed order visits c first (setting a.grad = 1) and then m, which overwrites it with b = -3. Lesson: an oracle test needs inputs that exercise every path, which is why PyTorch's own test suite runs gradcheck on random inputs.

Recap

  • A tensor with requires_grad=True makes PyTorch record a graph of backward nodes. grad_fn.next_functions are your _children; saved tensors are your _local_gradients, computed lazily.
  • backward() starts from a scalar with gradient 1. For a non-scalar output, pass gradient= with the output's shape.
  • Only leaves get .grad (use retain_grad() for intermediates). Leaves accumulate with += through AccumulateGrad, so clear them each step with optimizer.zero_grad().
  • The graph's saved tensors are freed after backward. A second backward needs retain_graph=True, but summing the losses is usually better.
  • no_grad for updates and init, inference_mode for serving, detach() to make one value a constant, requires_grad_(False) to freeze.
  • torch.autograd.grad returns gradients without touching .grad; create_graph=True allows higher derivatives.
  • Custom ops: subclass torch.autograd.Function, save with ctx.save_for_backward, call with .apply, and always gradcheck in float64.
