Chapter 11 Performance & Profiling

microgpt's fast path runs on one CPU thread, on purpose. This chapter measures why: what a PyTorch operation costs before it does any arithmetic, how to time code that runs asynchronously on a GPU, which innocent calls stall the GPU, how to read a profiler table, the roofline model that says whether you are short of FLOPs or of bytes, and what torch.compile does about it. Every number here was measured, and the method matters more than the numbers.

Why microgpt runs on one CPU thread

The first lines of run_fast_training():

pythonmicrogpt.py
# This model is too small to benefit from GPU kernel launches. One CPU
# thread is considerably faster for its many tiny tensor operations.
torch.set_num_threads(1)

To see why, follow one operation, a + b, from Python to the result:

  1. Python calls Tensor.__add__, which crosses into C++.
  2. The dispatcher, PyTorch's routing table, picks an implementation from the tensors' device and dtype, checks that the shapes broadcast, and allocates the output tensor. If any input requires grad, autograd records a node.
  3. The kernel, the function that does the arithmetic, runs. On CPU it may split the work across threads. On a GPU the CPU instead launches the kernel: it puts a command in the GPU's queue and returns before the work is done.

Steps 1 and 2 cost about the same for 16 numbers as for 16 million. Measure it:

import time
import statistics
import torch


def time_op(fn, repeats=200):
    for _ in range(10):                      # warm-up
        fn()
    times = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        fn()
        times.append(time.perf_counter() - t0)
    return statistics.median(times)


torch.set_num_threads(1)
for n in [16, 1_024, 65_536, 1_048_576, 16_777_216]:
    a, b = torch.randn(n), torch.randn(n)
    t = time_op(lambda: a + b, repeats=200 if n < 10**7 else 20)
    gbs = 3 * n * 4 / t / 1e9                # read a, read b, write the result
    print(f"n={n:>10,}  {t * 1e6:9.1f} us per add   {gbs:6.1f} GB/s")

Measured on an Apple Silicon laptop CPU (M4 Pro); your numbers will differ.

Adding 16 numbers and adding 1,024 numbers take the same 0.5 µs: that is the fixed per-op overhead, and below about a thousand elements it is all you pay for. Only from tens of thousands of elements does the time scale with size, at roughly 110 GB/s, the speed this core can stream memory. microgpt's tensors are 16 × 16 or 16 × 64: every op lives on the flat part of this curve.

Now a whole microgpt training step (forward, backward, Adam) for one 10-token name, on one CPU thread, ten CPU threads, and the laptop's GPU through MPS (Chapter 9), using TinyGPT from Chapter 10 saved as tinygpt.py:

import time
import statistics
import torch
import torch.nn.functional as F
from tinygpt import TinyGPT


def train_step_time(device, threads, repeats=200):
    torch.set_num_threads(threads)
    torch.manual_seed(0)
    model = TinyGPT().to(device)
    opt = torch.optim.Adam(model.parameters(), lr=0.01)
    x = torch.randint(0, 27, (1, 10), device=device)       # one 10-token name
    y = torch.randint(0, 27, (1, 10), device=device)

    def step():
        loss = F.cross_entropy(model(x).flatten(0, 1), y.flatten())
        opt.zero_grad()
        loss.backward()
        opt.step()
        if device == "mps":
            torch.mps.synchronize()                          # wait for the GPU

    for _ in range(20):
        step()
    times = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        step()
        times.append(time.perf_counter() - t0)
    return statistics.median(times)


for device, threads in [("cpu", 1), ("cpu", 10), ("mps", 1)]:
    t = train_step_time(device, threads)
    print(f"{device} threads={threads:2d}: {t * 1e6:7.0f} us per step  ({1 / t:6.0f} names/s)")
cpu threads= 1:     400 us per step  (  2498 names/s)
cpu threads=10:     673 us per step  (  1487 names/s)
mps threads= 1:    2224 us per step  (   450 names/s)

Your comment is right, by a lot. Ten threads are 1.7x slower than one: splitting a 16-element op across threads costs more in coordination than the op itself. The GPU is 5.6x slower than one thread: each of the few hundred ops per step becomes a kernel launch plus queue round-trip, and the GPU's thousands of cores have nothing to do with 16 numbers. A second run gave 362, 604 and 2,270 µs.

Many small ops versus one fused op

The overhead is per op, so the same math in fewer ops is faster. Here is your scalar softmax written as five tensor ops (max, subtract, exp, sum, divide), against PyTorch's single softmax kernel:

import torch.nn.functional as F
from torch.utils import benchmark

torch.set_num_threads(1)


def softmax_by_hand(x):                   # microgpt_scalar's softmax, as tensor ops
    m = x.max(dim=-1, keepdim=True).values
    e = (x - m).exp()
    return e / e.sum(dim=-1, keepdim=True)


for shape in [(16,), (4096, 4096)]:
    x = torch.randn(shape)
    torch.testing.assert_close(softmax_by_hand(x), F.softmax(x, dim=-1))
    for stmt in ["softmax_by_hand(x)", "F.softmax(x, dim=-1)"]:
        t = benchmark.Timer(stmt=stmt, globals=dict(x=x, F=F, softmax_by_hand=softmax_by_hand))
        m = t.blocked_autorange(min_run_time=0.5)
        print(f"{str(shape):14} {stmt:22} {m.median * 1e6:10.1f} us")
(16,)          softmax_by_hand(x)            2.8 us
(16,)          F.softmax(x, dim=-1)          0.4 us
(4096, 4096)   softmax_by_hand(x)        18926.0 us
(4096, 4096)   F.softmax(x, dim=-1)      16951.9 us

At 16 elements, five ops cost seven times one op: pure overhead. At 16.7 million elements the fused kernel is only about 10% faster here, because on one CPU core the bottleneck is computing 16.7 million exponentials, not moving the data. On a GPU, where arithmetic is cheap relative to memory traffic, the unfused version's extra passes over memory (write e, read it back for the sum, read it again for the divide) are what dominate. The roofline section below makes that precise.

Timing correctly

A benchmark that measures the wrong thing is worse than none, because you will act on it. Four rules:

  1. Use time.perf_counter(): the highest-resolution clock Python has, and it never jumps backwards.
  2. Warm up. The first calls pay one-time costs: memory allocator growth, lazy initialisation, CPU caches, and for torch.compile the whole compilation. Run the code a few times before timing.
  3. Repeat and take the median. The OS interrupts you at random; the median ignores those outliers, the mean does not.
  4. On a GPU, wait for the GPU. See below.

GPU kernels are asynchronous

When you call c = a @ b on a CUDA or MPS tensor, the CPU queues the kernel and returns immediately; c is a handle to a result that does not exist yet. A timer around that line measures the queueing. This runs on the laptop's GPU through MPS:

a = torch.randn(4096, 4096, device="mps")
b = torch.randn(4096, 4096, device="mps")
for _ in range(3):                         # warm-up
    a @ b
torch.mps.synchronize()

t0 = time.perf_counter()
c = a @ b
t1 = time.perf_counter()
print(f"no sync:   {(t1 - t0) * 1e3:7.2f} ms   (only measures queueing the work)")

t0 = time.perf_counter()
c = a @ b
torch.mps.synchronize()                    # block until the GPU has finished
t1 = time.perf_counter()
print(f"with sync: {(t1 - t0) * 1e3:7.2f} ms   (the real matmul time)")
print(f"=> {2 * 4096**3 / (t1 - t0) / 1e12:.1f} TFLOP/s")
no sync:      0.16 ms   (only measures queueing the work)
with sync:   48.59 ms   (the real matmul time)
=> 2.8 TFLOP/s

A 300x error, in the direction that makes your code look great. On CUDA the same pattern uses torch.cuda.synchronize(). The more precise CUDA tool is a pair of CUDA events: markers the GPU itself timestamps when it reaches them in its queue, so the measurement excludes CPU-side noise. This needs an NVIDIA GPU, so it was not run here:

# CUDA only
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()                    # enqueue "timestamp here"
y = model(x)
end.record()
torch.cuda.synchronize()          # wait until the GPU has actually reached `end`
print(start.elapsed_time(end), "ms")

Hidden syncs

The asynchronous queue is what makes a GPU fast: while kernel n runs, the CPU is already preparing kernel n+1, so the GPU never idles. A sync (synchronization) is any point where the CPU must stop and wait for the GPU to finish everything queued, because it needs a value. After the sync, the queue is empty, and the GPU idles while the CPU builds up the next batch of work. Some calls sync without saying so:

CallWhy it must wait
loss.item(), t.tolist()returns a Python number, which lives on the CPU
t.cpu(), t.to("cpu"), t.numpy()copies the data to host memory
print(t), f"{t}"formatting reads the values
if t:, while t > 0:, if (x < best):Python's if calls bool(t), which is .item()
t.nonzero(), x[mask], torch.unique(t)the output's size depends on the data, and the CPU must know the size to allocate it

The cost, measured on the laptop GPU (MPS): 500 iterations of a (64, 1024) @ (1024, 1024) layer, reading the loss each step versus accumulating on the device and reading once.

dev = "mps"
w = torch.randn(1024, 1024, device=dev) / 32
x0 = torch.randn(64, 1024, device=dev)


def loop(sync_every_step):
    x = x0
    total = torch.zeros((), device=dev)
    for _ in range(500):
        x = torch.tanh(x @ w)
        if sync_every_step:
            total += x.sum().item()          # .item(): copy to CPU -> wait for GPU
        else:
            total += x.sum()                 # stays on the GPU, nothing waits
    return total.item()                      # one sync at the very end


loop(True), loop(False)                      # warm-up
for flag in [True, False]:
    torch.mps.synchronize()
    t0 = time.perf_counter()
    loop(flag)
    print(f".item() every step={flag!s:5}: {(time.perf_counter() - t0) * 1e3:6.1f} ms")
.item() every step=True :   99.6 ms
.item() every step=False:   20.4 ms

Same math, five times slower, because every .item() drains the queue. Two more runs gave 101.9 / 24.3 and 130.3 / 20.4 ms. microgpt's training loop does recent_loss += loss.item() every step; on CPU that costs nothing (there is no queue), which is one more reason the CPU path is right for it. On a GPU, keep the running sum as a tensor and call .item() only when you print.

Let PyTorch find them for you (CUDA)

torch.cuda.set_sync_debug_mode("warn") makes PyTorch print a warning at every operation that synchronizes with a CUDA device, and "error" raises instead. Run one training step with it on and read the list. It works only for CUDA.

The profiler

Timing tells you how long; a profiler tells you where. torch.profiler.profile records every op PyTorch runs (and every GPU kernel, with ProfilerActivity.CUDA). record_function("name") adds your own labelled ranges, so you can see phases. Profile 20 batched training steps of TinyGPT, B = 32 names of 16 tokens:

from torch.profiler import profile, record_function, ProfilerActivity

torch.set_num_threads(1)
torch.manual_seed(0)
model = TinyGPT()
opt = torch.optim.Adam(model.parameters(), lr=0.01)
x = torch.randint(0, 27, (32, 16))
y = torch.randint(0, 27, (32, 16))


def train_step():
    with record_function("forward"):
        loss = F.cross_entropy(model(x).flatten(0, 1), y.flatten())
    with record_function("backward"):
        opt.zero_grad()
        loss.backward()
    with record_function("optimizer"):
        opt.step()


for _ in range(5):                                   # warm-up outside the profile
    train_step()

with profile(activities=[ProfilerActivity.CPU]) as prof:
    for _ in range(20):
        train_step()

print(prof.key_averages().table(sort_by="self_cpu_time_total", row_limit=8))

Reading the table

  • Self CPU is time spent in the op itself; CPU total includes the ops it called. backward has 58.8% total but 7.6% self: it is a label (from record_function) wrapping other work. Sort by self time to find where time actually goes; sort by total time to see which phase is expensive.
  • # of Calls is often the most informative column. aten::select, a function that picks one slice of a tensor (as in t[i]), was called 46,080 times in 20 steps.

Put those together. There are 120 bmm calls (batched matrix multiply) in 20 steps: two in attention per forward (q @ k.T and att @ v), and two more for each of those in backward. 46,080 / 120 = 384 = 3 × 128, and 128 = B × H = 32 × 4. So on this CPU build, each bmm on these tiny 16 × 4 matrices walks the 128 (sequence, head) pairs one at a time and slices out three matrices for each. The slicing bookkeeping costs nearly as much as the multiplications. That is the per-op overhead story again, hiding inside one op, and no amount of staring at the Python would have shown it. Exercise 11.6 replaces it.

export_chrome_trace writes a timeline you can open at ui.perfetto.dev: one bar per op, nested by call, on a time axis. Profile few steps; this one-step trace is 1.7 MB and a 20-step one was 35 MB. On a GPU machine, add ProfilerActivity.CUDA to activities and sort by "cuda_time_total"; the trace then shows CPU launches and GPU kernels on separate rows, and gaps in the GPU row are idle time, often caused by a hidden sync. For long runs, profile(schedule=torch.profiler.schedule(wait=1, warmup=1, active=3)) with prof.step() once per iteration records only a window of steps.

Roofline: short of FLOPs, or short of bytes?

Every kernel needs two resources: arithmetic (FLOPs, floating-point operations) and memory traffic (bytes moved between memory and the compute units). Its arithmetic intensity is the ratio, FLOPs per byte. A machine has a peak FLOP rate and a peak memory bandwidth; their ratio is its ridge point. A kernel whose intensity is below the ridge cannot use all the arithmetic, because the data cannot arrive fast enough: it is memory-bound, and its speed is set by bandwidth. Above the ridge it is compute-bound. Plotting attainable FLOP/s against intensity gives a sloped line (bandwidth × intensity) that flattens into a horizontal roof (peak FLOP/s): the roofline.

Two kernels, in fp32 (4 bytes per number), for N × N matrices:

  • Add: N² FLOPs, reads two matrices and writes one: 12 N² bytes. Intensity 1/12 ≈ 0.08, whatever N is.
  • Matmul: 2N³ FLOPs (a multiply and an add per term), and at minimum the same 12 N² bytes. Intensity N / 6: 341 at N = 2048. Each number loaded is reused N times.
torch.set_num_threads(1)
N = 2048
a, b = torch.randn(N, N), torch.randn(N, N)

mm = benchmark.Timer("a @ b", globals=dict(a=a, b=b)).blocked_autorange(min_run_time=1)
add = benchmark.Timer("a + b", globals=dict(a=a, b=b)).blocked_autorange(min_run_time=1)

flops_mm, bytes_mm = 2 * N**3, 3 * N * N * 4        # read a, b; write c (fp32)
flops_add, bytes_add = N * N, 3 * N * N * 4

for name, m, fl, by in [("matmul", mm, flops_mm, bytes_mm), ("add", add, flops_add, bytes_add)]:
    t = m.median
    print(f"{name:6}: intensity {fl / by:7.2f} FLOP/byte   {t * 1e3:7.2f} ms   "
          f"{fl / t / 1e9:7.1f} GFLOP/s   {by / t / 1e9:6.1f} GB/s")
matmul: intensity  341.33 FLOP/byte      5.39 ms    3186.0 GFLOP/s      9.3 GB/s
add   : intensity    0.08 FLOP/byte      0.42 ms       9.9 GFLOP/s    118.5 GB/s

The add runs at 118.5 GB/s, the same memory speed as the first table, and gets 9.9 GFLOP/s: memory-bound, it would not go faster with more arithmetic units. The matmul gets 3.2 TFLOP/s, 320 times the add's FLOP rate, while touching memory at only 9.3 GB/s: compute-bound. (One "thread" reaches TFLOP/s here because this PyTorch build calls Apple's Accelerate library for matmul, which uses the chip's dedicated matrix hardware.) The rough ridge of this core is 3186 / 118.5 ≈ 27 FLOP/byte.

A datacenter GPU has a much higher ridge. NVIDIA's H100 SXM datasheet lists about 989 TFLOP/s of dense BF16 tensor-core math and 3.35 TB/s of memory bandwidth: a ridge near 300 FLOP/byte. Consequences that drive inference engineering:

  • Elementwise ops, norms and softmax are always memory-bound (intensity below 1). Their cost is bytes moved, so the way to speed up a chain of them is to move fewer bytes: fusion, one kernel that reads the input once, does all the steps in registers, and writes once.
  • Large matmuls are compute-bound, which is why training (big batches times long sequences) can keep tensor cores busy.
  • Decode is memory-bound. One decode step multiplies a (B, d) activation by each (d, d) weight. For B = 1 in bf16, that is 2d² FLOPs over 2d² bytes of weights: intensity about 1, three hundred times below the ridge. Batching B sequences reuses each weight B times, raising the intensity to roughly B. That, and not convenience, is why servers batch decode (Chapter 10), and why the KV cache's size, which limits B, matters so much.

torch.compile

Eager PyTorch is an interpreter: one dispatch and one kernel per op, each reading and writing memory. torch.compile(fn) is a just-in-time compiler that sees many ops at once. Three stages, which a compiler engineer will recognise:

  1. TorchDynamo (graph capture) hooks CPython's frame evaluation, reads the function's bytecode as it is about to run, and extracts the tensor operations into an FX graph, PyTorch's IR. It also emits guards: cheap checks on the inputs (shapes, dtypes, devices, Python values the trace depended on) that must hold for the compiled code to be reused. Code it cannot trace causes a graph break: the graph ends, that piece runs in normal Python, and a new graph starts after it.
  2. AOTAutograd traces the backward pass ahead of time from the forward graph, so forward and backward are both graphs the backend can optimise, and decides which intermediates to save for backward.
  3. TorchInductor (the default backend) lowers the graphs to its own loop-level IR, fuses pointwise ops and reductions into combined kernels, and generates code: Triton kernels on NVIDIA and AMD GPUs, C++ with OpenMP and vector intrinsics on CPU. Matmuls usually go to the vendor library (cuBLAS, or here Accelerate).

On this laptop CPU it works. A memory-bound chain of four elementwise ops and a reduction:

torch.set_num_threads(1)


def chain(x):
    return ((x * 2.0 + 1.0).relu() * x).sum(dim=-1)   # 4 elementwise ops + a reduction


x = torch.randn(4096, 4096)
compiled = torch.compile(chain)

t0 = time.perf_counter()
compiled(x)                                           # first call: trace + codegen + build
print(f"first call: {time.perf_counter() - t0:.1f} s")
torch.testing.assert_close(compiled(x), chain(x))

for name, fn in [("eager", chain), ("compiled", compiled)]:
    m = benchmark.Timer("fn(x)", globals=dict(fn=fn, x=x)).blocked_autorange(min_run_time=1)
    print(f"{name:9}: {m.median * 1e3:6.1f} ms")
first call: 3.1 s
eager    :    6.1 ms
compiled :    2.6 ms

(Apple Silicon laptop CPU, one thread.) Eager mode writes and re-reads a 64 MB intermediate four times; Inductor generated one loop that reads x once and keeps the intermediates in registers: 2.3x faster. The cost is the first call, 3.1 s here with an empty cache. The very first compile on this machine took 14 s because Inductor also built precompiled C++ headers; a later process that hit Inductor's on-disk cache took 0.8 s. At a saving of 3.5 ms per call, the 3.1 s compile pays for itself after about 900 calls (Exercise 11.5).

On the overhead-bound microgpt forward the gain is smaller, since the fixed per-call costs (guard checks, launching the generated code, the matmul library calls) remain:

Graph breaks

Anything Dynamo cannot put in a graph splits it. The classic cause is a data-dependent Python branch, because the branch needs a tensor's value (a sync) and the graph can only hold one path. torch._dynamo.explain reports the breaks:

import torch._dynamo


def f(x):
    y = x.relu() * 2
    if y.sum().item() > 0:          # data-dependent Python branch: needs the value
        y = y + 1
    return y.exp()


explanation = torch._dynamo.explain(f)(torch.randn(8))
print(explanation.graph_count, explanation.graph_break_count)    # 2 1
for reason in explanation.break_reasons:
    print(reason.reason.splitlines()[0])
# Unsupported Tensor.item() call with capture_scalar_outputs=False

It also logs a warning that starts Graph break from `Tensor.item()`, consider setting: torch._dynamo.config.capture_scalar_outputs = True and points at the source line. Two graphs means two compiled pieces with Python in between, and no fusion across the break. The usual fix is to keep the decision on the device: y = torch.where(y.sum() > 0, y + 1, y). Other common breaks: print, calls into non-PyTorch libraries, and unsupported Python constructs. torch.compile(fn, fullgraph=True) turns any break into an error, which is what you want while optimising.

Recompiles and dynamic shapes

Guards include input shapes, so a new shape fails a guard and triggers a recompile. By default (dynamic=None), the first recompile caused by a changed size marks that dimension as dynamic, and the new code works for any size. dynamic=False specialises on every shape; dynamic=True starts dynamic. Turn on the recompile log to watch:

Modes

torch.compile(model, mode="reduce-overhead") attacks the launch overhead from the start of this chapter using CUDA graphs: the sequence of kernel launches is recorded once and replayed with a single launch, so hundreds of small kernels cost one launch. CUDA graphs need static shapes and fixed memory addresses, so inputs are copied into static buffers, and it needs a CUDA GPU. mode="max-autotune" spends longer compiling to benchmark alternative kernel configurations (for example Triton matmul templates against cuBLAS) and keep the fastest.

When compile is not enough

When the compiler cannot find the kernel you need (a fused attention variant, a quantised matmul, a paged-KV-cache read), you write it. Triton is a Python-embedded language for GPU kernels in which you program blocks of data rather than individual threads, and it is what Inductor itself generates, so its output is a good starting point. To make your kernel a first-class PyTorch op that torch.compile can trace around without a graph break and autograd can differentiate, register it with torch.library.custom_op (and register_autograd for its backward), or torch.library.triton_op for a Triton kernel that Inductor may inline. The registration part runs on CPU too:

@torch.library.custom_op("mylib::scaled_relu", mutates_args=())
def scaled_relu(x: torch.Tensor, scale: float) -> torch.Tensor:
    return (x * scale).clamp(min=0)          # imagine a hand-written kernel here


@scaled_relu.register_fake
def _(x, scale):                             # shape/dtype only, for torch.compile
    return torch.empty_like(x)


f = torch.compile(lambda x: scaled_relu(x, 2.0) + 1)
print(f(torch.tensor([-1.0, 0.5, 2.0])))     # tensor([1., 2., 5.])

The "fake" implementation tells the compiler the output's shape and dtype without running the kernel. The official "Custom Operators" tutorials on docs.pytorch.org cover the full recipe.

Write bench(fn, device) that warms up, synchronizes for "cuda" and "mps", repeats, and returns the median seconds. def bench(fn, device, warmup=5, repeats=30):
    def sync():
        if device == "cuda":
            torch.cuda.synchronize()
        elif device == "mps":
            torch.mps.synchronize()
    for _ in range(warmup):
        fn()
    sync()
    times = []
    for _ in range(repeats):
        t0 = time.perf_counter()
        fn()
        sync()
        times.append(time.perf_counter() - t0)
    return statistics.median(times)

The Timer runs the statement many times back to back. The GPU's queue has a limited depth, so after a few calls the CPU blocks waiting for space, and the average settles near the GPU's real throughput; what is missed is the work still queued when the clock stops. One isolated call has no such back-pressure, hence the 300x error. Do not rely on back-pressure: synchronize explicitly.

EX 11.4 medium Profile and name the top op

Run the profiler example. Which op has the most self CPU time? Account for its exact call count (120) and for the 46,080 aten::select calls from the shapes in the model. Then re-sort the same profile by "cpu_time_total" and explain why the top rows change.

Show solution

aten::bmm. Per training step: the forward makes 2 batched matmuls (q @ k.transpose(-2, -1) and att @ v); in backward, each of those becomes a BmmBackward0 that computes the gradient for both inputs with one bmm each, so 4.         x = x + F.linear(F.relu(F.linear(h, self.mlp_expand_weights)), self.mlp_contract_weights)
        return F.linear(x, self.language_model_head_weights)

Recap

  • Every op pays a fixed dispatch cost (about 0.5 µs on this laptop CPU) before any arithmetic; GPU ops add a launch. microgpt's tensors are so small that one CPU thread beats ten threads and beats the GPU.
  • Time with perf_counter, warm up, repeat, take the median. GPU work is asynchronous: synchronize (torch.cuda.synchronize(), torch.mps.synchronize()) or use CUDA events. benchmark.Timer syncs CUDA but not MPS.
  • .item(), .tolist(), .cpu(), print(t), if t: and data-dependent sizes (nonzero, x[mask]) all stall the GPU queue. Keep values on the device and read them rarely.
  • torch.profiler.profile plus record_function and key_averages().table(sort_by=...) show where time goes; the call-count column often explains it. Export a trace for the timeline.
  • Arithmetic intensity (FLOPs per byte) against the machine's ridge point says memory-bound or compute-bound. Elementwise ops and decode are memory-bound; big matmuls are compute-bound; fusion and batching raise effective intensity.
  • torch.compile = Dynamo (bytecode to FX graph, guards) + AOTAutograd (backward graph) + Inductor (fused Triton or C++ kernels). It costs seconds on the first call, breaks graphs on data-dependent Python, recompiles on new shapes unless dimensions are dynamic, and mode="reduce-overhead" adds CUDA graphs. Measured here: 2.3x on a memory-bound chain, 1.35x on the tiny microgpt forward.
