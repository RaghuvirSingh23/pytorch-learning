Chapter 12 Debugging PyTorch

PyTorch bugs come in two kinds: the ones that crash with a message you have to decode, and the ones that run and quietly produce wrong numbers. The second kind is worse. This chapter reads real error messages, shows the silent bugs that cost people days, tracks down NaNs, gives a checklist for a loss that won't go down, and ends with the strongest tool you have: testing the tensor code against a reference, including a scalar one in the style of microgpt_scalar.py.

Reading the error

PyTorch errors are long, but the useful part is short: the last line of the traceback names the operation (often as "while checking arguments for op") and the offending shapes, devices or dtypes. Read it before you read the stack. Each example below shows the real first line of the message from PyTorch 2.8 and the fix.

Shape mismatch in a matmul

import torch
import torch.nn.functional as F

x = torch.randn(4, 16)                # (B, E_in)
W = torch.randn(64, 16)               # [out][in], like microgpt
x @ W
# RuntimeError: mat1 and mat2 shapes cannot be multiplied (4x16 and 64x16)

mat1 @ mat2 needs mat1's last dimension to equal mat2's first: here 16 against 64. microgpt stores weights [out][in], so the product is x @ W.T, which is what F.linear(x, W) computes. Both give (4, 64). If you see the same message from F.linear, the weight was stored [in][out].

Device mismatch

Every tensor in one op must live on the same device. The wording depends on the op, so learn to recognise all of these (from the mps backend on a Mac):

emb = torch.nn.Embedding(27, 16).to("mps")
x.to("mps") @ W.T
# RuntimeError: Tensor for argument #2 'mat2' is on CPU, but expected it to be on GPU
#   (while checking arguments for mm)
F.linear(x, W.to("mps"))
# RuntimeError: Tensor for argument input is on cpu but expected on mps
emb(torch.tensor([1, 2, 3]))
# RuntimeError: Placeholder storage has not been allocated on MPS device!
torch.randn(3, device="mps") + torch.randn(3)
# RuntimeError: Expected all tensors to be on the same device, but found at least
#   two devices, mps:0 and cpu!

The third one is famously unhelpful: it means "an input of an MPS op is on the CPU", here the token ids fed to an embedding that was moved to mps. The last one is the generic check, and on an NVIDIA machine it names cuda:0 instead of mps:0. The fix is always the same: pick one device, move the model with model.to(device), and create or move every input with device=device, as microgpt's make_training_pair does.

Dtype mismatch

ids = torch.tensor([[1, 2, 3]])                  # int64 ("Long") token ids
ids @ torch.randn(3, 4)
# RuntimeError: expected m1 and m2 to have the same dtype, but got: long long != float
logits = torch.randn(4, 27)
F.cross_entropy(logits, torch.tensor([1.0, 2.0, 3.0, 4.0]))
# RuntimeError: expected scalar type Long but found Float
F.cross_entropy(logits, torch.tensor([1, 2, 3, 4], dtype=torch.int32))
# RuntimeError: expected scalar type Long but found Int
torch.nn.Embedding(27, 16)(torch.tensor([1.0, 2.0]))
# RuntimeError: Expected tensor for argument #1 'indices' to have one of the following
#   scalar types: Long, Int; but got torch.FloatTensor instead (while checking arguments for embedding)

Matmul does not promote between integer and float; convert with .float(). Class-index targets for cross_entropy must be int64: .long(). One trap: if float targets have the same shape as the logits, cross_entropy does not complain, because it reads them as per-class probabilities. That is a legitimate feature (soft labels) and a silent bug if you meant class indices.

view on a non-contiguous tensor

After attention, att @ v is (B, H, T, D) and you need (B, T, E). A transpose changes only the strides (Chapter 2), so the data is no longer laid out in the order view needs:

y = torch.randn(2, 4, 16, 4)           # att @ v: (B, H, T, D), contiguous
t = y.transpose(1, 2)                  # (B, T, H, D): same memory, new strides
print(t.shape, t.stride(), t.is_contiguous())
# torch.Size([2, 16, 4, 4]) (256, 4, 64, 1) False
t.view(2, 16, 16)
# RuntimeError: view size is not compatible with input tensor's size and stride (at least
#   one dimension spans across two contiguous subspaces). Use .reshape(...) instead.
print(t.reshape(2, 16, 16).shape)              # torch.Size([2, 16, 16]): copies when it has to
print(t.contiguous().view(2, 16, 16).shape)    # torch.Size([2, 16, 16]): explicit copy, then view

This is why FastMicroGPT writes .transpose(0, 1).reshape(...). Treat the error as information, not an obstacle: it tells you the memory order differs from the logical order. Exercise 12.5 shows a bug that switching to reshape silenced.

Shape discipline

Most transformer bugs are shape bugs, and many of them do not crash. Three habits catch them early.

  • Name the dimensions in comments. Pick letters once and use them everywhere: B batch, T sequence length, E embedding, H heads, D head size, V vocabulary. Write the shape next to every line that changes it.
  • Assert shapes at boundaries, with the actual shape in the message: assert q.shape == (B, H, T, D), q.shape. An assert costs nanoseconds and turns a silent bug into a crash at the right line.
  • Print every module's output shape once, with forward hooks.

A forward hook is a function PyTorch calls after a module's forward returns, with (module, inputs, output). register_forward_hook returns a handle; hooks stay installed until you call handle.remove(). To see them work we need a model built from submodules. Here is microgpt as nn.Modules (Chapter 6 style): same sizes, same 4,192 parameters, with Q, K and V packed into one (48, 16) weight.

pythondebug_gpt.py
import torch
import torch.nn as nn
import torch.nn.functional as F


class Attention(nn.Module):
    def __init__(self, n_embd=16, n_head=4):
        super().__init__()
        self.n_head = n_head
        self.qkv = nn.Linear(n_embd, 3 * n_embd, bias=False)
        self.proj = nn.Linear(n_embd, n_embd, bias=False)

    def forward(self, x):                                    # x: (B, T, E)
        B, T, E = x.shape
        q, k, v = self.qkv(x).split(E, dim=-1)               # 3 x (B, T, E)
        q, k, v = (t.view(B, T, self.n_head, E // self.n_head).transpose(1, 2)
                   for t in (q, k, v))                       # 3 x (B, H, T, D)
        y = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.proj(y.transpose(1, 2).reshape(B, T, E))


class MLP(nn.Module):
    def __init__(self, n_embd=16):
        super().__init__()
        self.fc = nn.Linear(n_embd, 4 * n_embd, bias=False)
        self.proj = nn.Linear(4 * n_embd, n_embd, bias=False)

    def forward(self, x):
        return self.proj(F.relu(self.fc(x)))


class GPT(nn.Module):
    def __init__(self, vocab_size=27, n_embd=16, block_size=16):
        super().__init__()
        self.tok = nn.Embedding(vocab_size, n_embd)
        self.pos = nn.Embedding(block_size, n_embd)
        self.norm1 = nn.RMSNorm(n_embd, eps=1e-5, elementwise_affine=False)
        self.attn = Attention(n_embd)
        self.norm2 = nn.RMSNorm(n_embd, eps=1e-5, elementwise_affine=False)
        self.mlp = MLP(n_embd)
        self.head = nn.Linear(n_embd, vocab_size, bias=False)

    def forward(self, idx):                                  # idx: (B, T)
        T = idx.shape[1]
        x = self.tok(idx) + self.pos(torch.arange(T, device=idx.device))
        x = x + self.attn(self.norm1(x))
        x = x + self.mlp(self.norm2(x))
        return self.head(x)                                  # (B, T, V)

def show_shapes(model):
    handles = []
    for name, module in model.named_modules():
        if name == "":                                       # skip the root module
            continue

        def hook(module, inputs, output, name=name):
            print(f"{name:10} {type(module).__name__:10} -> {tuple(output.shape)}")
        handles.append(module.register_forward_hook(hook))
    return handles

Hooks fire in execution order, children before their parent finishes, so this doubles as a trace of what the model actually ran. name=name in the inner function's defaults freezes the loop variable; without it every hook would print the last name.

Bugs that don't crash

Broadcasting (B, 1) against (B,)

A model that predicts one number per example often returns (B, 1); targets are often (B,). Broadcasting (Chapter 3) lines them up from the right and stretches both into (B, B): every prediction is compared with every target.

pred = torch.tensor([[1.0], [2.0], [3.0], [4.0]])     # (4, 1): a model's output
y = torch.tensor([1.0, 2.0, 3.0, 4.0])                # (4,): the targets
print((pred - y).shape)                               # torch.Size([4, 4]), not (4,)!
print(((pred - y) ** 2).mean())                       # tensor(2.5000), should be 0
print(((pred.squeeze(1) - y) ** 2).mean())            # tensor(0.): the fix
print(F.mse_loss(pred, y))                            # tensor(2.5000), with a warning

The predictions are perfect and the loss says 2.5. F.mse_loss at least warns: UserWarning: Using a target size (torch.Size([4])) that is different to the input size (torch.Size([4, 1])). This will likely lead to incorrect results due to broadcasting. A hand-written loss says nothing.

Softmax over the wrong dimension

torch.manual_seed(0)
logits = torch.randn(3, 5)                 # (B=3, V=5)
wrong = F.softmax(logits, dim=0)           # normalises over the batch
right = F.softmax(logits, dim=-1)          # normalises over the vocabulary
print(wrong.sum(dim=-1))                   # tensor([1.6968, 1.8793, 1.4239])
print(right.sum(dim=-1))                   # tensor([1.0000, 1.0000, 1.0000])

Both return a tensor of the right shape with values in [0, 1]. Use dim=-1 (the last dimension) for vocabulary and attention softmaxes, so adding a batch dimension later cannot shift it, and check that rows sum to 1.

Forgetting zero_grad

w = torch.tensor([1.0, 2.0], requires_grad=True)
for step in range(3):
    loss = (w ** 2).sum()                  # d loss / dw = 2w = [2, 4]
    loss.backward()                        # no zero_grad: .grad is += each time
    print(step, w.grad)
# 0 tensor([2., 4.])
# 1 tensor([4., 8.])
# 2 tensor([ 6., 12.])
w.grad = None                              # what optimizer.zero_grad() does by default
(w ** 2).sum().backward()
print("after reset", w.grad)               # after reset tensor([2., 4.])

This is your Value engine's child.grad += ...: gradients accumulate by design (it is how gradient accumulation over micro-batches works), which is why microgpt sets every parameter.grad = 0.0 before each backward(). Forget it and each step uses the sum of all past gradients: training diverges or crawls, with no error.

Forgetting model.eval()

torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 8), nn.ReLU(), nn.Dropout(0.3), nn.Linear(8, 1))
x = torch.ones(1, 4)
with torch.no_grad():
    print([round(net(x).item(), 4) for _ in range(3)])   # still in train mode
    net.eval()
    print([round(net(x).item(), 4) for _ in range(3)])
# [-0.0868, -0.4247, -0.4501]
# [-0.3621, -0.3621, -0.3621]

In train mode, dropout makes the same input give different outputs, and validation numbers come out noisy and pessimistic. no_grad does not help; only eval() switches dropout off (Chapter 10). The symptom to recognise: evaluating the same data twice gives different losses.

Evaluating without no_grad

Each forward with grad enabled builds a graph and keeps the activations backward would need. If you keep a reference to any tensor of that graph, the whole graph stays alive. The classic leak is accumulating the loss tensor instead of its value. Measured on the laptop GPU (MPS reports its allocator's usage; on CUDA use torch.cuda.memory_allocated()), with a wider version of the model:

def evaluate(model, batches, track_grad):
    total = 0.0
    with torch.set_grad_enabled(track_grad):
        for x, y in batches:
            loss = F.cross_entropy(model(x).flatten(0, 1), y.flatten())
            total = total + loss               # bug: should be loss.item()
    return total


torch.manual_seed(0)
dev = "mps"
model = GPT(n_embd=256, block_size=256).to(dev)
batches = [(torch.randint(0, 27, (32, 256), device=dev),
            torch.randint(0, 27, (32, 256), device=dev)) for _ in range(20)]

for track in [True, False]:
    torch.mps.empty_cache()
    before = torch.mps.current_allocated_memory()
    total = evaluate(model, batches, track_grad=track)
    after = torch.mps.current_allocated_memory()
    print(f"grad tracking={track!s:5}: {(after - before) / 2**20:7.1f} MiB still held, "
          f"requires_grad={total.requires_grad}")
    del total
grad tracking=True :  3546.4 MiB still held, requires_grad=True
grad tracking=False:     0.0 MiB still held, requires_grad=False

3.5 GiB of activations for 20 evaluation batches, all kept alive by one float-looking variable. Evaluate under torch.no_grad() or torch.inference_mode(), and accumulate loss.item() (which is what microgpt's evaluate_model does) or loss.detach().

.data misuse

t.data is a leftover from early PyTorch: a view of the same storage that autograd does not track at all, including its version counter. t.detach() also shares storage and is not tracked, but in-place edits through it still bump the version counter that autograd checks. The difference shows when you edit a value backward needs. Sigmoid's backward reuses its output (σ' = σ(1 − σ)):

def run(use_data):
    a = torch.tensor([1.0, 2.0, 3.0], requires_grad=True)
    out = a.sigmoid()                      # sigmoid's backward reuses `out`
    c = out.data if use_data else out.detach()
    c.zero_()                              # in-place edit through the alias
    out.sum().backward()
    return a.grad


print(".data:   ", run(True))              # .data:    tensor([0., 0., 0.])  silently wrong
print(".detach():", run(False))
# RuntimeError: one of the variables needed for gradient computation has been modified
#   by an inplace operation: [torch.FloatTensor [3]], which is output 0 of SigmoidBackward0,
#   is at version 1; expected version 0 instead. Hint: ...
a = torch.tensor([1.0, 2.0, 3.0], requires_grad=True)
print("correct: ", torch.autograd.grad(a.sigmoid().sum(), a)[0])
# correct:  tensor([0.1966, 0.1050, 0.0452])

With .data, the gradient is computed from the zeroed output and comes out as zeros: no error, wrong answer. Use .detach() for "a tensor without history", and with torch.no_grad(): for in-place parameter updates. Your microgpt optimizer writes parameter.data -= ... on Value objects; that is your own class, unrelated to PyTorch's .data.

A parameter that never gets a gradient

If a parameter does not take part in computing the loss, autograd never reaches it and its .grad stays None. It still counts in parameters(), still gets saved, and never trains. A typo is enough:

class Block(nn.Module):
    def __init__(self, n_embd=16):
        super().__init__()
        self.norm1 = nn.RMSNorm(n_embd)            # learnable scale this time
        self.norm2 = nn.RMSNorm(n_embd)
        self.fc = nn.Linear(n_embd, n_embd)

    def forward(self, x):
        x = x + self.fc(self.norm1(x))
        return x + self.fc(self.norm1(x))          # typo: should be norm2


torch.manual_seed(0)
block = Block()
block(torch.randn(2, 16)).sum().backward()
print([name for name, p in block.named_parameters() if p.grad is None])
# ['norm2.weight']

Run this one-liner after the first backward() of every new model. Any name it prints is either dead code or a bug.

In-place errors

Autograd saves some tensors during the forward pass for use in backward (Chapter 4). Every tensor has a version counter that each in-place operation (+=, add_, relu_, slice assignment) increments. Autograd records the version when it saves a tensor and checks it again in backward. If they differ, the saved value was overwritten and the gradient would be wrong, so it stops:

x = torch.tensor([0.0, 1.0, 2.0], requires_grad=True)
y = x.exp()               # exp's backward needs its own output: dy/dx = y
y += 1                    # in-place: overwrites the saved y
y.sum().backward()
RuntimeError: one of the variables needed for gradient computation has been modified by an
inplace operation: [torch.FloatTensor [3]], which is output 0 of ExpBackward0, is at version 1;
expected version 0 instead. Hint: enable anomaly detection to find the operation that failed
to compute its gradient, with torch.autograd.set_detect_anomaly(True).

Decode it piece by piece: a [3]-element float tensor, which is the output of ExpBackward0 (so: the result of an exp), was saved at version 0 and is now at version 1 (one in-place edit since). The fix is to make the edit out-of-place, y = y + 1, which creates a new tensor and leaves the saved one intact:

x = torch.tensor([0.0, 1.0, 2.0], requires_grad=True)
y = x.exp()
y = y + 1                 # out-of-place: a new tensor, the saved y is intact
y.sum().backward()
print(x.grad)             # tensor([1.0000, 2.7183, 7.3891])

Ops whose backward reuses their output (exp, sigmoid, tanh, relu, softmax) are the usual victims; ops whose backward needs their input (mul, pow, matmul) are victims when you edit the input. In a big model the message does not say which line did it; the anomaly mode below does, and Exercise 12.7 uses it.

NaN and inf

inf is the float value for "too large to represent" (or the result of dividing by zero); NaN ("not a number") is the result of an undefined operation such as 0 × inf, inf − inf or 0 / 0. NaN spreads: any arithmetic with a NaN gives NaN, so one bad value in one activation becomes a NaN loss and then NaN in every weight after the optimizer step. The common sources in transformer code:

# 1. a query that may see no key at all (e.g. a padding position)
scores = torch.tensor([[0.5, 1.0, 2.0],
                       [0.3, 0.1, 0.4]])
allowed = torch.tensor([[True, True, False],
                        [False, False, False]])      # row 1: nothing allowed
att = scores.masked_fill(~allowed, float("-inf")).softmax(dim=-1)
print(att)
# tensor([[0.3775, 0.6225, 0.0000],
#         [   nan,    nan,    nan]])

# 2. log(0), and 0 * -inf
p = torch.tensor([0.0, 0.5, 0.5])
onehot = torch.tensor([0.0, 1.0, 0.0])
print(p.log())                                       # tensor([   -inf, -0.6931, -0.6931])
print(-(onehot * p.log()).sum())                     # tensor(nan): 0 * -inf = nan
logits = torch.tensor([-100.0, 0.0, 0.0])            # same distribution, as logits
print(F.cross_entropy(logits[None], torch.tensor([1])))   # tensor(0.6931)

# 3. fp16 overflow
print(torch.finfo(torch.float16).max)                # 65504.0
h = torch.tensor([300.0], dtype=torch.float16)
print(h * h, (h * h) - (h * h))                      # tensor([inf], ...) tensor([nan], ...)
print(torch.tensor([300.0], dtype=torch.bfloat16) ** 2)   # tensor([90112.], dtype=torch.bfloat16)
  1. A fully masked attention row. Softmax of all -inf computes exp(-inf) / sum = 0 / 0. This is the left-padding problem from Chapter 10, where TinyGPT lets each query see its own column so no row is empty. Another fix is to give empty rows one allowed key, or to replace NaN rows afterwards. (In PyTorch 2.8 on CPU, F.scaled_dot_product_attention returned zeros for a fully masked row in my test; a hand-written softmax does not.)
  2. log(0) is -inf, and multiplying it by a zero weight gives NaN. Computing cross-entropy as softmax then log hits this as soon as a probability underflows to 0. F.cross_entropy and F.log_softmax work on logits with the log-sum-exp trick and never take the log of 0.
  3. fp16 overflow. fp16's largest finite value is 65,504, so 300² is inf, and inf minus inf is NaN. bf16 has fp32's exponent range and survives (at reduced precision: 90,000 rounds to 90,112). This is why fp16 training needs a GradScaler and bf16 usually does not (Chapter 9).

Finding them

torch.isfinite(t) is True where a value is neither inf nor NaN (torch.isnan and torch.isinf separate the two). Check the loss every step, cheaply, and stop at the first bad one: if not torch.isfinite(loss): raise RuntimeError(...) (a sync on GPU, so in a hot loop check every N steps). To find which module first produces non-finite values in the forward pass, put the check in a forward hook (Exercise 12.8).

NaNs that appear only in gradients need anomaly detection. Under torch.autograd.set_detect_anomaly(True), autograd records the Python stack of every forward op, and during backward checks each gradient function's output; at the first NaN it raises and prints where that op was created in your forward code. The example is a hand-written L2 norm applied to a row of zeros, which is what a padding row looks like:

pythonnan_hunt.py
import torch


def my_norm(x):
    return (x ** 2).sum(dim=-1).sqrt()       # hand-written L2 norm


x = torch.zeros(2, 3)
x[0] = torch.tensor([1.0, 2.0, 2.0])         # row 1 stays all zeros (a padding row)
x.requires_grad_(True)

my_norm(x).sum().backward()
print(x.grad)                                 # no error, just NaNs

x.grad = None
with torch.autograd.set_detect_anomaly(True):
    try:
        my_norm(x).sum().backward()
    except RuntimeError as e:
        print("RuntimeError:", e)
tensor([[0.3333, 0.6667, 0.6667],
        [   nan,    nan,    nan]])

  File "nan_hunt.py", line 18, in <module>
    my_norm(x).sum().backward()
  File "nan_hunt.py", line 5, in my_norm

(Directory paths shortened.) Read it backwards through the chain rule: sqrt's derivative at 0 is 1 / (2·0) = inf, which is not NaN, so SqrtBackward0 passes. Then x ** 2's backward multiplies that inf by 2x = 0: NaN, flagged at PowBackward0, line 5. The fix is an epsilon inside the square root, or torch.linalg.vector_norm, which defines the gradient at 0 as 0. Your microgpt rms_norm has + 1e-5 for exactly this reason. Anomaly mode slows everything down; switch it on to hunt, then off.

"The loss isn't going down": a checklist

Work through these in order; each is cheap and rules out a whole class of bugs.

1. Check the loss at initialisation

A freshly initialised model should be unsure about everything, which means a roughly uniform prediction over V classes and a cross-entropy of ln V: ln 27 = 3.2958 for microgpt. Much higher means the initial logits are large (confidently wrong); much lower before any training usually means the answer leaks into the input.

import math

torch.manual_seed(0)
model = GPT()
x = torch.randint(0, 27, (32, 16))
y = torch.randint(0, 27, (32, 16))
with torch.no_grad():
    loss0 = F.cross_entropy(model(x).flatten(0, 1), y.flatten())
print(f"initial loss {loss0.item():.4f}   ln(27) = {math.log(27):.4f}")
# initial loss 3.6421   ln(27) = 3.2958

3.64 is a little high: PyTorch's default nn.Embedding initialisation is N(0, 1), larger than microgpt's 0.08, so the logits start wider than uniform. With every parameter re-initialised to N(0, 0.08) as microgpt does (torch.nn.init.normal_(p, std=0.08)), the same check gives 3.2998.

2. Look at gradient norms per parameter

  mlp.proj.weight   grad norm 0.1912
  head.weight       grad norm 0.3754

You are looking for zeros (a disconnected parameter, or dead ReLUs), NaN or inf, and norms that differ by many orders of magnitude between layers (vanishing or exploding gradients). Here every parameter gets a gradient and they shrink smoothly toward the input, which is normal.

3. Overfit one batch, and sweep the learning rate

A model with 4,192 parameters can memorise 32 random sequences. If it cannot drive the loss on one fixed batch close to zero, the bug is in the model, the loss or the optimizer, not in the data or the amount of training. Run it for several learning rates at once:

def overfit(lr, steps=300):
    torch.manual_seed(0)
    m = GPT()
    opt = torch.optim.Adam(m.parameters(), lr=lr)
    for _ in range(steps):
        loss = F.cross_entropy(m(x).flatten(0, 1), y.flatten())
        opt.zero_grad()
        loss.backward()
        opt.step()
    return loss.item()

5. The rest of the usual suspects

  • optimizer.zero_grad() missing, or called between backward() and step().
  • The optimizer was built from a different model's parameters, or before the model was replaced (Exercise 12.6 has a variant).
  • The learning-rate schedule is wrong: print the LR every N steps (microgpt prints it with the loss).
  • model.eval() was called for validation and model.train() never called again.
  • Logits passed through a softmax before cross_entropy, which applies its own (Exercise 12.4).

Checking against a reference

The strongest test of numerical code is a second, independent implementation that must agree with it. Three levels.

Gradients against finite differences

A derivative can be estimated without calculus: f'(x) ≈ (f(x + h) − f(x − h)) / 2h, the central finite difference. Do it in float64, because float32's rounding error swamps the difference for small h. torch.autograd.gradcheck does this for every input element and compares the whole Jacobian with autograd's.

def f(x):                                   # a little rms_norm + softmax pipeline
    return F.softmax(F.rms_norm(x, (4,), eps=1e-5), dim=-1)[..., 0].sum()

with torch.no_grad():

    numeric = (f(x + e) - f(x - e)) / (2 * h)
print(f"autograd {x.grad[1, 2].item():.10f}   finite diff {numeric.item():.10f}")

A scalar reference for the whole model

Your microgpt_scalar.py is the ideal reference: written one number at a time, it is slow but each line is obviously right. Load the same weights into a few lines in that style, on plain Python floats, and compare the next-token probabilities at every position with the tensor model's. Since all of GPT's weights are stored [out][in], .tolist() gives exactly microgpt's matrix layout.

import math


def linear(inputs, weights):                 # microgpt_scalar's linear, on floats
    return [sum(w * x for w, x in zip(row, inputs)) for row in weights]


def softmax(logits):
    m = max(logits)
    exps = [math.exp(v - m) for v in logits]
    total = sum(exps)
    return [e / total for e in exps]


def rms_norm(xs):
    scale = (sum(x * x for x in xs) / len(xs) + 1e-5) ** -0.5
    return [x * scale for x in xs]


def scalar_forward(W, token_ids, n_head=4, head_size=4, scale=4**-0.5):
    Wq, Wk, Wv = (W["attn.qkv.weight"][i * 16:(i + 1) * 16] for i in range(3))
    keys, values, all_probs = [], [], []
    for pos, tok in enumerate(token_ids):                  # one position at a time
        x = [a + b for a, b in zip(W["tok.weight"][tok], W["pos.weight"][pos])]
        h = rms_norm(x)
        q = linear(h, Wq)
        keys.append(linear(h, Wk))
        values.append(linear(h, Wv))
        heads = []
        for hd in range(n_head):
            s = slice(hd * head_size, (hd + 1) * head_size)
            att = softmax([sum(a * b for a, b in zip(q[s], k[s])) * scale
                           for k in keys])
            heads += [sum(a * v[s][d] for a, v in zip(att, values))
                      for d in range(head_size)]
        x = [a + b for a, b in zip(x, linear(heads, W["attn.proj.weight"]))]
        hidden = [max(0.0, u) for u in linear(rms_norm(x), W["mlp.fc.weight"])]
        x = [a + b for a, b in zip(x, linear(hidden, W["mlp.proj.weight"]))]
        all_probs.append(softmax(linear(x, W["head.weight"])))
    return all_probs

EX 12.4 medium The loss floor at 2.36

Show solution

cross_entropy applies its own log-softmax, so it is treating probabilities as logits. EX 12.5 medium The head split that peeks at the future

Someone got the view error from earlier in this chapter inside Attention.forward and "fixed" it by writing t.reshape(B, self.n_head, T, E // self.n_head) instead of t.view(B, T, self.n_head, E // self.n_head).transpose(1, 2). Shapes are fine and it trains. What is wrong, and how could a test catch it without a reference implementation?

Show solution

(B, T, E) is laid out token by token. Reshaping it directly to (B, H, T, D) cuts that memory into H consecutive chunks, so "head 0" gets the first T/H tokens' full embeddings rearranged as T fake positions. Positions now mix data from different real tokens, including later ones. The correct code splits each token's E into (H, D) first, then moves H forward with a transpose; view refused the buggy version because split leaves non-contiguous strides, and reshape silently copied.

A causality test needs no reference: change only the last token, and the outputs at all earlier positions must not change.

class BuggyAttention(Attention):
    def forward(self, x):
        B, T, E = x.shape
        q, k, v = self.qkv(x).split(E, dim=-1)
        q, k, v = (t.reshape(B, self.n_head, T, E // self.n_head)   # bug
                   for t in (q, k, v))
        y = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.proj(y.transpose(1, 2).reshape(B, T, E))


def leaks_future(model, T=10):
    """Change only the LAST token; outputs at earlier positions must not move."""
    torch.manual_seed(1)
    ids = torch.randint(0, 27, (1, T))
    ids2 = ids.clone()
    ids2[0, -1] = (ids[0, -1] + 1) % 27
    with torch.no_grad():
        a, b = model(ids), model(ids2)
    return not torch.allclose(a[:, :-1], b[:, :-1])


torch.manual_seed(0)
model = GPT()
print("correct attention leaks future:", leaks_future(model))   # False
model.attn.__class__ = BuggyAttention          # swap in the buggy forward, same weights
print("buggy attention leaks future:  ", leaks_future(model))   # True

A model that can see the future trains to a suspiciously low loss and then generates garbage, because at generation time the future is not there. Keep leaks_future in your test suite.

The isfinite(...).all() check is a sync on a GPU, so enable this only while debugging.

Recap

  • Read the last line of the error first. mat1 and mat2 shapes cannot be multiplied means inner dimensions differ (check [out][in] storage); device errors name both devices or say "Placeholder storage" on MPS; dtype errors want .long() targets and indices or .float() operands; the view error means "non-contiguous, use reshape or think about the layout".
  • Name dimensions in comments, assert shapes with the shape in the message, and print module output shapes with forward hooks (remove them with the handle).
  • Silent bugs: (B, 1) against (B,) broadcasting, softmax over the wrong dim, missing zero_grad, missing eval(), evaluating with grad on (3.5 GiB held in the example), .data edits that corrupt gradients, and parameters whose .grad is still None after backward.
  • The in-place error names the op whose saved tensor changed and its version numbers; make the edit out-of-place.
  • NaNs come from fully masked softmax rows, log(0), 0 × inf and fp16 overflow. Check with torch.isfinite; find NaN gradients with torch.autograd.set_detect_anomaly(True).
  • Loss not going down: initial loss ≈ ln V, per-layer grad norms, overfit one batch, sweep the LR, check target alignment (a loss that is too good is a bug too).
  • Check against references: gradcheck in float64 for gradients, assert_close with justified rtol/atol for outputs, and a scalar implementation in the style of microgpt_scalar.py loaded with the same weights.
