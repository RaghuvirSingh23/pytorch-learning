Chapter 08 The Training Loop

microgpt trains on one name per step. Real training feeds the model a batch of sequences at once, which means padding, masking, and a data pipeline. This chapter builds that pipeline with Dataset and DataLoader, writes the canonical train and eval loops line by line, and adds the habits that keep long runs honest: sanity checks, checkpoints you can resume bit-for-bit, reproducibility, and gradient accumulation. It ends with a complete script that trains a batched microgpt on CPU in under a second.

From one name per step to a batch

microgpt's PyTorch loop does this every step: take the next name, build input_ids and target_ids of length T (make_training_pair), run the model to get (T, 27) logits, compute F.cross_entropy, step. The gradient comes from one name, so it is noisy, and each step is a handful of tiny matrix multiplies that leave most of the hardware idle.

A mini-batch (usually just "batch") is B examples processed together. The model sees a (B, T) tensor of token ids and returns (B, T, 27) logits. The loss averages over all B × T predictions, so the gradient is an average over B names: less noise per step, and one big matmul instead of B small ones. An epoch is one full pass over the training set.

The catch: names have different lengths, and a tensor must be rectangular.

Padding a batch of names

Encode each name exactly as microgpt does: BOS (id 26), the letters, then BOS again to mark the end. Inputs are all tokens but the last, targets are all tokens but the first. Then pad every row to the longest one: fill the extra input slots with any valid token id (we use BOS) and the extra target slots with -100, the value F.cross_entropy ignores (Chapter 7).

pythonbatch.py
import torch

BOS, BLOCK, IGNORE = 26, 16, -100

def encode(name):
    return [BOS] + [ord(ch) - ord("a") for ch in name] + [BOS]

def make_pair(name):                       # microgpt's make_training_pair
    ids = encode(name)[: BLOCK + 1]
    return torch.tensor(ids[:-1]), torch.tensor(ids[1:])

def collate(batch):
    """Pad a list of (input, target) pairs to the longest one in the batch."""
    T = max(len(x) for x, _ in batch)
    inputs = torch.full((len(batch), T), BOS, dtype=torch.long)
    targets = torch.full((len(batch), T), IGNORE, dtype=torch.long)
    for row, (x, y) in enumerate(batch):
        inputs[row, : len(x)] = x
        targets[row, : len(y)] = y
    return inputs, targets

Read row 1 ("ava"): the input [26, 0, 21, 0] means "<BOS> a v a", the target [0, 21, 0, 26] means "a v a <end>", shifted by one. Then five pad slots. Only 18 of the 27 target slots are real; the loss must count those 18 and nothing else.

Why pads need no attention mask here

Pads go on the right, after the real tokens. With a causal mask, position t attends only to positions 0..t, so every real position only ever sees real tokens before it. The pad positions do compute garbage, but their targets are -100, so the garbage is never scored and sends back no gradient. Right padding plus causal attention plus ignore_index is all a decoder-only model needs for training. (Exercise 8.2 proves it: scramble the pad inputs and the loss does not move.) Left padding, used in batched generation, does need an explicit mask; Chapter 10 covers it.

The loss is now token-weighted

F.cross_entropy with reduction="mean" divides by the number of real targets in the batch, so a 9-token name counts 9 times as much as a 1-token one. microgpt averages per name (calculate_document_loss) and then each step is one name, so every name counts equally per step. Neither is wrong, but they are different objectives. Token weighting is what every LLM trainer uses, and it matches how microgpt's evaluate_model already scores the test set.

Dataset and DataLoader

PyTorch splits the data pipeline into two objects:

  • A Dataset answers two questions: how many examples (__len__) and what is example i (__getitem__). It knows nothing about batches.
  • A DataLoader wraps a dataset and yields batches. It picks the indices (in order, or shuffled), calls __getitem__ for each, and hands the list of examples to a collate function that stacks them into tensors.
# continues batch.py: torch, encode and BLOCK are defined there
from torch.utils.data import DataLoader, Dataset

class NamesDataset(Dataset):
    def __init__(self, names):
        self.names = names

    def __len__(self):
        return len(self.names)

    def __getitem__(self, i):
        ids = encode(self.names[i])[: BLOCK + 1]
        return torch.tensor(ids[:-1]), torch.tensor(ids[1:])   # (input, target)

ds = NamesDataset(["emma", "ava", "isabella"])
print(len(ds), ds[1])
# 3 (tensor([26,  0, 21,  0]), tensor([ 0, 21,  0, 26]))

Each for over the loader is one epoch and draws a fresh permutation from the generator. Seeding the generator makes the whole sequence of epochs repeatable, independent of any other random numbers your program uses. len(loader) is the number of batches per epoch.

num_workers and the macOS caveat

With num_workers=N > 0, the DataLoader starts N worker processes that build batches in parallel while the main process trains. That matters when __getitem__ is expensive (decoding images, reading files, tokenizing text on the fly). It needs two things your code must allow:

  • The main-module guard. On macOS (and Windows) Python starts worker processes with spawn: a fresh interpreter that re-imports your script. Without if __name__ == "__main__": around the training code, each worker would start training too. Python stops this with an error:
RuntimeError:
        An attempt has been made to start a new process before the
        current process has finished its bootstrapping phase.

        This probably means that you are not using fork to start your
        child processes and you have forgotten to use the proper idiom
        in the main module:

            if __name__ == '__main__':
                freeze_support()
                ...
  • Picklable dataset and collate_fn. They are sent to the workers by pickling, so they must be defined at module top level. A lambda fails: _pickle.PicklingError: Can't pickle <function <lambda> at 0x10945d1f0>: attribute lookup <lambda> on __main__ failed.

Linux (through Python 3.13) uses fork by default, which copies the parent process and hides both problems, so code written on Linux often breaks on a Mac. Workers also cost startup time: on the Apple Silicon laptop used for this tutorial, iterating the 95-name dataset once took 0.001 s with num_workers=0 and about 12 s with num_workers=2, nearly all of it spent starting two Python processes that each import torch. Your numbers will differ; the lesson is that for small in-memory data, num_workers=0 is right. When you do use workers, persistent_workers=True keeps them alive between epochs.

The canonical training loop

Every PyTorch training loop has the same skeleton. Here it is as it appears in the full script later in this chapter:

model.train()                                             # 1
while step < total_steps:
    for inputs, targets in train_loader:                  # 2
        logits = model(inputs)                            # 3  (B, T, 27)
        loss = F.cross_entropy(logits.view(-1, VOCAB),    # 4
                               targets.view(-1))
        optimizer.zero_grad(set_to_none=True)             # 5
        loss.backward()                                   # 6
        grad_norm = torch.nn.utils.clip_grad_norm_(       # 7
            model.parameters(), 1.0)
        optimizer.step()                                  # 8
        scheduler.step()                                  # 9
        step += 1
        if step % log_every == 0:                         # 10
            val_loss, val_ppl = evaluate(model, val_loader)
            print(step, loss.item(), val_loss, grad_norm.item())
        if step == total_steps:
            break
#linewhy it is there, and why there
1model.train()Puts every submodule in training mode. It changes behaviour only for layers like dropout and batch norm; microgpt has neither, so here it is a habit. Evaluation switches to eval mode, so something must switch back; our evaluate() does it on exit.
2for ... in train_loaderOne batch per iteration. The outer while counts optimizer steps rather than epochs, which is how LLM runs are specified.
3model(inputs)Forward pass. Autograd records the graph as it goes (Chapter 4).
4F.cross_entropyFlatten (B, T, C) to (B*T, C); pads are ignored via -100.
5zero_gradClears the previous step's gradients, which would otherwise be added to. Anywhere before backward() works; right before it is the clearest.
6loss.backward()Fills p.grad for every parameter and frees the graph.
7clip_grad_norm_Must come after backward (it needs the grads) and before step (it changes what the step uses).
8optimizer.step()Updates the weights in place from .grad.
9scheduler.step()After the optimizer, so step 0 used the schedule's first value (Chapter 7).
10loggingloss.item() copies one number to the CPU. On a GPU this forces the CPU to wait for the GPU (Chapter 11), so log every N steps, not every step.

microgpt's loop has the same lines in a slightly different order: it sets the lr by hand between backward() and step() instead of using a scheduler, and it has no clipping.

The evaluation loop

Evaluation runs the model over held-out data without training it. Three differences from the training loop:

  • model.eval() switches dropout and similar layers to inference behaviour. Switch back with model.train() afterwards.
  • torch.no_grad() (or the stricter torch.inference_mode(), which microgpt's evaluate_model uses) stops autograd from recording a graph: less memory, less time. Chapter 10 covers the difference.
  • The average must be token-weighted: sum the losses with reduction="sum", count the real targets, divide at the end. Perplexity is exp(average loss): the effective number of tokens the model is choosing between. A uniform guess over 27 tokens has perplexity 27.
@torch.no_grad()
def evaluate(model, loader):
    model.eval()
    total_loss, total_tokens = 0.0, 0
    for inputs, targets in loader:
        logits = model(inputs)
        total_loss += F.cross_entropy(
            logits.view(-1, VOCAB), targets.view(-1), reduction="sum"
        ).item()
        total_tokens += (targets != IGNORE).sum().item()
    model.train()
    avg = total_loss / total_tokens
    return avg, math.exp(avg)

To check this is the same number microgpt computes, run the trained model from the full script through both: microgpt's one-name-at-a-time evaluate_model, and the batched version at two batch sizes.

The complete script

Everything so far, in one file you can paste and run. The model is microgpt's FastMicroGPT with a batch dimension: the same architecture as Chapter 6's GPT, written as one compact class so the file stands alone. Same 4,192 parameters, the same N(0, 0.08) initialisation, F.rms_norm with no gain, and scaled_dot_product_attention(is_causal=True) in place of the hand-written causal mask and softmax. The query, key and value weights are stacked into one Linear(16, 48), which is the same 768 numbers. The names are inline, so there is no download. Like microgpt, it reads STEPS and LR from the environment.

pythontrain_names.py
import math
import os
import time

import torch
import torch.nn as nn
import torch.nn.functional as F
from torch.utils.data import DataLoader, Dataset

NAMES = """emma olivia ava isabella sophia mia charlotte amelia harper evelyn abigail
emily elizabeth sofia avery ella scarlett grace chloe victoria riley aria lily aubrey
zoey penelope lillian addison layla natalie camila hannah brooklyn zoe nora leah
savannah audrey claire eleanor skylar ellie samantha stella paisley violet mila
allison alexa anna hazel aaliyah ariana lucy caroline sarah genesis kennedy sadie
gabriella madelyn adeline maya autumn aurora piper hailey arianna kaylee ruby serenity
eva naomi nevaeh alice luna bella quinn lydia peyton melanie kylie aubree mackenzie
kinsley cora julia taylor katherine madeline gianna eliana elena vivian willow""".split()

BOS = 26             # a-z are 0..25; BOS marks both start and end, as in microgpt
VOCAB = 27
BLOCK = 16
IGNORE = -100        # F.cross_entropy's default ignore_index


def encode(name):
    return [BOS] + [ord(ch) - ord("a") for ch in name] + [BOS]


class NamesDataset(Dataset):
    def __init__(self, names):
        self.names = names

    def __len__(self):
        return len(self.names)

    def __getitem__(self, i):
        ids = encode(self.names[i])[: BLOCK + 1]
        return torch.tensor(ids[:-1]), torch.tensor(ids[1:])   # (input, target)


def collate(batch):
    """Pad a list of (input, target) pairs to the longest one in the batch."""
    T = max(len(x) for x, _ in batch)
    inputs = torch.full((len(batch), T), BOS, dtype=torch.long)
    targets = torch.full((len(batch), T), IGNORE, dtype=torch.long)
    for row, (x, y) in enumerate(batch):
        inputs[row, : len(x)] = x
        targets[row, : len(y)] = y
    return inputs, targets


class MicroGPT(nn.Module):
    """microgpt's FastMicroGPT, batched: (B, T) ids -> (B, T, 27) logits."""

    def __init__(self, d=16, heads=4):
        super().__init__()
        self.heads = heads
        self.tok = nn.Embedding(VOCAB, d)
        self.pos = nn.Embedding(BLOCK, d)
        self.qkv = nn.Linear(d, 3 * d, bias=False)    # query, key, value weights stacked
        self.proj = nn.Linear(d, d, bias=False)       # attention_output_weights
        self.up = nn.Linear(d, 4 * d, bias=False)     # mlp_expand_weights
        self.down = nn.Linear(4 * d, d, bias=False)   # mlp_contract_weights
        self.head = nn.Linear(d, VOCAB, bias=False)   # language_model_head_weights
        for p in self.parameters():
            nn.init.normal_(p, mean=0.0, std=0.08)    # microgpt's random.gauss(0, 0.08)

    def forward(self, idx):
        B, T = idx.shape
        d = self.tok.embedding_dim
        x = self.tok(idx) + self.pos(torch.arange(T, device=idx.device))
        h = F.rms_norm(x, (d,), eps=1e-5)
        q, k, v = self.qkv(h).split(d, dim=-1)
        q, k, v = (t.view(B, T, self.heads, -1).transpose(1, 2) for t in (q, k, v))
        a = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        x = x + self.proj(a.transpose(1, 2).reshape(B, T, d))
        h = F.rms_norm(x, (d,), eps=1e-5)
        x = x + self.down(F.relu(self.up(h)))
        return self.head(x)


@torch.no_grad()
def evaluate(model, loader):
    model.eval()
    total_loss, total_tokens = 0.0, 0
    for inputs, targets in loader:
        logits = model(inputs)
        total_loss += F.cross_entropy(
            logits.view(-1, VOCAB), targets.view(-1), reduction="sum"
        ).item()
        total_tokens += (targets != IGNORE).sum().item()
    model.train()
    avg = total_loss / total_tokens
    return avg, math.exp(avg)


@torch.no_grad()
def sample(model, generator, max_len=BLOCK):
    model.eval()
    ids = [BOS]
    while len(ids) < max_len:
        logits = model(torch.tensor([ids]))[0, -1]
        nxt = torch.multinomial(F.softmax(logits, dim=-1), 1, generator=generator).item()
        if nxt == BOS:
            break
        ids.append(nxt)
    model.train()
    return "".join(chr(ord("a") + i) for i in ids[1:])


def train(total_steps=200, peak_lr=3e-3, verbose=True):
    log = print if verbose else (lambda *args: None)
    warmup, log_every = total_steps // 20, max(1, total_steps // 8)

    torch.manual_seed(0)
    train_names, val_names = NAMES[:84], NAMES[84:]
    loader_gen = torch.Generator().manual_seed(0)
    train_loader = DataLoader(NamesDataset(train_names), batch_size=12, shuffle=True,
                              collate_fn=collate, drop_last=True, generator=loader_gen)
    val_loader = DataLoader(NamesDataset(val_names), batch_size=12, collate_fn=collate)

    model = MicroGPT()
    log(f"parameters: {sum(p.numel() for p in model.parameters())}")
    optimizer = torch.optim.AdamW(model.parameters(), lr=peak_lr, betas=(0.85, 0.99),
                                  eps=1e-8, weight_decay=0.0)

    def lr_factor(step):                       # warmup, then cosine down to 10%
        if step < warmup:
            return (step + 1) / warmup
        progress = (step - warmup) / (total_steps - warmup)
        return 0.1 + 0.9 * 0.5 * (1 + math.cos(math.pi * progress))

    scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, lr_factor)
    log(f"step    0  val {evaluate(model, val_loader)[0]:.4f}  (ln 27 = {math.log(27):.4f})")

    step, t0 = 0, time.perf_counter()
    model.train()
    while step < total_steps:
        for inputs, targets in train_loader:              # one pass = one epoch
            logits = model(inputs)                        # (B, T, 27)
            loss = F.cross_entropy(logits.view(-1, VOCAB), targets.view(-1))
            optimizer.zero_grad(set_to_none=True)
            loss.backward()
            grad_norm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
            optimizer.step()
            scheduler.step()
            step += 1
            if step % log_every == 0:
                val_loss, val_ppl = evaluate(model, val_loader)
                log(f"step {step:4d}  train {loss.item():.4f}  val {val_loss:.4f}"
                    f"  ppl {val_ppl:5.2f}  grad_norm {grad_norm.item():.3f}")
            if step == total_steps:
                break
    log(f"trained {total_steps} steps in {time.perf_counter() - t0:.1f}s")
    return model


def main():
    model = train(int(os.environ.get("STEPS", "200")), float(os.environ.get("LR", "3e-3")))
    g = torch.Generator().manual_seed(42)
    print("samples:", " ".join(sample(model, g) for _ in range(8)))


if __name__ == "__main__":
    main()

Sanity checks

Before trusting a long run, check three things. Each takes seconds and catches a whole class of bugs.

1. The first loss is about ln(vocab)

Step 0 above prints val 3.3043 against ln 27 = 3.2958. If it were 8 or 20, the initial logits are far too large (Chapter 7, the ln(C) baseline). If it were 0.5 before any training, the model can see the answer: typically the causal mask is missing and position t attends to the token it is supposed to predict.

2. The model can overfit one batch

Train on one fixed batch over and over. A correct model and loop drive the loss as low as the data allows. If it plateaus high, something between the loss and the weights is broken: a missing zero_grad, a detached tensor, an optimizer built on the wrong parameters, or a target off by one position.

"Overfit to about 0" has a catch for language models: the first prediction of every name is made from BOS alone, and the four names start with four different letters. No model can do better than probability 1/4 there, which costs ln 4 on each of 4 of the 25 targets. The loss lands exactly on that floor of 0.2218, which is the strongest possible evidence that the loop works. With a single name, the loss really does go to about 0 (Exercise 8.3).

Checkpoints and resuming

A checkpoint is everything needed to continue training as if it had never stopped. That is more than the weights:

  • model.state_dict(): the parameters and persistent buffers (Chapter 5).
  • optimizer.state_dict(): Adam's exp_avg, exp_avg_sq and step for every parameter, plus the param groups with their current lr.
  • scheduler.state_dict(): where the schedule is.
  • The step counter, and the random number generator states: the data-order generator, and torch.get_rng_state() for anything else random in the loop (dropout, sampling).

The test of a checkpoint is simple: run 20 steps straight; separately run 10, save, throw every object away, rebuild from scratch, load, run 10 more. The losses must be identical, not close. To make the data resumable, this demo draws each batch with torch.randint from its own generator, whose state goes in the checkpoint.

pythonresume_check.py
import torch
import torch.nn.functional as F
from train_names import NAMES, NamesDataset, MicroGPT, collate, VOCAB

dataset = NamesDataset(NAMES[:84])

def get_batch(gen, batch_size=12):          # random batch, driven by its own generator
    idx = torch.randint(len(dataset), (batch_size,), generator=gen)
    return collate([dataset[i] for i in idx.tolist()])

def make_run():
    torch.manual_seed(0)
    model = MicroGPT()
    opt = torch.optim.AdamW(model.parameters(), lr=3e-3, betas=(0.85, 0.99), weight_decay=0.1)
    sched = torch.optim.lr_scheduler.LambdaLR(opt, lambda s: 1.0 - s / 20)
    gen = torch.Generator().manual_seed(1)
    return model, opt, sched, gen

def train_steps(model, opt, sched, gen, start, end):
    losses = []
    for step in range(start, end):
        inputs, targets = get_batch(gen)
        loss = F.cross_entropy(model(inputs).view(-1, VOCAB), targets.view(-1))
        opt.zero_grad()
        loss.backward()
        opt.step()
        sched.step()
        losses.append(round(loss.item(), 6))
    return losses

# Run A: 20 steps without stopping
straight = train_steps(*make_run(), 0, 20)

# Run B: 10 steps, save, throw everything away, rebuild, load, 10 more
model, opt, sched, gen = make_run()
resumed = train_steps(model, opt, sched, gen, 0, 10)
torch.save({
    "model": model.state_dict(),
    "optimizer": opt.state_dict(),
    "scheduler": sched.state_dict(),
    "step": 10,
    "data_rng": gen.get_state(),
    "torch_rng": torch.get_rng_state(),
}, "ckpt.pt")
del model, opt, sched, gen

model, opt, sched, gen = make_run()          # fresh objects in their step-0 state
ckpt = torch.load("ckpt.pt", weights_only=True)
model.load_state_dict(ckpt["model"])
opt.load_state_dict(ckpt["optimizer"])
sched.load_state_dict(ckpt["scheduler"])
gen.set_state(ckpt["data_rng"])
torch.set_rng_state(ckpt["torch_rng"])
resumed += train_steps(model, opt, sched, gen, ckpt["step"], 20)

print(straight[9:13])
print(resumed[9:13])
print("identical:", straight == resumed)

# Run C: same, but "forget" the optimizer state
model, opt, sched, gen = make_run()
model.load_state_dict(ckpt["model"])
sched.load_state_dict(ckpt["scheduler"])
gen.set_state(ckpt["data_rng"])
print(train_steps(model, opt, sched, gen, 10, 13))
[3.130078, 3.147485, 3.135179, 3.101751]
[3.130078, 3.147485, 3.135179, 3.101751]
identical: True
[3.147485, 3.117953, 3.079063]

Run C loads the weights but builds a fresh optimizer: step 10's loss matches (it is computed before any update) and then the run diverges. A fresh Adam has zero moments, and its param_groups carry the initial lr instead of the decayed one. This is the bug you get from saving only model.state_dict().

Resuming a DataLoader mid-epoch takes one more idea: make each epoch's order depend only on the epoch number, then skip the batches already done. Exercise 8.5 does exactly that.

torch.load and weights_only

torch.save uses Python's pickle format, and unpickling an arbitrary file can run arbitrary code. Since PyTorch 2.6, torch.load defaults to weights_only=True: it only rebuilds tensors, primitive types (int, float, str, bool, None), and dicts, lists and tuples of them. Everything a normal checkpoint holds fits, including microgpt's own checkpoint (its character_to_id and config are plain dicts), so microgpt's weights_only=False is not actually needed. Anything else fails with a long message whose start is:

Pass map_location="cpu" (or a device) to load a checkpoint saved on a GPU onto a machine without one, as microgpt does with map_location=device.

Reproducibility

torch.manual_seed(s) seeds PyTorch's generator on every device (CPU, and each CUDA GPU). That covers weight initialisation, torch.randint, dropout and torch.multinomial sampling, unless you pass an explicit generator=. Python's random and NumPy have their own generators: seed them separately if you use them, as microgpt does with random.seed(42).

Seeds make the inputs to every operation the same; they do not promise that every operation is deterministic. Some GPU kernels use atomic additions whose order varies from run to run, so the float rounding varies. torch.use_deterministic_algorithms(True) tells PyTorch to choose deterministic implementations and to raise a RuntimeError for any op that has none (the docs list examples such as torch.histc on a CUDA tensor). On CUDA it also requires the environment variable CUBLAS_WORKSPACE_CONFIG=:4096:8 (or :16:8), otherwise even torch.mm raises. Add torch.backends.cudnn.benchmark = False so cuDNN does not pick its algorithm by timing. All of that needs a CUDA GPU; on CPU, the check below simply passes.

import torch
from train_names import train

torch.use_deterministic_algorithms(True)
a = train(50, 3e-3, verbose=False)
b = train(50, 3e-3, verbose=False)
print(all(torch.equal(p, q) for p, q in zip(a.parameters(), b.parameters())))   # True
print(torch.are_deterministic_algorithms_enabled())                            # True

Two runs of 50 steps produce bit-identical weights (torch.equal, not allclose), because train() seeds the model and the loader's generator. With num_workers > 0, each worker's torch generator is seeded from the loader's generator automatically, but NumPy and random inside workers are not; the DataLoader docs show a worker_init_fn that seeds them from torch.initial_seed(). Determinism has a cost (some deterministic kernels are slower), so many teams turn it on only when chasing a bug.

Gradient accumulation

Suppose the batch you want does not fit in memory. Because gradients add up across backward() calls (Chapter 4), you can run several small micro-batches, call backward() on each, and step once. That is gradient accumulation: the same gradient as one big batch, at the memory cost of a small one.

The loss must be scaled so the accumulated gradient equals the big-batch gradient. The common recipe is "divide each micro-batch loss by the number of micro-batches K". That is exact only when every micro-batch has the same number of real tokens. With padded names it does not:

pythonaccumulate.py
import torch
import torch.nn.functional as F
from train_names import NAMES, NamesDataset, MicroGPT, collate, VOCAB

ds = NamesDataset(NAMES)
big = [ds[i] for i in range(8)]                 # 8 names of different lengths
micro = [big[:4], big[4:]]                      # 2 micro-batches of 4

def grads(model):
    return torch.cat([p.grad.flatten() for p in model.parameters()])

def fresh():
    torch.manual_seed(0)
    return MicroGPT()

# reference: one batch of 8
m = fresh()
x, y = collate(big)
F.cross_entropy(m(x).view(-1, VOCAB), y.view(-1)).backward()
ref = grads(m)

# accumulate, dividing each micro-batch's mean loss by the number of micro-batches
m = fresh()
for chunk in micro:
    x, y = collate(chunk)
    (F.cross_entropy(m(x).view(-1, VOCAB), y.view(-1)) / len(micro)).backward()
print("divide by K:      ", (grads(m) - ref).abs().max().item())

# accumulate summed losses, divide by the TOTAL number of real target tokens
m = fresh()
n_tokens = sum((collate(chunk)[1] != -100).sum().item() for chunk in micro)
for chunk in micro:
    x, y = collate(chunk)
    (F.cross_entropy(m(x).view(-1, VOCAB), y.view(-1), reduction="sum") / n_tokens).backward()
print("divide by tokens: ", (grads(m) - ref).abs().max().item())
print([ (collate(c)[1] != -100).sum().item() for c in micro ], ref.abs().max().item())
divide by K:       0.0010072654113173485
divide by tokens:  5.587935447692871e-09
[25, 28] 0.04060910642147064

The micro-batches hold 25 and 28 real tokens. Dividing by K = 2 gives the first 25 tokens slightly more weight than the big batch does; the error is about 2.5% of the largest gradient. Summing and dividing by the total token count matches to float rounding. In a training loop: count the real tokens of all K micro-batches first (cheap, it is just the targets), then backward each with reduction="sum" divided by that count, then clip and step once.

Things that break accumulation

Calling zero_grad() inside the micro-batch loop (it erases what you accumulated). Clipping per micro-batch instead of once on the total. Stepping the scheduler per micro-batch instead of per optimizer step. And layers that compute statistics across the batch (batch norm) see small batches, which accumulation cannot fix; transformers use RMSNorm or LayerNorm, which work per token, so they are unaffected.

import torch

BOS, IGNORE = 26, -100

def encode(name):
    return [BOS] + [ord(ch) - ord("a") for ch in name] + [BOS]

def collate_with_lengths(batch, pad_id=0):
    lengths = torch.tensor([len(x) for x, _ in batch])
    T = int(lengths.max())
    inputs = torch.full((len(batch), T), pad_id, dtype=torch.long)
    targets = torch.full((len(batch), T), IGNORE, dtype=torch.long)
    for row, (x, y) in enumerate(batch):

        targets[row, : len(y)] = y
    return inputs, targets, lengths

pairs = []
for name in ["mia", "ella", "zoe"]:

print(lengths)

EX 8.5 hard Resume a DataLoader run mid-epoch, exactly

With 84 names and batch_size=12, drop_last=True, an epoch is 7 batches. Write a loop that trains 20 steps with a shuffled DataLoader, and a resumed version that stops after step 10 (in the middle of the second epoch), saves model and optimizer, rebuilds both from scratch, and continues to step 20. The two loss sequences must be identical. Hint: make each epoch's shuffle depend only on the epoch number.

Show solution 
import torch
import torch.nn.functional as F
from torch.utils.data import DataLoader
from train_names import NAMES, NamesDataset, MicroGPT, collate, VOCAB

dataset = NamesDataset(NAMES[:84])
BATCHES_PER_EPOCH = len(dataset) // 12                 # 7 with drop_last=True

def make_run():
    torch.manual_seed(0)
    model = MicroGPT()
    opt = torch.optim.AdamW(model.parameters(), lr=3e-3, betas=(0.85, 0.99))
    return model, opt

def run(model, opt, start_step, end_step):
    losses, step = [], start_step
    while step < end_step:
        epoch, skip = divmod(step, BATCHES_PER_EPOCH)
        gen = torch.Generator().manual_seed(1000 + epoch)    # order depends only on epoch
        loader = DataLoader(dataset, batch_size=12, shuffle=True, collate_fn=collate,
                            drop_last=True, generator=gen)
        for i, (inputs, targets) in enumerate(loader):
            if i < skip:
                continue                                      # already trained on these
            loss = F.cross_entropy(model(inputs).view(-1, VOCAB), targets.view(-1))
            opt.zero_grad()
            loss.backward()
            opt.step()
            losses.append(round(loss.item(), 6))
            step += 1
            if step == end_step:
                break
    return losses

straight = run(*make_run(), 0, 20)

model, opt = make_run()
resumed = run(model, opt, 0, 10)                              # stops mid-epoch 1
torch.save({"model": model.state_dict(), "opt": opt.state_dict(), "step": 10}, "mid.pt")
model, opt = make_run()
ckpt = torch.load("mid.pt")
model.load_state_dict(ckpt["model"])
opt.load_state_dict(ckpt["opt"])
resumed += run(model, opt, ckpt["step"], 20)
print(straight == resumed, straight[8:12])
# True [3.130168, 3.033649, 3.067718, 2.956724]

The only state the data pipeline needs is the step number: epoch and position within it follow from divmod. Skipping batches still runs __getitem__ and collate for them, which is fine for small data; for large datasets, a custom sampler that starts at an offset avoids that work, and the separate torchdata package offers a StatefulDataLoader with its own state_dict().

Recap

  • Batches turn (T,) into (B, T). Encode with BOS on both ends, shift by one for targets, right-pad inputs with any valid id and targets with -100. Causal attention plus ignore_index makes pads harmless.
  • Dataset = __len__ + __getitem__; DataLoader batches it. Variable-length data needs a collate_fn. Use shuffle=True with a seeded generator for training, drop_last for equal batches.
  • num_workers > 0 on macOS means spawn: guard with if __name__ == "__main__":, keep dataset and collate at top level, and expect seconds of startup.
  • The loop: train(), forward, loss, zero_grad, backward, clip, optimizer.step(), scheduler.step(), log every N steps.
  • Eval: eval(), no_grad/inference_mode, sum losses and divide by real tokens; perplexity is exp(loss). Averaging batch means is subtly wrong.
  • Sanity checks: first loss ≈ ln(V); overfit one batch down to the data's floor; read the train/val curves.
  • Checkpoints hold model, optimizer, scheduler, step and RNG states; a correct resume reproduces the losses exactly. torch.load defaults to weights_only=True since 2.6.
  • Reproducibility: seed everything, seed the loader's generator, and use use_deterministic_algorithms(True) (plus CUBLAS_WORKSPACE_CONFIG on CUDA) when you need bit-identical runs.
  • Gradient accumulation: backward several micro-batches, step once. With padding, divide summed losses by the total token count, not by K.
