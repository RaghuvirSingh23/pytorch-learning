Tensors & broadcasting (1–10)

What is a tensor, physically?

A flat block of memory (the storage) plus metadata that says how to read it: shape, stride, storage offset, dtype and device. The stride is how many elements to skip in storage to move one step along each dimension, exactly the base + i*stride0 + j*stride1 you would write for a C array. Transpose, slicing, view and expand only rewrite the metadata and share the storage, which is why they cost nothing.

x = torch.arange(6.).reshape(2, 3)
print(x.shape, x.stride(), x.dtype, x.device)
# torch.Size([2, 3]) (3, 1) torch.float32 cpu
t = x.t()
print(t.shape, t.stride(), t.data_ptr() == x.data_ptr())
# torch.Size([3, 2]) (1, 3) True
view vs reshape?

view never copies: it returns a tensor on the same storage, and raises if the new shape can't be expressed with strides over the existing layout. reshape returns a view when it can and silently copies when it can't. Use view when you are relying on "no copy" and want an error if that assumption breaks; use reshape when you don't care.

x = torch.arange(6).reshape(2, 3)
t = x.t()                  # strides (1, 3): no longer row-major
t.view(6)
# RuntimeError: view size is not compatible with input tensor's size and stride (at least one dimension spans across two contiguous subspaces). Use .reshape(...) instead.
r = t.reshape(6)           # works, by copying
print(r, r.data_ptr() == x.data_ptr())
# tensor([0, 3, 1, 4, 2, 5]) False
What does contiguous() do, and when do you need it?

A tensor is contiguous when its elements sit in storage in row-major order with no gaps. transpose, permute and expand return non-contiguous views; .contiguous() copies into a fresh row-major buffer (and returns self if it already is). You need it before .view() on such a tensor, and some custom kernels require it. The classic spot is merging attention heads back into (B, T, C); microgpt's .transpose(0, 1).reshape(...) does the same copy implicitly.

y = torch.randn(2, 4, 5, 4)            # (B, H, T, D)
yt = y.transpose(1, 2)                 # (B, T, H, D), a view
print(yt.is_contiguous())              # False
out = yt.contiguous().view(2, 5, 16)   # (B, T, C)
print(out.shape)                       # torch.Size([2, 5, 16])
State the broadcasting rules.

Line the shapes up from the right. Two sizes are compatible if they are equal or one of them is 1; a missing dimension counts as 1. The result takes the larger size in each position, and size-1 dimensions are stretched without copying (stride 0). Adding a per-channel vector of shape (C,) to (B, T, C) works for this reason.

print((torch.ones(4, 1) + torch.arange(3.)).shape)      # torch.Size([4, 3])
print((torch.zeros(2, 5, 16) * torch.ones(16)).shape)   # torch.Size([2, 5, 16])
torch.ones(2, 3) + torch.ones(2)
# RuntimeError: The size of tensor a (3) must match the size of tensor b (2) at non-singleton dimension 1
Show a broadcasting bug that raises no error.

A (N, 1) prediction against an (N,) target broadcasts to (N, N): every prediction is compared with every target. Below, the predictions are perfect and the loss still comes out as 2.5. mse_loss at least emits a UserWarning; most elementwise code doesn't. Assert shapes at module boundaries and squeeze explicitly.

pred = torch.arange(4.).unsqueeze(1)   # (4, 1): perfect values, wrong shape
target = torch.arange(4.)              # (4,)
print((pred - target).shape)           # torch.Size([4, 4])
print(F.mse_loss(pred, target))        # tensor(2.5000)  plus a UserWarning
print(F.mse_loss(pred.squeeze(-1), target))   # tensor(0.)
Why is x.T @ y shaped (D, K)?

For 2-D operands, (n, k) @ (k, m) -> (n, m): the inner sizes must match and disappear. With x of shape (N, D) and y of shape (N, K), the shared axis is the N samples, so you transpose x to put it in the middle: (D, N) @ (N, K) -> (D, K). That is the weight gradient of a linear layer, summed over the batch. With more than two dimensions, @ treats all leading dimensions as batch dimensions (broadcast) and multiplies the last two; use .mT or .transpose(-2, -1) there, because .T on a non-2-D tensor is deprecated.

x, y = torch.randn(100, 16), torch.randn(100, 27)
print((x.T @ y).shape)                    # torch.Size([16, 27])
h = torch.randn(8, 16, 16)                # (B, T, C)
W = torch.randn(27, 16)                   # (out, in), like microgpt's head weights
print((h @ W.T).shape)                    # torch.Size([8, 16, 27])
q = torch.randn(8, 4, 16, 4)              # (B, H, T, D)
print((q @ q.transpose(-2, -1)).shape)    # torch.Size([8, 4, 16, 16])
What do dim and keepdim mean in a reduction?

dim names the axis that is reduced away; it disappears from the shape. keepdim=True leaves a size-1 axis in its place so the result broadcasts back against the input. That is how you normalise rows, and it is why softmax over the vocabulary is softmax(dim=-1).

m = torch.tensor([[1., 2., 3.], [4., 5., 6.]])
print(m.sum(dim=0))                    # tensor([5., 7., 9.])
print(m.sum(dim=1))                    # tensor([ 6., 15.])
print(m / m.sum(dim=1, keepdim=True))
# tensor([[0.1667, 0.3333, 0.5000],
#         [0.2667, 0.3333, 0.4000]])
m / m.sum(dim=1)                       # (2, 3) / (2,): wrong axis lines up
# RuntimeError: The size of tensor a (3) must match the size of tensor b (2) at non-singleton dimension 1
How do you pick the target's log-probability out of each row?

microgpt's negative_log_likelihood did probabilities[target_id] for one position. For a batch, index with two integer tensors, one for the rows and one for the columns, or use gather. F.cross_entropy does exactly this, plus the log-softmax and the mean.

torch.manual_seed(0)
logits = torch.randn(3, 5)
targets = torch.tensor([4, 0, 2])
logp = logits.log_softmax(dim=-1)
picked = logp[torch.arange(3), targets]       # one element per row
print(picked)                                 # tensor([-3.1168, -3.0493, -2.5657])
print(torch.equal(picked, logp.gather(1, targets.unsqueeze(1)).squeeze(1)))   # True
print(-picked.mean(), F.cross_entropy(logits, targets))   # tensor(2.9106) tensor(2.9106)
When do two tensors share memory?

Views share storage with their base: slices, view, transpose, expand, detach. So do torch.from_numpy and .numpy() on CPU. An in-place op (+=, anything ending in _) on a view writes through to the base, while v = v + 5 makes a new tensor. Use .clone() when you need an independent copy.

x = torch.zeros(3)
v = x[1:]
v += 5                       # in place, through the view
print(x)                     # tensor([0., 5., 5.])
n = np.zeros(3, dtype=np.float32)
torch.from_numpy(n)[0] = 7
print(n)                     # [7. 0. 0.]
What dtype do you get, and what is type promotion?

Integer literals give int64; float literals give the default float dtype, float32; NumPy float arrays arrive as float64. True division of integers gives a float, // stays integer. Two tensors of different dtypes promote to the wider one, but a Python scalar does not widen a tensor's float dtype. The common real bug is a float64 tensor from NumPy meeting float32 weights: nn.Linear raises mat1 and mat2 must have the same dtype, but got Double and Float.

i = torch.tensor([1, 2, 3])
print(i.dtype, (i / 2).dtype, i // 2)
# torch.int64 torch.float32 tensor([0, 1, 1])
f = torch.tensor([1.0])
print(f.dtype, (f + torch.tensor([1.0], dtype=torch.float64)).dtype, (f + 2.5).dtype)
# torch.float32 torch.float64 torch.float32
print(torch.from_numpy(np.array([1.0])).dtype)                  # torch.float64
print((torch.tensor([1.0], dtype=torch.float16) * 3.0).dtype)   # torch.float16

Autograd (11–20)

What is a leaf tensor, and why is .grad sometimes None?

A leaf is a tensor that no tracked op produced: one you created with requires_grad=True, or any nn.Parameter. backward() stores .grad only on leaves; intermediate gradients are computed, used and thrown away (call .retain_grad() to keep one). Your Value class kept a .grad on every node; PyTorch keeps only the leaves to save memory. Watch out: .to() is an op, so the result of torch.randn(2, requires_grad=True).to(torch.float64) is not a leaf and never gets a .grad. Create tensors directly with the dtype and device you want.

w = torch.tensor([2.0, 3.0], requires_grad=True)
y = w * 3
print(w.is_leaf, y.is_leaf)       # True False
y.sum().backward()
print(w.grad)                     # tensor([3., 3.])
print(y.grad)                     # None, with a UserWarning about non-leaf .grad
d = torch.randn(2, requires_grad=True).to(torch.float64)
print(d.is_leaf)                  # False
Why do gradients accumulate, and why zero_grad()?

backward() adds into .grad; it never overwrites. That is the same += your Value.backward() did, and the reason microgpt reset every parameter.grad = 0.0 before each step. It is deliberate: a parameter used in several places sums its contributions, and you can run backward on several micro-batches before one optimizer step (gradient accumulation). Forget to clear and each step uses the sum of all past gradients. optimizer.zero_grad() sets them to None by default (set_to_none=True), which skips a memset.

w = torch.tensor(1.0, requires_grad=True)
for _ in range(3):
    (w * 2).backward()
    print(w.grad)          # tensor(2.), then tensor(4.), then tensor(6.)
no_grad vs inference_mode vs detach?

torch.no_grad() is a context in which ops are not recorded; the outputs are ordinary tensors you can later feed into autograd as constants. Use it for evaluation, EMA updates and manual weight edits. torch.inference_mode() is a stricter, faster version that also skips version counting and view tracking; its outputs are "inference tensors" that autograd refuses to use later. microgpt's evaluate_model and generate_name use it, which is right for pure serving. x.detach() acts on one tensor: same storage, cut from the graph. Use it to stop gradients along one path, and remember in-place edits to it change the original.

w = torch.ones(2, requires_grad=True)
with torch.no_grad():
    a = w * 2
with torch.inference_mode():
    b = w * 2
print(a.requires_grad, a.is_inference())   # False False
print(b.requires_grad, b.is_inference())   # False True
(w * b).sum().backward()
# RuntimeError: Inference tensors cannot be saved for backward. To work around you can make a clone to get a normal tensor and use it in autograd.
What does loss.backward() actually do?

The forward pass records a graph: every result tensor has a grad_fn pointing at the backward node of the op that made it. backward() walks that graph in reverse topological order from the loss, and each node applies its local derivative to the incoming gradient (the chain rule), accumulating into the leaves' .grad. It is your Value.backward() with build_topological_order, except that a node is a whole-tensor op (one node for a 16x16 matmul instead of 256 multiplies), its backward is a compiled kernel, and the graph is freed afterwards. It needs a scalar to start from, or an explicit gradient tensor.

x = torch.tensor([1.0, 2.0], requires_grad=True)
y = x ** 2
print(y.grad_fn.name())           # PowBackward0
y.backward()
# RuntimeError: grad can be implicitly created only for scalar outputs
y.backward(torch.ones_like(y))    # same as y.sum().backward()
print(x.grad)                     # tensor([2., 4.])
What causes "Trying to backward through the graph a second time"?

After backward(), autograd frees the intermediate values it saved during forward, to get the memory back. A second backward through the same graph has nothing left to use. In real code this is almost always a bug: a tensor from the previous iteration (a hidden state, a cache, a running total_loss = total_loss + loss) is still connected to the old graph. Detach the carried state or recompute it. retain_graph=True is only for when you really need two backward passes, and it costs memory.

x = torch.tensor(2.0, requires_grad=True)
y = x.exp()
y.backward()
y.backward()
# RuntimeError: Trying to backward through the graph a second time (or directly access saved tensors after they have already been freed). ...
Why does an in-place op break backward?

Many backward formulas need values saved from forward: sigmoid's derivative is s * (1 - s), computed from its output. Every tensor carries a version counter that each in-place op bumps; at backward time autograd checks that the saved tensors still have the version it recorded and raises if not. Fix it with the out-of-place form (y = y + 1) or a clone().

x = torch.randn(3, requires_grad=True)
y = x.sigmoid()
y.add_(1)                # in place: y is now at version 1
y.sum().backward()
# RuntimeError: one of the variables needed for gradient computation has been modified by an inplace operation: [torch.FloatTensor [3]], which is output 0 of SigmoidBackward0, is at version 1; expected version 0 instead. Hint: ...
How do you freeze part of a model?

Call requires_grad_(False) on those parameters. Autograd then skips their gradients (saving compute and memory) and their .grad stays None, so the optimizer leaves them alone. Pass only the trainable ones to the optimizer so it doesn't allocate Adam state for frozen weights. Freezing is not eval(): that changes dropout and batch-norm behaviour, requires_grad controls gradients. This is how you fine-tune a head on a frozen backbone, or train LoRA adapters.

torch.manual_seed(0)
m = nn.Sequential(nn.Linear(16, 64), nn.ReLU(), nn.Linear(64, 27))
for p in m[0].parameters():
    p.requires_grad_(False)
print(sum(p.numel() for p in m.parameters()))                      # 2843
print(sum(p.numel() for p in m.parameters() if p.requires_grad))   # 1755
opt = torch.optim.AdamW([p for p in m.parameters() if p.requires_grad], lr=1e-3)
How do you check that a gradient is correct?

torch.autograd.gradcheck compares autograd's analytic Jacobian against finite differences. Give it float64 inputs: in float32 the finite differences are so noisy that it reports GradcheckError: Jacobian mismatch on correct code. Use it for every custom autograd.Function or hand-written backward. For a whole model, compare against a reference implementation instead, for example microgpt's scalar engine on the same weights.

def rms_norm(x):
    return x * (x.pow(2).mean(-1, keepdim=True) + 1e-5).rsqrt()

torch.manual_seed(0)
inp = torch.randn(3, 16, dtype=torch.float64, requires_grad=True)
print(torch.autograd.gradcheck(rms_norm, (inp,)))   # True
How do you get gradients with respect to the inputs, or second derivatives?

torch.autograd.grad(outputs, inputs) returns the gradients instead of accumulating them into .grad, so it doesn't disturb parameter gradients. Pass create_graph=True to make the returned gradient differentiable itself, which gives you second derivatives (gradient penalties, meta-learning). Typical uses: saliency (which input embeddings mattered), adversarial inputs, physics-style losses.

x = torch.tensor(2.0, requires_grad=True)
y = x ** 3
(dy,) = torch.autograd.grad(y, x, create_graph=True)   # 3x^2
(d2y,) = torch.autograd.grad(dy, x)                    # 6x
print(dy, d2y, x.grad)
# tensor(12., grad_fn=<MulBackward0>) tensor(12.) None
When do you write a custom autograd.Function?

When the gradient you want is not the true derivative (straight-through estimators for quantisation), when you call a fused Triton or CUDA kernel that comes with its own backward, or when you want to recompute instead of saving activations. You subclass torch.autograd.Function with static forward(ctx, ...) and backward(ctx, grad_out), stashing tensors with ctx.save_for_backward. It is the tensor-level version of building a Value with its local_gradients. Always gradcheck it.

class MyReLU(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return x.clamp(min=0)

    @staticmethod
    def backward(ctx, grad_out):
        (x,) = ctx.saved_tensors
        return grad_out * (x > 0).to(grad_out.dtype)

x = torch.tensor([-1.0, 0.5, 2.0], requires_grad=True)
MyReLU.apply(x).sum().backward()
print(x.grad)          # tensor([0., 1., 1.])

nn.Module & training (21–30)

Parameters vs buffers vs plain tensor attributes?

All three are tensors stored on a module; they differ in what the module does with them.

KindIn parameters() (trained)In state_dictMoved by .to()
nn.Parameteryesyesyes
register_buffer(...)noyesyes
register_buffer(..., persistent=False)nonoyes
plain self.x = torch.tensor(...)nonono

microgpt's causal mask is a non-persistent buffer: it follows the model to the device but isn't saved, because it can be rebuilt from block_size. A plain tensor attribute is the bug: it stays on the CPU when the model moves to the GPU.

class Attn(nn.Module):
    def __init__(self):
        super().__init__()
        self.wq = nn.Parameter(torch.randn(16, 16))
        self.register_buffer("mask", torch.ones(16, 16).tril().bool(), persistent=False)
        self.register_buffer("step", torch.zeros((), dtype=torch.long))
        self.scale = torch.tensor(0.5)            # invisible to the module

m = Attn().to(torch.float64)
print([n for n, _ in m.named_parameters()])     # ['wq']
print([n for n, _ in m.named_buffers()])        # ['mask', 'step']
print(list(m.state_dict().keys()))              # ['wq', 'step']
print(m.wq.dtype, m.mask.dtype, m.scale.dtype)  # torch.float64 torch.bool torch.float32
What does model.eval() change, and what doesn't it?

It sets self.training = False on the module and every child; that's all. Modules that read the flag change behaviour: Dropout becomes the identity, BatchNorm uses its running statistics and stops updating them. It does not turn off autograd (the graph is still built and activations still kept) and doesn't touch requires_grad, so pair it with torch.inference_mode(). microgpt has no dropout or batch norm, so eval() changes nothing numerically there; call it anyway.

torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 4), nn.Dropout(p=0.5))
x = torch.ones(1, 4)
print(net(x))       # training mode: random zeros, survivors scaled by 2
# tensor([[-0.6347,  1.2561, -1.0009, -0.0000]], grad_fn=<MulBackward0>)
net.eval()
out = net(x)
print(out)          # dropout is now the identity
# tensor([[-0.3173,  0.6281, -0.5004, -1.2141]], grad_fn=<AddmmBackward0>)
print(out.requires_grad)   # True: eval() did not turn off autograd
Why does F.cross_entropy take logits, not probabilities?

It computes log_softmax and the negative log-likelihood in one step, and log_softmax is evaluated as x - logsumexp(x) with the max subtracted first, so it never overflows or takes log(0). Doing softmax then log yourself gives inf for large logits. Passing probabilities applies softmax twice: the loss is wrong, gradients are squashed, and nothing errors. Shapes: logits (N, C) float, targets (N,) int64 class indices.

logits = torch.tensor([[1000.0, 0.0]])
target = torch.tensor([1])
print(-logits.softmax(-1).log()[0, 1])     # tensor(inf)
print(F.cross_entropy(logits, target))     # tensor(1000.)
logits = torch.tensor([[2.0, 1.0, 0.1]])
target = torch.tensor([0])
print(F.cross_entropy(logits, target))                 # tensor(0.4170)
print(F.cross_entropy(logits.softmax(-1), target))     # tensor(0.8021): double softmax
Adam vs AdamW?

Same moment estimates and update as your apply_adam; they differ only in weight decay. Adam(weight_decay=wd) adds wd * p to the gradient, and that term then gets divided by sqrt(v) like the rest, so the decay depends on gradient history; a weight with no loss gradient is decayed by about lr per step whatever wd is. AdamW decouples it: p -= lr * wd * p, then the normal Adam step. AdamW is the transformer default. Their default weight_decay also differs: 0.01 for AdamW, 0 for Adam.

for cls in (torch.optim.Adam, torch.optim.AdamW):
    p = nn.Parameter(torch.tensor([1.0]))
    opt = cls([p], lr=0.01, weight_decay=0.1)
    for _ in range(10):
        p.grad = torch.zeros(1)        # no loss gradient: only decay acts
        opt.step()
    print(cls.__name__, p.data)
# Adam tensor([0.9003])
# AdamW tensor([0.9900])
What is the correct order of a training step?

Forward, loss, clear grads, backward, clip, optimizer step, scheduler step. zero_grad can go anywhere before backward. Common slips: stepping the scheduler before the optimizer (PyTorch warns "Detected call of `lr_scheduler.step()` before `optimizer.step()`" and you skip the first LR value), clipping after step() (too late), and calling loss.item() every step on a GPU (a sync, see q45). microgpt's loop has the same order, with the schedule written by hand.

for x, y in loader:
    logits = model(x)                                         # 1. forward
    loss = F.cross_entropy(logits.view(-1, V), y.view(-1))    # 2. loss
    optimizer.zero_grad(set_to_none=True)                     # 3. clear old grads
    loss.backward()                                           # 4. fill .grad
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)   # 5. optional clip
    optimizer.step()                                          # 6. update weights
    scheduler.step()                                          # 7. next learning rate
What exactly does clip_grad_norm_ do?

It computes one global L2 norm over all the parameters' gradients, as if concatenated into a single vector. If that norm exceeds max_norm, it multiplies every gradient by max_norm / total_norm: the direction is kept, only the length is capped. It returns the norm before clipping; log it, because spikes in the gradient norm are usually the first sign of an unstable run.

lin = nn.Linear(2, 2, bias=False)
with torch.no_grad():
    lin.weight.fill_(1.0)
lin(torch.full((1, 2), 10.0)).sum().backward()
print(lin.weight.grad)    # all four entries 10: global norm sqrt(4 * 100) = 20
total = torch.nn.utils.clip_grad_norm_(lin.parameters(), max_norm=1.0)
print(total)              # tensor(20.)
print(lin.weight.grad)    # all four entries 10 * 1/20 = 0.5
How do DataLoader workers work, and how many should you use?

With num_workers=0 (the default), __getitem__ and collate_fn run in the training process between steps. With N > 0 the loader starts N worker processes that each build whole batches, round robin, and keep 2 batches each in flight (prefetch_factor), so the accelerator doesn't wait for data. Increase workers until data time disappears from the profile; add pin_memory=True when feeding a CUDA GPU and persistent_workers=True to avoid restarting them every epoch. On macOS and Windows the workers are spawned, so the dataset must be picklable and the script needs an if __name__ == "__main__": guard. For small in-memory data such as names.txt, 0 workers is fastest: process start-up and inter-process copies cost more than the work.

from torch.utils.data import Dataset, DataLoader, get_worker_info

class Squares(Dataset):
    def __len__(self):
        return 8
    def __getitem__(self, i):
        info = get_worker_info()           # None in the main process
        return torch.tensor([i * i, -1 if info is None else info.id])

if __name__ == "__main__":
    loader = DataLoader(Squares(), batch_size=2, num_workers=2, persistent_workers=True)
    for batch in loader:
        print(batch[:, 0].tolist(), "from worker", batch[0, 1].item())
# [0, 1] from worker 0
# [4, 9] from worker 1
# [16, 25] from worker 0
# [36, 49] from worker 1
How do you checkpoint a training run so it can resume?

Save state_dicts, not module objects: model, optimizer (Adam's m, v and step count per parameter), scheduler, the step number, RNG states and the config. To restore, build the same objects and call load_state_dict on each. Since PyTorch 2.6, torch.load defaults to weights_only=True: tensors, dicts, lists, strings and numbers load, arbitrary pickled objects (such as a whole saved nn.Module) raise UnpicklingError, which protects you from malicious checkpoint files. microgpt's checkpoint holds only such plain data, so it would load without its weights_only=False.

torch.save({"model": model.state_dict(), "optimizer": opt.state_dict(),
            "scheduler": sched.state_dict(), "step": step,
            "torch_rng": torch.get_rng_state()}, "ckpt.pt")

ckpt = torch.load("ckpt.pt", map_location="cpu")    # weights_only=True by default
model.load_state_dict(ckpt["model"])
opt.load_state_dict(ckpt["optimizer"])
sched.load_state_dict(ckpt["scheduler"])
torch.set_rng_state(ckpt["torch_rng"])
How do you make training reproducible?

Seed every generator (random, NumPy, torch.manual_seed, which covers CPU and all CUDA devices), make the data order deterministic (a seeded generator= for the DataLoader), and call torch.use_deterministic_algorithms(True), which picks deterministic kernels or raises if an op has none. On CUDA also set CUBLAS_WORKSPACE_CONFIG=:4096:8 and torch.backends.cudnn.benchmark = False. Even then, bitwise equality is only promised on the same hardware, library versions and settings: a different GPU, batch size or thread count changes the order of float additions.

def run(seed):
    random.seed(seed); np.random.seed(seed); torch.manual_seed(seed)
    m = nn.Linear(8, 1)
    opt = torch.optim.SGD(m.parameters(), lr=0.1)
    for _ in range(5):
        loss = m(torch.randn(4, 8)).pow(2).mean()
        opt.zero_grad(); loss.backward(); opt.step()
    return loss.item()

torch.use_deterministic_algorithms(True)
print(run(0) == run(0))     # True
The loss is nan. How do you debug it?

First find the first step where it happens (assert torch.isfinite(loss)). Then check that batch: bad data, or every target masked out, which makes a mean over zero tokens and is itself nan. Look at the gradient-norm history: a climb before the nan means LR too high, so add warmup or clipping. Then look for unsafe math: log(0), a division by a norm without eps, sqrt at 0 in backward, exp overflow, fp16 values above 65504. Finally, torch.autograd.detect_anomaly() names the op whose backward produced the nan and prints its forward traceback. It is slow, so use it only for debugging.

x = torch.tensor(0.0, requires_grad=True)
(x.sqrt() * 0).backward()
print(x.grad)          # tensor(nan): 0 * inf in the chain rule
x.grad = None
with torch.autograd.detect_anomaly():
    (x.sqrt() * 0).backward()
# RuntimeError: Function 'SqrtBackward0' returned nan values in its 0th output.

Transformers in PyTorch (31–40)

Why scale attention scores by √d?

If the components of q and k have unit variance and are independent, q · k is a sum of d unit-variance products: variance d, standard deviation √d. For d = 64 the scores have std 8, softmax saturates to nearly one-hot, and gradients through it vanish. Dividing by √d brings the std back to 1. microgpt does attention_logits / head_size**0.5, a divide by 2 for its 4-wide heads.

torch.manual_seed(0)
d = 64
q, k = torch.randn(10000, d), torch.randn(10000, d)
s = (q * k).sum(-1)
print(f"{s.std():.2f} {(s / d**0.5).std():.2f}")     # 8.00 1.00
torch.manual_seed(0)
q1, K = torch.randn(1, d), torch.randn(16, d)
raw = q1 @ K.T
print(f"{raw.softmax(-1).max():.3f} {(raw / d**0.5).softmax(-1).max():.3f}")   # 0.995 0.222
How do you build and apply a causal mask?

Position t may attend to positions 0..t. Build a lower-triangular boolean matrix (True = allowed) and set the disallowed scores to -inf before softmax, so they get weight exactly 0 and every row still sums to 1. microgpt stores the inverse, triu(diagonal=1) meaning "blocked", and calls masked_fill(mask, -inf); it's the same thing. Register it once as a buffer of size block_size and slice [:T, :T].

T = 4
mask = torch.tril(torch.ones(T, T, dtype=torch.bool))
print(mask)
# tensor([[ True, False, False, False],
#         [ True,  True, False, False],
#         [ True,  True,  True, False],
#         [ True,  True,  True,  True]])
torch.manual_seed(0)
w = torch.randn(T, T).masked_fill(~mask, float("-inf")).softmax(dim=-1)
print(w)
# tensor([[1.0000, 0.0000, 0.0000, 0.0000],
#         [0.5391, 0.4609, 0.0000, 0.0000],
#         [0.4478, 0.0917, 0.4604, 0.0000],
#         [0.1340, 0.4099, 0.3632, 0.0928]])
What is F.scaled_dot_product_attention, and why use it?

One call that computes softmax(q kᵀ / √d + mask) v on (B, H, T, D) inputs and dispatches to the best kernel available: FlashAttention or memory-efficient attention on CUDA (neither materialises the T x T score matrix), a fused kernel on CPU, or a plain math fallback. Use is_causal=True for decoder self-attention. The trap: a boolean attn_mask means True = may attend, the opposite of masked_fill's True = blocked.

torch.manual_seed(0)
B, H, T, D = 2, 4, 16, 4
q, k, v = (torch.randn(B, H, T, D) for _ in range(3))
mask = torch.tril(torch.ones(T, T, dtype=torch.bool))
att = (q @ k.transpose(-2, -1)) / D**0.5
manual = att.masked_fill(~mask, float("-inf")).softmax(-1) @ v
fused = F.scaled_dot_product_attention(q, k, v, is_causal=True)
print((manual - fused).abs().max())     # tensor(2.3842e-07)
Walk through the shapes in multi-head attention.

Project (B, T, C) to q, k, v, each (B, T, C). Split C into H heads of size D = C / H with view(B, T, H, D), then transpose(1, 2) to (B, H, T, D) so the heads become a batch dimension. Scores are (B, H, T, T), the weighted values (B, H, T, D); transpose back and merge to (B, T, C). microgpt does the same with no B: view(T, H, D).transpose(0, 1).

B, T, C, H = 2, 5, 16, 4
D = C // H
x = torch.randn(B, T, C)
q = nn.Linear(C, C, bias=False)(x)
print(q.shape)                                    # torch.Size([2, 5, 16])
qh = q.view(B, T, H, D).transpose(1, 2)
print(qh.shape)                                   # torch.Size([2, 4, 5, 4])
scores = qh @ qh.transpose(-2, -1)
print(scores.shape)                               # torch.Size([2, 4, 5, 5])
y = (scores.softmax(-1) @ qh).transpose(1, 2).reshape(B, T, C)
print(y.shape)                                    # torch.Size([2, 5, 16])
RMSNorm vs LayerNorm?

LayerNorm computes (x - mean) / sqrt(var + eps) * weight + bias. RMSNorm computes x / sqrt(mean(x²) + eps) * weight: no mean subtraction, no bias, one reduction instead of two, and in practice it trains as well; LLaMA-family models use it. Your rms_norm is F.rms_norm with no weight. nn.RMSNorm (PyTorch 2.4+) adds a learnable per-channel weight unless you pass elementwise_affine=False.

x = torch.tensor([[3.0, 4.0]])
print(F.rms_norm(x, (2,), eps=1e-5))     # tensor([[0.8485, 1.1314]])
print(nn.LayerNorm(2)(x))                # tensor([[-1.0000,  1.0000]], grad_fn=<NativeLayerNormBackward0>)
print([n for n, _ in nn.RMSNorm(16).named_parameters()])     # ['weight']
print([n for n, _ in nn.LayerNorm(16).named_parameters()])   # ['weight', 'bias']
What does nn.Embedding compute?

Mathematically one_hot(ids) @ W; in practice it is row indexing, O(C) per token instead of O(V·C). Its gradient is nonzero only for rows that were looked up, and a row used twice gets the sum. microgpt's token_embedding_table[token_ids] is the same lookup on a raw Parameter.

torch.manual_seed(0)
emb = nn.Embedding(27, 16)
ids = torch.tensor([26, 0, 26])
print(torch.allclose(emb(ids), F.one_hot(ids, 27).float() @ emb.weight))   # True
emb(ids).sum().backward()
print(emb.weight.grad[26, :3], emb.weight.grad[0, :3])
# tensor([2., 2., 2.]) tensor([1., 1., 1.])
What is weight tying, and how do you do it?

The token embedding is (V, C) and the output head's weight is also (V, C), since nn.Linear stores [out, in]. Tying makes them one Parameter: it saves V·C parameters (a lot when V is 128k) and often helps small models. parameters() de-duplicates shared tensors, so the count and the optimizer see it once; state_dict still lists both names. microgpt doesn't tie; tying would remove 432 of its 4,192 parameters.

class Tiny(nn.Module):
    def __init__(self, tie):
        super().__init__()
        self.tok = nn.Embedding(27, 16)
        self.head = nn.Linear(16, 27, bias=False)
        if tie:
            self.head.weight = self.tok.weight

print(sum(p.numel() for p in Tiny(False).parameters()))   # 864
print(sum(p.numel() for p in Tiny(True).parameters()))    # 432
print(list(Tiny(True).state_dict().keys()))               # ['tok.weight', 'head.weight']
How many parameters does a transformer block have?

About 12·d² for width d with a 4x MLP: attention has q, k, v and output projections (4d²), the MLP has d·4d + 4d·d = 8d². Biases and norm weights add a little: nn.Linear(16, 16) has 272 parameters, 256 with bias=False. Then add embeddings (V·d, plus block_size·d for learned positions) and an untied head (V·d). microgpt: 12·16² = 3,072 in the block plus 27·16 + 16·16 + 27·16 = 1,120 gives 4,192. With d = 4096 and 32 layers, 12·32·4096² ≈ 6.44B, which is most of a "7B" model.

print(sum(p.numel() for p in nn.Linear(16, 16).parameters()))               # 272
print(sum(p.numel() for p in nn.Linear(16, 16, bias=False).parameters()))   # 256
C, V, T = 16, 27, 16
print(12 * C * C, V * C + T * C + V * C, 12 * C * C + V * C + T * C + V * C)   # 3072 1120 4192
Why are targets the inputs shifted by one, and what shape does cross_entropy want?

In a causal language model the logits at position t predict token t + 1, so inputs = ids[:-1] and targets = ids[1:], which is microgpt's make_training_pair. F.cross_entropy wants the class dimension second: (N, C) with targets (N,), or (N, C, d1) with targets (N, d1). For (B, T, V) logits, flatten to (B·T, V) or transpose to (B, V, T). Passing (B, T, V) directly raises an error, or, if T happens to equal V, silently computes nonsense.

ids = torch.tensor([26, 4, 12, 12, 0, 26])          # BOS e m m a BOS
print(ids[:-1].tolist(), ids[1:].tolist())          # [26, 4, 12, 12, 0] [4, 12, 12, 0, 26]
torch.manual_seed(0)
B, T, V = 2, 5, 27
logits, targets = torch.randn(B, T, V), torch.randint(0, V, (B, T))
print(F.cross_entropy(logits.view(-1, V), targets.view(-1)))   # tensor(3.9079)
print(F.cross_entropy(logits.transpose(1, 2), targets))       # tensor(3.9079)
F.cross_entropy(logits, targets)
# RuntimeError: Expected target size [2, 27], got [2, 5]
How do you batch sequences of different lengths?

Pad to the longest sequence in the batch. Right-pad the inputs with any valid token id and set the padded targets to ignore_index (-100 by default): cross_entropy skips them and averages over real tokens only. With a causal mask, right padding cannot affect real positions (they never look ahead), so training needs no extra attention mask. Left padding, common in batched generation so every prompt ends at the same column, does need a key-padding mask and shifted position ids. Across batches, sum the loss and divide by the real-token count instead of averaging batch means.

torch.manual_seed(0)
logits = torch.randn(2, 4, 27)
targets = torch.tensor([[4, 12, 0, 26],
                        [1, 26, -100, -100]])        # second row padded
loss = F.cross_entropy(logits.view(-1, 27), targets.view(-1))
keep = targets.view(-1) != -100
manual = F.cross_entropy(logits.view(-1, 27)[keep], targets.view(-1)[keep])
print(loss, manual, keep.sum().item())               # tensor(3.7283) tensor(3.7283) 6

Inference, performance & precision (41–50)

How much memory does the KV cache take?

2 (K and V) × n_layers × n_kv_heads × head_dim × seq_len × batch × bytes_per_element. For a Llama-2-7B shape (32 layers, 32 KV heads, head_dim 128, fp16) that is 0.5 MiB per token, so a 4,096-token sequence holds 2 GiB of cache. Grouped-query attention with 8 KV heads cuts it to 0.5 GiB. In serving, the KV cache, not the weights, is what limits batch size times context length. microgpt's whole cache is 2,048 bytes.

def kv_cache_bytes(n_layers, n_kv_heads, head_dim, seq_len, batch, bytes_per_elem):
    return 2 * n_layers * n_kv_heads * head_dim * seq_len * batch * bytes_per_elem

print(kv_cache_bytes(32, 32, 128, 1, 1, 2) / 2**20)       # 0.5     (MiB per token)
print(kv_cache_bytes(32, 32, 128, 4096, 1, 2) / 2**30)    # 2.0     (GiB)
print(kv_cache_bytes(32, 8, 128, 4096, 1, 2) / 2**30)     # 0.5     (GiB, 8 KV heads)
print(kv_cache_bytes(1, 4, 4, 16, 1, 4))                  # 2048    (bytes, microgpt fp32)
Explain temperature, top-k and top-p.

Temperature divides the logits before softmax: below 1 sharpens toward the argmax, above 1 flattens, and the limit at 0 is greedy decoding. Top-k keeps the k highest-scoring tokens; top-p (nucleus) keeps the smallest set of top tokens whose cumulative probability reaches p. Everything else gets -inf and the survivors are renormalised. The usual order is temperature, then top-k, then top-p, then sample. microgpt's generate_name uses temperature only.

def sample_next(logits, temperature=1.0, top_k=None, top_p=None, generator=None):
    logits = logits / temperature
    if top_k is not None:
        kth = torch.topk(logits, top_k).values[..., -1, None]
        logits = logits.masked_fill(logits < kth, float("-inf"))
    if top_p is not None:
        sorted_logits, idx = torch.sort(logits, descending=True)
        probs = sorted_logits.softmax(-1)
        drop = probs.cumsum(-1) - probs >= top_p          # mass before this token already enough
        sorted_logits = sorted_logits.masked_fill(drop, float("-inf"))
        logits = torch.full_like(logits, float("-inf")).scatter(-1, idx, sorted_logits)
    probs = logits.softmax(-1)
    return torch.multinomial(probs, 1, generator=generator), probs

logits = torch.tensor([2.0, 1.0, 0.5, 0.0, -1.0])
for t in (0.5, 1.0, 2.0):
    print(t, (logits / t).softmax(-1).numpy().round(3))
# 0.5 [0.829 0.112 0.041 0.015 0.002]
# 1.0 [0.563 0.207 0.126 0.076 0.028]
# 2.0 [0.375 0.227 0.177 0.138 0.084]
print(sample_next(logits, top_k=2)[1].numpy().round(3))     # [0.731 0.269 0.    0.    0.   ]
print(sample_next(logits, top_p=0.8)[1].numpy().round(3))   # [0.629 0.231 0.14  0.    0.   ]
Why is decode memory-bound and prefill compute-bound?

Arithmetic intensity is FLOPs per byte moved from memory. Decoding one token at batch 1 multiplies each weight matrix by a single vector: each 2-byte fp16 weight is read once and used for 2 FLOPs (a multiply and an add), about 1 FLOP/byte. An H100 SXM's spec sheet gives about 989 TFLOPS dense BF16 and 3.35 TB/s of HBM bandwidth, a ridge point near 295 FLOP/byte, so decode sits two orders of magnitude below it and its time is bytes divided by bandwidth: a 7B fp16 model (14 GB) is capped near 3.35e12 / 14e9 ≈ 239 tokens/s at batch 1, however fast the tensor cores are. Prefill pushes T prompt tokens through each weight at once (matrix times matrix), so intensity grows with T and becomes compute-bound. Batching decode requests is the main lever: B sequences share one read of the weights, until KV-cache reads dominate.

How do you time GPU code correctly?

CUDA kernel launches are asynchronous: the Python call returns when the kernel is queued, not when it has finished. Wrapping a GPU op in time.perf_counter() measures launch overhead unless you call torch.cuda.synchronize() before reading the clock each time. Warm up first (the first calls pay for context creation, cuBLAS heuristics, autotuning and compilation), repeat, and report the median. CUDA events or torch.utils.benchmark.Timer (which synchronises and warms up for you) do this properly. The event version below needs a CUDA GPU; the Timer version also runs on CPU.

x = torch.randn(4096, 4096, device="cuda")
for _ in range(3):                         # warm-up
    x @ x
torch.cuda.synchronize()
start = torch.cuda.Event(enable_timing=True)
end = torch.cuda.Event(enable_timing=True)
start.record()
for _ in range(10):
    x @ x
end.record()
torch.cuda.synchronize()                   # wait until 'end' has really happened
print(start.elapsed_time(end) / 10, "ms per matmul")

import torch.utils.benchmark as benchmark
print(benchmark.Timer(stmt="x @ x", globals={"x": x}).blocked_autorange(min_run_time=1.0))
What is a hidden sync, and which calls cause one?

A sync is any point where the CPU has to wait for the GPU to finish queued work, which kills the overlap that keeps the GPU busy. The hidden ones: .item(), .tolist(), .cpu() and .numpy(), print(tensor), if loss > 0: on a CUDA tensor, torch.nonzero and boolean-mask indexing x[mask] (the output size depends on the data), and blocking device-to-host copies. Find them with torch.cuda.set_sync_debug_mode("warn") or as cudaStreamSynchronize and device-to-host memcpy entries in the profiler. The usual fix is to keep running metrics on the GPU and read them every N steps. This needs a CUDA GPU to observe.

torch.cuda.set_sync_debug_mode("warn")         # warn on every synchronising call
running = torch.zeros((), device="cuda")
for step, (x, y) in enumerate(loader):
    loss = train_step(x, y)
    running += loss.detach()                   # stays on the GPU: no sync
    if step % 100 == 99:
        print(step, (running / 100).item())    # one sync per 100 steps
        running.zero_()
What is a torch.compile graph break, and how do you find one?

torch.compile uses TorchDynamo to trace your Python bytecode into FX graphs, then a backend (Inductor by default) fuses ops and generates kernels. When Dynamo meets something it can't put in a graph (a print, a branch on tensor data such as if x.sum() > 0, .item() fed to Python, an unsupported library call) it ends the graph, runs that piece as normal Python and starts a new graph. Each break loses fusion, adds overhead, and can trigger recompiles. Find them with torch._dynamo.explain, with TORCH_LOGS="graph_breaks", or make them errors with fullgraph=True.

import torch._dynamo as dynamo

def f(x):
    y = x.sin()
    print("hi")            # Python side effect: can't go in a graph
    return y.cos()

ex = dynamo.explain(f)(torch.randn(4))         # runs f once, so "hi" is printed
print(ex.graph_count, ex.graph_break_count)    # 2 1
print(ex.break_reasons[0].reason.splitlines()[0])
# Failed to trace builtin operator
fp16 vs bf16?

Both are 16 bits. fp16 has 5 exponent and 10 mantissa bits: max 65504, smallest normal about 6.1e-5, so activations overflow and gradients underflow unless you scale the loss. bf16 has 8 exponent and 7 mantissa bits: the same range as fp32 (max about 3.39e38) but only 2–3 significant decimal digits (eps 0.0078). Range matters more than precision for training, so bf16 is the default on GPUs that support it (Ampere and newer); fp16 is more precise for values inside its range.

for dt in (torch.float16, torch.bfloat16):
    fi = torch.finfo(dt)
    print(dt, fi.max, fi.eps, fi.tiny)
# torch.float16 65504.0 0.0009765625 6.103515625e-05
# torch.bfloat16 3.3895313892515355e+38 0.0078125 1.1754943508222875e-38
print(torch.tensor(70000.0).to(torch.float16))       # tensor(inf, dtype=torch.float16)
print(torch.tensor(70000.0).to(torch.bfloat16))      # tensor(70144., dtype=torch.bfloat16)
print(torch.tensor(1 + 1 / 256).to(torch.bfloat16))  # tensor(1., dtype=torch.bfloat16)
print(torch.tensor(1 + 1 / 256).to(torch.float16))   # tensor(1.0039, dtype=torch.float16)
What does GradScaler do, and when do you need it?

In fp16, small gradients flush to zero: 1e-8 becomes exactly 0. GradScaler multiplies the loss by a scale S (default 65536) before backward so gradients are S times larger and representable, then divides them back before the optimizer step. If any gradient is inf or nan, it skips that step and halves S; after 2,000 clean steps it doubles S. Call scaler.unscale_(optimizer) before clipping so the clip sees true norms. You need it for fp16 training only, not bf16 or fp32. The loop below needs a CUDA GPU.

print(torch.tensor(1e-8).to(torch.float16))            # tensor(0., dtype=torch.float16)
print(torch.tensor(1e-8 * 65536).to(torch.float16))    # tensor(0.0007, dtype=torch.float16)

scaler = torch.amp.GradScaler("cuda")
for x, y in loader:
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        loss = F.cross_entropy(model(x).view(-1, V), y.view(-1))
    scaler.scale(loss).backward()          # backward on loss * S
    scaler.unscale_(optimizer)             # true-scale grads, so clipping is correct
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)                 # skipped if any grad is inf/nan
    scaler.update()                        # adjust S
How much memory per parameter does training take?

Plain fp32 training with Adam: weights 4 bytes + gradients 4 + Adam's m 4 + v 4 = 16 bytes per parameter. Mixed precision with 16-bit working weights and an fp32 master copy is also 16: 2 + 2 + 4 + 4 + 4 (the ZeRO paper's "2 + 2 + 12"). A 7B model therefore needs about 112 GB for weights and optimizer state before any activations, against 14 GB to serve it in bf16. Activations grow with batch × sequence × layers × width; gradient checkpointing trades them for recompute. microgpt: 4,192 × 16 = 67,072 bytes.

What does torch.autocast actually change?

Inside torch.autocast(device_type, dtype), each op picks its own dtype: matmuls, linears and convolutions run in the low-precision dtype (that's where tensor cores pay off), while precision-sensitive ops such as losses and large reductions run in fp32. The weights stay fp32; autocast casts copies on the fly, so it is not model.half(). Backward automatically uses the same dtypes as forward, so don't put backward() inside the context. The per-op lists differ by device: on CUDA, softmax and log_softmax run in fp32, while on CPU (below) they stay bf16.

torch.manual_seed(0)
lin = nn.Linear(16, 27)
x = torch.randn(4, 16)
with torch.autocast(device_type="cpu", dtype=torch.bfloat16):
    out = lin(x)
    sm = F.softmax(out, dim=-1)
    ce = F.cross_entropy(out, torch.zeros(4, dtype=torch.long))
print(lin.weight.dtype, out.dtype, sm.dtype, ce.dtype)
# torch.float32 torch.bfloat16 torch.bfloat16 torch.float32
