Chapter 07 Losses & Optimizers

A model produces numbers; a loss turns them into one score for "how wrong", and an optimizer uses the gradients of that score to change the weights. You wrote both by hand in microgpt: negative_log_likelihood and apply_adam. This chapter shows the PyTorch versions, proves they compute the same numbers, and adds the pieces every real training run uses: AdamW, learning-rate schedules, and gradient clipping.

What a loss function is

A loss function takes the model's output and the right answer and returns a single number that is small when the model is right. Training is the loop "compute the loss, compute its gradient with respect to every weight, nudge every weight downhill".

For next-token prediction the right answer at each position is one token id out of the vocabulary. The model outputs one logit per vocabulary entry: a raw, unnormalised score, any real number. Softmax turns logits into probabilities, and the loss at that position is -log(p[target]), the negative log-likelihood. If the model gives the right token probability 1, the loss is 0; probability 0.5 costs 0.69; probability 0.01 costs 4.6. microgpt does exactly this in negative_log_likelihood(), and calculate_document_loss() averages it over the positions of one name.

In classification language, each vocabulary entry is a class, the number of classes is C (27 for microgpt), and this loss is called cross-entropy.

F.cross_entropy is your negative_log_likelihood

Here are three positions and a toy vocabulary of 4 tokens. We compute the loss three ways: step by step with tensors, with F.cross_entropy, and with microgpt's own functions on plain Python floats.

pythonce_by_hand.py
import math
import torch
import torch.nn.functional as F

# 3 positions, a vocabulary of 4 tokens: one row of logits per position
logits = torch.tensor([[2.0, 1.0, 0.1, -1.0],
                       [0.5, 2.5, 0.0,  0.3],
                       [1.0, 1.0, 1.0,  1.0]])
targets = torch.tensor([0, 1, 3])        # correct next token at each position

probs = torch.softmax(logits, dim=-1)    # each row sums to 1
picked = probs[torch.arange(3), targets] # p[target] for each row
per_token = -torch.log(picked)           # negative log-likelihood per position
print(picked)                            # tensor([0.6381, 0.7529, 0.2500])
print(per_token)                         # tensor([0.4493, 0.2838, 1.3863])
print(per_token.mean())                  # tensor(0.7065)
print(F.cross_entropy(logits, targets))  # tensor(0.7065)

# microgpt's softmax + negative_log_likelihood + average, on plain floats
def softmax(row):
    m = max(row)
    exps = [math.exp(x - m) for x in row]
    total = sum(exps)
    return [e / total for e in exps]

def negative_log_likelihood(probabilities, target_id):
    return -math.log(probabilities[target_id])

token_losses = [negative_log_likelihood(softmax(row), t)
                for row, t in zip(logits.tolist(), targets.tolist())]
print([round(x, 4) for x in token_losses])   # [0.4493, 0.2838, 1.3863]
print(sum(token_losses) / len(token_losses)) # 0.7064832182393465

Same three per-token losses, same average. probs[torch.arange(3), targets] is advanced indexing from Chapter 2: row i, column targets[i]. The third row is all equal logits, so each token gets probability 0.25 and the loss is ln 4 = 1.3863.

So F.cross_entropy(logits, targets) is calculate_document_loss for one name: softmax, pick the target probability, negative log, average. The PyTorch version takes raw logits, not probabilities, and does the softmax inside. The next section shows why.

Why it takes logits: log_softmax

Computing log(softmax(x)) in two steps breaks when the model is very confident and wrong. Probabilities live in float32, and float32 cannot store anything smaller than about 1.4e-45. A probability of exp(-200) becomes exactly 0, and log(0) is minus infinity.

pythonlog_softmax.py
import torch
import torch.nn.functional as F

logits = torch.tensor([[0.0, 200.0]])   # the model is very sure of token 1
target = torch.tensor([0])              # ...but the answer is token 0

p = torch.softmax(logits, dim=-1)
print(p)                                # tensor([[0., 1.]])  exp(-200) underflowed to 0
print(-torch.log(p[0, 0]))              # tensor(inf)         the naive loss
print(-F.log_softmax(logits, dim=-1)[0, 0])  # tensor(200.)
print(F.cross_entropy(logits, target))       # tensor(200.)

# the gradient of the naive version is poisoned too
x = logits.clone().requires_grad_()
naive = -torch.log(torch.softmax(x, dim=-1)[0, 0])
naive.backward()
print(x.grad)                           # tensor([[nan, nan]])

x = logits.clone().requires_grad_()
F.cross_entropy(x, target).backward()
print(x.grad)                           # tensor([[-1.,  1.]])

# and without subtracting the max first, exp itself overflows
big = torch.tensor([100.0, 0.0])
e = torch.exp(big)
print(e)                                # tensor([inf, 1.])
print(e / e.sum())                      # tensor([nan, 0.])

The right answer is 200 (the logit gap), and log_softmax gets it because it never forms the tiny probability. It uses the identity

log_softmax(x)_i = x_i - m - log( sum_j exp(x_j - m) )      where m = max(x)
                 = x_i - logsumexp(x)

After subtracting m the largest exponent is exp(0) = 1, so the sum is between 1 and C and its log is always finite. That max-subtraction is the same trick as the maximum_logit line in microgpt's softmax(); the last two prints above show what happens without it.

import torch

x = torch.tensor([0.0, 200.0])
m = x.max()
print(x - m - torch.log(torch.exp(x - m).sum()))   # tensor([-200.,    0.])
print(x - torch.logsumexp(x, dim=0))               # tensor([-200.,    0.])
print(torch.log_softmax(x, dim=0))                 # tensor([-200.,    0.])
Under the hood: two kernels, one formula

F.cross_entropy(x, t) computes F.nll_loss(F.log_softmax(x, dim=1), t). nll_loss just picks -logp[i, t[i]] and reduces. The fused gradient is also simple: softmax(x) - onehot(t), divided by N for the mean. That is the [-1., 1.] above: probabilities [0, 1] minus one-hot [1, 0].

Never softmax before cross_entropy

If your model already applies softmax and you pass probabilities in, PyTorch softmaxes them again. It runs, returns a plausible-looking number, and quietly stops learning: with 4 classes even a perfect probability row [1, 0, 0, 0] scores 0.7437, not 0. On the example above the loss becomes 1.1147 instead of 0.7065. Models return logits; the loss owns the softmax.

Shapes: (N, C) logits, (N,) targets

The basic contract is: input has shape (N, C), one row of C logits per example, and target has shape (N,), one integer class id per example, dtype torch.long (int64). microgpt's forward returns (T, 27) for one name, which already fits.

A batched model returns (B, T, C): B names, T positions each, C logits per position. Every position is an independent prediction, so flatten batch and time into one axis of B*T rows:

import torch
import torch.nn.functional as F

torch.manual_seed(0)
B, T, C = 2, 3, 27
logits = torch.randn(B, T, C)           # what a batched model returns
targets = torch.randint(0, C, (B, T))   # one target id per position

flat = F.cross_entropy(logits.view(B * T, C), targets.view(B * T))
print(logits.view(B * T, C).shape, targets.view(B * T).shape)
# torch.Size([6, 27]) torch.Size([6])
print(flat)                                            # tensor(4.5729)
# same thing with the class dimension moved to position 1: (B, C, T)
print(F.cross_entropy(logits.transpose(1, 2), targets))   # tensor(4.5729)

try:
    F.cross_entropy(logits, targets)    # (B, T, C): T=3 is read as the class dim
except Exception as e:
    print(type(e).__name__ + ":", e)
# RuntimeError: Expected target size [2, 27], got [2, 3]

For inputs with more than two dimensions, cross_entropy expects the class dimension second: (N, C, d1, d2, ...), a convention inherited from images. Passing (B, T, C) makes it think there are 3 classes and 27 positions. Here the shapes happened to disagree and you got an error. If T equalled C it would silently compute the wrong thing. Flattening to (B*T, C) is the habit to keep. Use .reshape instead of .view if the logits might not be contiguous (Chapter 2).

Targets must be int64

Class-index targets must be torch.long. An int32 target fails with RuntimeError: expected scalar type Long but found Int, and a float target of shape (N,) fails with ... but found Float. A float target of the same shape as the logits is legal, and means something else: a full probability distribution per row (soft labels).

reduction, ignore_index, label_smoothing

Three keyword arguments cover nearly everything you will need for language models.

  • reduction: how the per-position losses become one number. "mean" (default) averages, "sum" adds, "none" returns the per-position vector, which is microgpt's token_losses list.
  • ignore_index (default -100): any target equal to it contributes nothing, neither to the sum nor to the count the mean divides by. This is how you mask padding, the filler positions you add so names of different lengths fit in one rectangular tensor (Chapter 8 builds such batches).
  • label_smoothing (default 0.0): mixes the one-hot target with a uniform distribution, so the model is never pushed toward infinite confidence. With ε = 0.1 the target becomes 90% "the right token" and 10% spread over all classes. Common in translation models, rare in LLM pretraining.
import torch
import torch.nn.functional as F

logits = torch.tensor([[2.0, 1.0, 0.1, -1.0],
                       [0.5, 2.5, 0.0,  0.3],
                       [1.0, 1.0, 1.0,  1.0]])
targets = torch.tensor([0, 1, 3])

print(F.cross_entropy(logits, targets, reduction="none"))  # tensor([0.4493, 0.2838, 1.3863])
print(F.cross_entropy(logits, targets, reduction="sum"))   # tensor(2.1194)
print(F.cross_entropy(logits, targets, reduction="mean"))  # tensor(0.7065)

# position 2 is padding: mark its target with -100 (the default ignore_index)
padded_targets = torch.tensor([0, 1, -100])
print(F.cross_entropy(logits, padded_targets))             # tensor(0.3666)  mean over 2
print(F.cross_entropy(logits[:2], targets[:2]))            # tensor(0.3666)  same number
print(F.cross_entropy(logits, padded_targets, reduction="none"))
# tensor([0.4493, 0.2838, 0.0000])

print(F.cross_entropy(logits, targets, label_smoothing=0.1))   # tensor(0.8115)

Note the mean with padding is (0.4493 + 0.2838) / 2, not / 3. PyTorch divides by the number of non-ignored targets. microgpt's evaluate_model uses reduction="sum" and divides by its own token count for the same reason: so every token counts once, whatever the name lengths.

The first number to expect: ln(C)

A model that knows nothing should spread probability evenly: 1/C for every class. Its loss is -log(1/C) = ln(C). For microgpt's 27 tokens that is 3.2958. A freshly initialised model with small weights emits small, nearly equal logits, so its first loss should land right there.

import math
import torch
import torch.nn.functional as F

V = 27
print(math.log(V))                             # 3.295836866004329

uniform = torch.zeros(5, V)                    # equal logits = uniform guess
targets = torch.tensor([0, 4, 13, 26, 7])
print(F.cross_entropy(uniform, targets))       # tensor(3.2958)

torch.manual_seed(0)
small = 0.1 * torch.randn(1000, V)             # what a freshly initialised model emits
print(F.cross_entropy(small, torch.randint(0, V, (1000,))))   # tensor(3.2990)

If your step-0 loss is much higher than ln(C), the initial logits are too large: the model is confidently wrong before it has learned anything, usually because of a too-wide weight initialisation. That costs you the first few hundred steps just undoing it. Chapter 8 turns this into a standard sanity check.

What an optimizer is

After loss.backward(), every parameter p has a p.grad tensor of the same shape: the slope of the loss with respect to each number in p. An optimizer is an object that holds references to the parameters (not copies) and, when you call optimizer.step(), updates each one in place using its .grad. The learning rate (lr) is the step size.

The simplest rule is SGD (stochastic gradient descent): p = p - lr * p.grad. That is exactly microgpt's demonstration line parameter.data -= learning_rate * parameter.grad.

pythonsgd.py
import torch

w = torch.nn.Parameter(torch.tensor([1.0, -2.0]))
opt = torch.optim.SGD([w], lr=0.1)

loss = (w ** 2).sum()        # d(loss)/dw = 2w = [2, -4]
loss.backward()
print(w.grad)                # tensor([ 2., -4.])

opt.step()                   # w <- w - lr * w.grad
print(w.data)                # tensor([ 0.8000, -1.6000])

opt.zero_grad()
print(w.grad)                # None

# the same update by hand
v = torch.tensor([1.0, -2.0], requires_grad=True)
(v ** 2).sum().backward()
with torch.no_grad():        # the update itself must not be recorded by autograd
    v -= 0.1 * v.grad
print(v.data)                # tensor([ 0.8000, -1.6000])

Three facts about every torch.optim optimizer:

  • The first argument is an iterable of parameters, usually model.parameters(). They are stored in optimizer.param_groups, a list of dicts, each with its own "params", "lr" and other settings.
  • step() reads .grad and writes the parameters in place, under no_grad. It does not compute gradients; backward() does.
  • step() does not clear .grad. Gradients accumulate across backward() calls (Chapter 4), so you clear them yourself with zero_grad() every iteration.

SGD has options: momentum=0.9 keeps a running "velocity" buffer per parameter and steps along it, which smooths noisy gradients. SGD with momentum is still common for image models. For transformers, Adam-family optimizers are the default.

Adam: your apply_adam, as a class

Adam keeps two running averages per parameter. The first moment m is an exponential moving average of the gradient (its direction, smoothed). The second moment v is a moving average of the squared gradient (its typical size). The update divides one by the square root of the other, so every parameter moves about lr per step whether its gradients are tiny or huge. beta1 and beta2 are how much of the old average to keep each step; eps keeps the division safe when v is near zero.

Because m and v start at 0, early averages are biased toward 0. Dividing by 1 - beta**t (the bias correction) undoes that: at step 1, m = 0.15·g and m / (1 - 0.85) = g. So the first step moves every parameter by almost exactly lr, in the direction opposite its gradient's sign.

Below, microgpt's apply_adam runs on plain Python floats next to torch.optim.Adam with microgpt's settings, on the same small function, for 5 steps.

pythonadam_match.py
import torch

beta1, beta2, eps, lr = 0.85, 0.99, 1e-8, 0.01
c = [3.0, -1.0, 0.5]

def gradient(w):                 # d/dw of sum((w - c)^2) + w0*w1*w2
    return [2 * (w[0] - c[0]) + w[1] * w[2],
            2 * (w[1] - c[1]) + w[0] * w[2],
            2 * (w[2] - c[2]) + w[0] * w[1]]

# microgpt's apply_adam, on plain Python floats
w_micro = [0.1, 0.2, 0.3]
first_moments = [0.0] * 3
second_moments = [0.0] * 3

def apply_adam(params, grads, step_number, learning_rate):
    for i, g in enumerate(grads):
        first_moments[i] = beta1 * first_moments[i] + (1 - beta1) * g
        second_moments[i] = beta2 * second_moments[i] + (1 - beta2) * g ** 2
        m_hat = first_moments[i] / (1 - beta1 ** step_number)
        v_hat = second_moments[i] / (1 - beta2 ** step_number)
        params[i] -= learning_rate * m_hat / (v_hat ** 0.5 + eps)

# PyTorch
w = torch.nn.Parameter(torch.tensor([0.1, 0.2, 0.3]))
opt = torch.optim.Adam([w], lr=lr, betas=(beta1, beta2), eps=eps)

for step in range(1, 6):
    opt.zero_grad()
    loss = ((w - torch.tensor(c)) ** 2).sum() + w.prod()
    loss.backward()
    opt.step()

    apply_adam(w_micro, gradient(w_micro), step, lr)
    diff = max(abs(a - b) for a, b in zip(w.tolist(), w_micro))
    print(step, [round(x, 6) for x in w.tolist()], f"max diff {diff:.1e}")

state = opt.state[w]
print(sorted(state.keys()))
print(state["step"])
print(state["exp_avg"], [round(m, 4) for m in first_moments])
print(state["exp_avg_sq"], [round(v, 4) for v in second_moments])

Step 1 moved each weight by exactly 0.01, as the bias-correction argument predicted. The two implementations agree to about 1e-8: the only difference is that PyTorch works in float32 and microgpt's Python floats are float64.

optimizer.state is your moment lists

opt.state is a dict keyed by parameter tensor. For Adam each entry holds:

microgpt_scalar.pytorch.optim.Adamshape
adam_first_moments[i]state[p]["exp_avg"]same as p
adam_second_moments[i]state[p]["exp_avg_sq"]same as p

Two consequences. First, Adam's state is twice the size of the model: two extra float32 tensors per parameter. Chapter 9 turns that into the "16 bytes per parameter" rule. Second, the state is part of the training run. A checkpoint that saves only the weights resumes with m = v = 0, which is a different optimizer. Chapter 8 saves optimizer.state_dict() too, as microgpt already does.

foreach and fused

microgpt passes foreach=False. By default PyTorch picks a "foreach" implementation that updates all parameters with a few multi-tensor kernels instead of a Python loop over parameters, which matters on a GPU where each kernel launch has a fixed cost. fused=True (CUDA and some other devices) goes further and does the whole Adam update in one kernel. The math is the same in all three; microgpt's tiny CPU model happens to run fastest with the simple loop.

AdamW and decoupled weight decay

Weight decay pulls every weight a little toward zero each step, which discourages the model from relying on a few huge weights. There are two ways to do it, and with Adam they are not the same.

  • L2 penalty (torch.optim.Adam(weight_decay=wd)): add wd * p to the gradient. Adam then divides the whole gradient, decay included, by sqrt(v). Parameters with large gradients get almost no decay.
  • Decoupled decay (torch.optim.AdamW): first shrink p = p * (1 - lr * wd), then do the normal Adam update with the raw gradient. Every weight decays by the same fraction.

One step with numbers small enough to check by hand: p = 1.0, grad = 0.5, lr = 0.1, wd = 0.1.

import torch

p_adamw = torch.nn.Parameter(torch.tensor([1.0]))
p_l2 = torch.nn.Parameter(torch.tensor([1.0]))
opt_adamw = torch.optim.AdamW([p_adamw], lr=0.1, weight_decay=0.1)
opt_l2 = torch.optim.Adam([p_l2], lr=0.1, weight_decay=0.1)   # L2 inside Adam

p_adamw.grad = torch.tensor([0.5])
p_l2.grad = torch.tensor([0.5])
opt_adamw.step()
opt_l2.step()
print(f"AdamW:   {p_adamw.item():.6f}")    # AdamW:   0.890000
print(f"Adam+L2: {p_l2.item():.6f}")       # Adam+L2: 0.900000

AdamW: decay 1.0 × (1 - 0.01) = 0.99, then the first Adam step moves by lr = 0.1: 0.89. Adam+L2: the gradient becomes 0.5 + 0.1 × 1.0 = 0.6, but the first Adam step normalises it to "move by lr" anyway: 0.90. The decay vanished into the normalisation. This is why every modern LLM recipe uses AdamW (in torch 2.8 you can also write Adam(..., decoupled_weight_decay=True), which is the same thing). Note that AdamW's default weight_decay is 0.01, not 0.

Param groups: no decay on norms and biases

The usual recipe decays only weight matrices and embedding tables. Biases and normalisation weights (gains) are 1-D vectors with a few numbers each; pulling a norm's gain toward 0 just fights the normalisation. Optimizers accept a list of dicts called param groups, each with its own settings:

import torch
from torch import nn

torch.manual_seed(0)
model = nn.Sequential(
    nn.Linear(16, 64), nn.ReLU(), nn.Linear(64, 16), nn.RMSNorm(16),
)

decay, no_decay = [], []
for name, p in model.named_parameters():
    if p.dim() >= 2:          # weight matrices (and embedding tables)
        decay.append(p)
    else:                     # biases and norm weights: 1-D
        no_decay.append(p)
    print(f"{name:9s} {str(tuple(p.shape)):9s} {'decay' if p.dim() >= 2 else 'no decay'}")

optimizer = torch.optim.AdamW(
    [
        {"params": decay, "weight_decay": 0.1},
        {"params": no_decay, "weight_decay": 0.0},
    ],
    lr=3e-4,
    betas=(0.9, 0.95),
)
for group in optimizer.param_groups:
    print(len(group["params"]), group["weight_decay"], group["lr"])
0.weight  (64, 16)  decay
0.bias    (64,)     no decay
2.weight  (16, 64)  decay
2.bias    (16,)     no decay
3.weight  (16,)     no decay

3 0.0 0.0003

Keys you leave out of a group (lr, betas) come from the keyword arguments. microgpt has no biases and no norm weights (its F.rms_norm call has no gain), so all 9 of its tensors are 2-D and would land in the decay group.

zero_grad(set_to_none=True)

optimizer.zero_grad() clears the gradients of every parameter it manages. Since PyTorch 2.0 the default is set_to_none=True: instead of filling .grad with zeros it sets it to None, which skips a memory write and frees the memory until the next backward() allocates it again. microgpt writes it out explicitly: optimizer.zero_grad(set_to_none=True).

The difference is visible with Adam. A zero gradient is still a gradient: Adam updates its moments with it and, because m remembers the past, still moves the weight. A None gradient means "skip this parameter".

import torch

w = torch.nn.Parameter(torch.tensor([1.0]))
opt = torch.optim.Adam([w], lr=0.1)
w.grad = torch.tensor([0.5])
opt.step()
print(f"after step 1: {w.item():.4f}")          # after step 1: 0.9000

opt.zero_grad(set_to_none=False)       # grad becomes a tensor of zeros
print(w.grad)                          # tensor([0.])
opt.step()                             # zero gradient, but momentum still moves w
print(f"after zero-grad step: {w.item():.4f}")  # after zero-grad step: 0.8330

opt.zero_grad()                        # default set_to_none=True
print(w.grad)                          # None
opt.step()                             # params with grad None are skipped
print(f"after None-grad step: {w.item():.4f}")  # after None-grad step: 0.8330

The difference shows up only for a parameter that gets no gradient at all in some step: a frozen layer, or a branch the forward pass skipped. (An embedding row the batch did not use is not that case: the table as a whole gets a gradient with zeros in that row, so Adam's momentum still moves the row.) The flip side of None: any code of yours that reads p.grad must handle it.

Learning-rate schedules

A learning-rate schedule changes lr over the run. microgpt uses linear decay: lr = 0.01 * (1 - progress), written straight into param_groups each step. PyTorch packages this as a scheduler object that wraps the optimizer. LambdaLR is the general one: you give it a function from step number to a multiplier, and it sets lr = base_lr * f(step).

pythonlambdalr.py
import torch

number_of_training_steps = 5
w = torch.nn.Parameter(torch.zeros(1))
optimizer = torch.optim.Adam([w], lr=0.01, betas=(0.85, 0.99), eps=1e-8)
scheduler = torch.optim.lr_scheduler.LambdaLR(
    optimizer,
    lr_lambda=lambda step: 1.0 - step / number_of_training_steps,
)

for training_iteration in range(number_of_training_steps):
    microgpt_lr = 0.01 * (1.0 - training_iteration / number_of_training_steps)
    used_lr = optimizer.param_groups[0]["lr"]

    w.grad = torch.ones(1)       # stands in for loss.backward()
    optimizer.step()             # uses the current lr
    scheduler.step()             # then moves the lr to the next step's value

    print(training_iteration, f"used={used_lr:.8f}", f"microgpt={microgpt_lr:.8f}")
print(scheduler.get_last_lr())

Creating the scheduler immediately applies f(0). Each scheduler.step() advances an internal counter and applies f(counter), so iteration i trains with f(i), exactly microgpt's schedule. get_last_lr() returns the lr that is set now, which after the last step is the "next" value 0.0.

Warmup + cosine

LLM pretraining almost always uses warmup then cosine decay. Warmup ramps the lr up from near 0 over the first few hundred steps. Early on Adam's v estimate is based on very few gradients and the weights are random, so full-size steps can blow the run up. Cosine decay then glides from the peak down to a floor along half a cosine wave: it stays near the peak for a while, then falls, then flattens out.

pythonwarmup_cosine.py
import math
import torch

warmup_steps, total_steps, min_ratio = 100, 1000, 0.1

def warmup_cosine(step):
    if step < warmup_steps:                       # linear ramp 1/100 .. 100/100
        return (step + 1) / warmup_steps
    progress = (step - warmup_steps) / (total_steps - warmup_steps)   # 0 -> 1
    cosine = 0.5 * (1.0 + math.cos(math.pi * progress))              # 1 -> 0
    return min_ratio + (1.0 - min_ratio) * cosine

w = torch.nn.Parameter(torch.zeros(1))
optimizer = torch.optim.AdamW([w], lr=3e-3)
scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, warmup_cosine)

for step in range(total_steps):
    if step in (0, 49, 99, 100, 325, 550, 775, 999):
        print(f"step {step:4d}  lr={optimizer.param_groups[0]['lr']:.6f}")
    w.grad = torch.ones(1)
    optimizer.step()
    scheduler.step()

The (step + 1) avoids a wasted first step at lr 0. Halfway through the decay (step 550) the lr is exactly halfway between peak and floor. PyTorch also ships ready-made pieces (LinearLR, CosineAnnealingLR, chained with SequentialLR), but one LambdaLR with a function you can read is easier to check.

Call order: optimizer.step(), then scheduler.step()

Get it backwards and PyTorch warns you, and your run skips the first value of the schedule:

import warnings
import torch

w = torch.nn.Parameter(torch.zeros(1))
optimizer = torch.optim.SGD([w], lr=0.1)
scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, lambda s: 1.0 - s / 10)

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    scheduler.step()             # wrong order: scheduler before optimizer
    w.grad = torch.ones(1)
    optimizer.step()
print(caught[0].message)
Detected call of `lr_scheduler.step()` before `optimizer.step()`. In PyTorch 1.1.0 and later, you should call them in the opposite order: `optimizer.step()` before `lr_scheduler.step()`.  Failure to do this will result in PyTorch skipping the first value of the learning rate schedule. See more details at https://pytorch.org/docs/stable/optim.html#how-to-adjust-learning-rate

Gradient clipping

Sometimes one batch produces a huge gradient (an unusual example, a loss spike) and one step throws the weights somewhere bad. Gradient clipping caps the size of the update direction. The standard version measures the global norm: square every gradient number in every parameter, add them all up, take the square root. It is the length of the whole gradient seen as one long vector. If that length exceeds max_norm, every gradient is multiplied by max_norm / norm; the direction is unchanged, only the length shrinks.

microgpt_scalar.py computes this same number as gradient_norm = sqrt(sum(parameter.grad**2 ...)). Worked example: one parameter with gradient [3, 4] and one with [12]. Global norm = sqrt(9 + 16 + 144) = sqrt(169) = 13.

import torch

a = torch.nn.Parameter(torch.zeros(2))
b = torch.nn.Parameter(torch.zeros(1))
a.grad = torch.tensor([3.0, 4.0])
b.grad = torch.tensor([12.0])

total = torch.nn.utils.clip_grad_norm_([a, b], max_norm=1.0)
print(total)                       # tensor(13.)          the norm BEFORE clipping
print(a.grad, b.grad)              # tensor([0.2308, 0.3077]) tensor([0.9231])
print(torch.cat([a.grad, b.grad]).norm())   # tensor(1.0000)

a.grad = torch.tensor([0.3, 0.4])  # norm 0.5 < max_norm: left alone
b.grad = torch.tensor([0.0])
print(torch.nn.utils.clip_grad_norm_([a, b], max_norm=1.0), a.grad)
# tensor(0.5000) tensor([0.3000, 0.4000])

The trailing underscore means it modifies the .grad tensors in place. It returns the norm measured before clipping, which is worth logging every step: a rising or spiky grad norm is often the first sign of trouble. Typical LLM setting: max_norm=1.0. Clip after backward() and before optimizer.step(). Clipping per parameter (clip_grad_value_ clamps each number) exists too, but changes the direction and is rarely used for transformers.

Hands-on · do this now

Put every piece of this chapter together on the smallest language model there is: a bigram table, where the logits for the next character depend only on the current one. The "model" is one 27 × 27 parameter; row i holds the next-token logits after token i.

pythonbigram.py
import math
import torch
import torch.nn.functional as F

names = ["emma", "olivia", "ava", "isabella", "sophia", "mia", "amelia", "harper"]
BOS = 26

def encode(name):
    return [BOS] + [ord(ch) - ord("a") for ch in name] + [BOS]

inputs, targets = [], []
for name in names:
    ids = encode(name)
    inputs += ids[:-1]
    targets += ids[1:]
x = torch.tensor(inputs)            # (N,) current token
y = torch.tensor(targets)           # (N,) next token
print(x.shape, f"baseline ln(27) = {math.log(27):.4f}")

torch.manual_seed(0)
table = torch.nn.Parameter(0.01 * torch.randn(27, 27))   # row = current, col = next-token logit
optimizer = torch.optim.Adam([table], lr=0.1, betas=(0.85, 0.99), eps=1e-8)
steps = 100
scheduler = torch.optim.lr_scheduler.LambdaLR(optimizer, lambda s: 1.0 - s / steps)

for step in range(steps):
    logits = table[x]                         # (N, 27)
    loss = F.cross_entropy(logits, y)
    optimizer.zero_grad()
    loss.backward()
    lr = optimizer.param_groups[0]["lr"]      # the lr this step uses
    grad_norm = torch.nn.utils.clip_grad_norm_([table], max_norm=1.0)
    optimizer.step()
    scheduler.step()
    if step % 20 == 0 or step == steps - 1:
        print(f"step {step:3d}  loss {loss.item():.4f}  grad_norm {grad_norm.item():.3f}"
              f"  lr {lr:.4f}")

EX 7.4 medium Hand-check one AdamW step

Parameter [2.0, -1.0], gradient [0.4, -0.1], lr=0.01, weight_decay=0.1, default betas (0.9, 0.999), eps=1e-8. Predict the parameter after one AdamW step, write the four stages as tensor code, and compare with torch.optim.AdamW.

Show solution

Decay: [2.0, -1.0] × 0.999 = [1.998, -0.999]. First Adam step after bias correction is lr × g / |g|, so -0.01 for the first, +0.01 for the second: [1.988, -0.989].

import torch

lr, wd, b1, b2, eps = 0.01, 0.1, 0.9, 0.999, 1e-8
p = torch.nn.Parameter(torch.tensor([2.0, -1.0]))
g = torch.tensor([0.4, -0.1])
opt = torch.optim.AdamW([p], lr=lr, betas=(b1, b2), eps=eps, weight_decay=wd)
p.grad = g.clone()
opt.step()

# by hand
q = torch.tensor([2.0, -1.0])
q = q * (1 - lr * wd)                           # 1. decoupled decay
m = (1 - b1) * g                                # 2. moments (start at 0)
v = (1 - b2) * g * g
m_hat = m / (1 - b1)                            # 3. bias correction, step 1
v_hat = v / (1 - b2)
q = q - lr * m_hat / (v_hat.sqrt() + eps)       # 4. Adam update
print(p.data, q, torch.allclose(p.data, q))
# tensor([ 1.9880, -0.9890]) tensor([ 1.9880, -0.9890]) True
EX 7.5 medium Warmup + cosine with real numbers

Build a schedule with peak lr 1e-3, floor 1e-4, 10 warmup steps, 50 total steps, using LambdaLR. Print the lr used at steps 0, 5, 9, 10, 30, 49. Before running, predict step 30 (the midpoint of the decay).

Show solution

Step 30 is progress (30 - 10) / 40 = 0.5, cosine factor 0.5, so lr = 1e-4 + 0.5 × 9e-4 = 5.5e-4. LambdaLR wants a multiplier of the base lr, so the function divides by the peak.

import math
import torch

peak, floor, warmup, total = 1e-3, 1e-4, 10, 50

def factor(step):
    if step < warmup:
        return (step + 1) / warmup
    progress = (step - warmup) / (total - warmup)
    lr = floor + (peak - floor) * 0.5 * (1 + math.cos(math.pi * progress))
    return lr / peak                         # LambdaLR wants a multiplier

w = torch.nn.Parameter(torch.zeros(1))
opt = torch.optim.AdamW([w], lr=peak)
sched = torch.optim.lr_scheduler.LambdaLR(opt, factor)
for step in range(total):
    if step in (0, 5, 9, 10, 30, 49):
        print(step, f"{opt.param_groups[0]['lr']:.6f}")
    w.grad = torch.zeros(1)
    opt.step()
    sched.step()

EX 7.6 hard Write apply_adam as a real torch.optim.Optimizer

Subclass torch.optim.Optimizer to make MicroAdam, a line-for-line port of microgpt's apply_adam that keeps its moments in self.state. Train two copies of a small MLP for 10 steps, one with MicroAdam and one with torch.optim.Adam(lr=0.01, betas=(0.85, 0.99), eps=1e-8), and show the parameters match.

Show solution 
import torch
from torch import nn

class MicroAdam(torch.optim.Optimizer):
    def __init__(self, params, lr=0.01, betas=(0.85, 0.99), eps=1e-8):
        super().__init__(params, dict(lr=lr, betas=betas, eps=eps))

    @torch.no_grad()
    def step(self):
        for group in self.param_groups:
            beta1, beta2 = group["betas"]
            for p in group["params"]:
                if p.grad is None:
                    continue
                state = self.state[p]
                if not state:                                  # first time we see p
                    state["step"] = 0
                    state["m"] = torch.zeros_like(p)
                    state["v"] = torch.zeros_like(p)
                state["step"] += 1
                t, m, v, g = state["step"], state["m"], state["v"], p.grad
                m.mul_(beta1).add_(g, alpha=1 - beta1)         # first moment
                v.mul_(beta2).addcmul_(g, g, value=1 - beta2)  # second moment
                m_hat = m / (1 - beta1 ** t)
                v_hat = v / (1 - beta2 ** t)
                p.sub_(group["lr"] * m_hat / (v_hat.sqrt() + group["eps"]))

def make_model():
    torch.manual_seed(0)
    return nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 4))

torch.manual_seed(1)
x, y = torch.randn(32, 8), torch.randint(0, 4, (32,))
ours, ref = make_model(), make_model()
opt_ours = MicroAdam(ours.parameters())
opt_ref = torch.optim.Adam(ref.parameters(), lr=0.01, betas=(0.85, 0.99), eps=1e-8)

for step in range(10):
    for model, opt in ((ours, opt_ours), (ref, opt_ref)):
        opt.zero_grad()
        nn.functional.cross_entropy(model(x), y).backward()
        opt.step()

diff = max((a - b).abs().max().item() for a, b in zip(ours.parameters(), ref.parameters()))
print(f"max parameter difference after 10 steps: {diff:.2e}")
# max parameter difference after 10 steps: 5.96e-08

The base class gives you param_groups, self.state (a dict keyed by parameter), zero_grad() and state_dict() for free. The remaining 6e-8 is float32 rounding: PyTorch evaluates the same formula in a slightly different order.

EX 7.7 hard Implement clip_grad_norm_ yourself

Write my_clip_grad_norm_(parameters, max_norm): compute the global L2 norm, scale all gradients in place if it exceeds max_norm, and return the pre-clip norm. Compare against PyTorch on a small MLP whose loss you multiply by 10 to get big gradients, and confirm the clipped norm is max_norm.

Show solution 
import torch
from torch import nn

def my_clip_grad_norm_(parameters, max_norm, eps=1e-6):
    grads = [p.grad for p in parameters if p.grad is not None]
    total = torch.sqrt(sum((g ** 2).sum() for g in grads))   # one norm over everything
    scale = torch.clamp(max_norm / (total + eps), max=1.0)   # never scale up
    for g in grads:
        g.mul_(scale)
    return total

def grads_after_backward():
    torch.manual_seed(0)
    model = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 4))
    x, y = torch.randn(32, 8), torch.randint(0, 4, (32,))
    (10 * nn.functional.cross_entropy(model(x), y)).backward()   # big grads on purpose
    return model

a, b = grads_after_backward(), grads_after_backward()
n1 = my_clip_grad_norm_(list(a.parameters()), max_norm=0.5)
n2 = torch.nn.utils.clip_grad_norm_(b.parameters(), max_norm=0.5)
print(n1, n2)                     # tensor(3.6348) tensor(3.6348)
print(max((p.grad - q.grad).abs().max().item() for p, q in zip(a.parameters(), b.parameters())))

print(torch.sqrt(sum((p.grad ** 2).sum() for p in a.parameters())))   # tensor(0.5000)

EX 7.8 hard Label smoothing from the formula

With smoothing ε, the target distribution is (1 - ε)·onehot + ε/C for every class. Show that this makes the loss (1 - ε)·NLL + ε·mean_c(-log p_c), compute it with log_softmax, and match F.cross_entropy(..., label_smoothing=0.1) on the three-row example from this chapter (0.8115).

Show solution

Cross-entropy against a distribution q is -Σ_c q_c log p_c. Split q: the one-hot part gives (1 - ε)·(-log p_target); the uniform part gives (ε/C)·Σ_c(-log p_c) = ε·mean_c(-log p_c).

import torch
import torch.nn.functional as F

logits = torch.tensor([[2.0, 1.0, 0.1, -1.0],
                       [0.5, 2.5, 0.0,  0.3],
                       [1.0, 1.0, 1.0,  1.0]])
targets = torch.tensor([0, 1, 3])
eps = 0.1

log_p = F.log_softmax(logits, dim=-1)                 # (N, C)
nll = -log_p[torch.arange(3), targets]                # usual per-token loss
uniform = -log_p.mean(dim=-1)                         # loss against a uniform target
by_hand = ((1 - eps) * nll + eps * uniform).mean()
print(by_hand)                                        # tensor(0.8115)
print(F.cross_entropy(logits, targets, label_smoothing=eps))   # tensor(0.8115)

The uniform term is minimised when all logits are equal, so it keeps pulling logits together and the model can never reach probability 1. Even a perfect model's loss stays above 0.

Recap

  • F.cross_entropy(logits, targets) = softmax, pick p[target], -log, average: microgpt's negative_log_likelihood + calculate_document_loss. It takes raw logits and uses log_softmax (logsumexp) so confident-but-wrong predictions give large finite losses instead of inf/nan.
  • Shapes: (N, C) logits with (N,) int64 targets. Flatten (B, T, C) to (B*T, C); never pass (B, T, C) directly.
  • reduction="none"|"sum"|"mean"; ignore_index=-100 masks padding and removes it from the mean's denominator; label_smoothing softens targets.
  • An untrained model should start at ln(C): 3.2958 for 27 tokens.
  • Optimizers hold parameter references; step() updates in place from .grad; zero_grad() (default set_to_none=True) clears them. SGD is p -= lr * grad.
  • torch.optim.Adam(betas=(0.85, 0.99), eps=1e-8) reproduces apply_adam to float32 precision; optimizer.state[p] holds exp_avg, exp_avg_sq, step.
  • AdamW decays weights directly (p *= 1 - lr*wd) instead of through the gradient; use param groups to skip decay on biases and norm gains.
  • Schedules: LambdaLR reproduces microgpt's linear decay; warmup + cosine is the LLM default. Call optimizer.step() then scheduler.step().
  • clip_grad_norm_ rescales all gradients so their global L2 norm is at most max_norm, and returns the pre-clip norm. Log it.
