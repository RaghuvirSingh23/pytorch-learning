Chapter 09 Devices & Precision

Two questions decide whether a model fits on a machine and how fast it runs: where the tensors live (CPU, a CUDA GPU, Apple's mps) and how many bits each number gets. This chapter covers moving models and data between devices, the floating-point formats from the bit level up (fp32, fp16, bf16, TF32, fp8), mixed precision with autocast and GradScaler, and the arithmetic that tells you how many bytes training and inference really need, KV cache included.

Devices: where a tensor lives

Every tensor has a device: the memory it is stored in, and therefore the processor that runs operations on it. torch.device("cpu") is ordinary RAM. torch.device("cuda") is an NVIDIA GPU's memory ("cuda:1" picks the second GPU). torch.device("mps") is Apple Silicon's GPU through Metal. An operation runs on the device of its inputs, and all its tensor inputs must be on the same one.

microgpt reads its device from the DEVICE environment variable. The usual pattern picks the best one available:

pythondevice.py
import torch

def best_device():
    if torch.cuda.is_available():
        return torch.device("cuda")
    if torch.backends.mps.is_available():
        return torch.device("mps")
    return torch.device("cpu")

device = best_device()
print(device, torch.cuda.is_available(), torch.backends.mps.is_available())
# mps False True                       (on the Apple Silicon laptop used here)

x = torch.ones(2, 3)
y = x.to(device)                 # a NEW tensor on the device; x is untouched
print(x.device, y.device, y is x)              # cpu mps:0 False
print(y.to(device) is y)         # already there: no copy, same object   -> True

model = torch.nn.Linear(3, 2)
returned = model.to(device)      # moves the parameters IN PLACE, returns self
print(returned is model, model.weight.device)  # True mps:0

print(y.sum().item(), y.cpu().device)          # 6.0 cpu

The one asymmetry to remember: tensor.to(device) returns a new tensor and leaves the original where it was, so you must reassign (x = x.to(device)). module.to(device) moves the module's parameters and buffers in place and returns the same module, so model.to(device) on its own line works. That is why microgpt writes model = FastMicroGPT().to(device) but builds its token tensors with device=device directly. Creating a tensor on the device (torch.zeros(..., device=device)) is better than creating it on the CPU and copying.

.item(), .tolist() and .cpu() copy data back to the host. NumPy only understands host memory:

import torch

model = torch.nn.Linear(3, 2).to("mps")
x = torch.ones(4, 3)                     # forgot to move the batch

The second message is the one you will see most, with cuda:0 and cpu on an NVIDIA machine. The fix is always the same: move the model once, and move every batch inside the loop. Chapter 12 shows how to find which tensor was left behind.

Host-to-GPU copies: pin_memory and non_blocking (CUDA)

Ordinary host memory is pageable: the operating system may move it around, so the GPU cannot read it directly. A copy to the GPU first goes through a pinned (page-locked) staging buffer. If the batch is already in pinned memory, the GPU's copy engine can read it directly, and the copy can be asynchronous: the CPU queues it and moves on while the bytes travel.

# needs a CUDA GPU
loader = DataLoader(dataset, batch_size=64, shuffle=True, collate_fn=collate,
                    pin_memory=True)                 # worker output lands in pinned memory
for inputs, targets in loader:
    inputs = inputs.to("cuda", non_blocking=True)    # async copy, CPU does not wait
    targets = targets.to("cuda", non_blocking=True)
    logits = model(inputs)                           # queued after the copy on the same stream
    ...

This is safe because CUDA runs operations in order on a stream: the forward pass is queued behind the copy and cannot start before the data arrives. It also hints at something bigger: CUDA operations are asynchronous. model(inputs) returns as soon as the kernels are queued, long before the GPU finishes them. The CPU only waits when it needs a result, such as at loss.item(). That is why timing GPU code with time.perf_counter() alone gives nonsense; Chapter 11 does it properly with torch.cuda.synchronize() and CUDA events. pin_memory is a CUDA feature; leave it off on CPU-only and mps machines.

Floating-point formats from zero

A floating-point number stores three fields:

  • sign: 1 bit, 0 for positive.
  • exponent: which power of two the number is near. More exponent bits = wider range (how big and how small).
  • mantissa (or fraction): the digits after the leading 1. More mantissa bits = finer precision (how close two neighbouring values are).

For a normal number, value = (-1)^sign × 2^(exponent - bias) × 1.mantissa. The bias lets the stored exponent be unsigned: 127 for 8-bit exponents, 15 for 5-bit ones. Take 6.5: it is 1.625 × 2^2, and 0.625 in binary is .101. So fp32 stores sign 0, exponent 2 + 127 = 129 = 10000001, mantissa 101000.... You can look at the actual bits by reinterpreting the tensor's memory as an integer with .view(torch.int32):

pythonbits.py
import torch

def fp32_fields(x):
    bits = torch.tensor(x, dtype=torch.float32).view(torch.int32).item() & 0xFFFFFFFF
    b = f"{bits:032b}"
    return b[0], b[1:9], b[9:], f"0x{bits:08x}"

def bf16_fields(x):
    bits = torch.tensor(x, dtype=torch.bfloat16).view(torch.int16).item() & 0xFFFF
    b = f"{bits:016b}"
    return b[0], b[1:9], b[9:], f"0x{bits:04x}"

def fp16_fields(x):
    bits = torch.tensor(x, dtype=torch.float16).view(torch.int16).item() & 0xFFFF
    b = f"{bits:016b}"
    return b[0], b[1:6], b[6:], f"0x{bits:04x}"

Read the trade-off off the table. fp16 is precise (eps about 0.001, three decimal digits) but tops out at 65,504. bf16 has fp32's range (up to 3.4e38) but only eps = 1/128, two to three significant digits. The fn in float8_e4m3fn means "finite": it has no infinity, and spends those bit patterns on extra range (max 448 instead of 240).

Range and precision, demonstrated

pythonrange_precision.py
import torch

big = torch.tensor([65504.0, 65519.0, 65520.0, 70000.0])
print(big.to(torch.float16))                  # fp16 max is 65504
print(big.to(torch.bfloat16))                 # bf16 has the range, not the precision

  • fp16 overflow: anything from 65,520 up rounds to inf, and so does 60000 × 2. One inf in a forward pass becomes nan everywhere after it (inf - inf, 0 × inf).
  • fp16 underflow: below about 6e-8 (the smallest subnormal), values become 0. Gradients live down there; the GradScaler section deals with it.
  • bf16 range: 70,000 and 1e-8 are both fine, just rounded (70,000 becomes 70,144).
  • bf16 precision: near 1.0 the representable values are 1, 1 + 1/128, 1 + 2/128, .... 1 + 1/256 sits exactly halfway and rounds to the even neighbour, 1.0: the addition is lost. At 256 the spacing is 2, so 256 + 1 = 256.

Adding many small numbers

Precision bites hardest in long sums, because each addition rounds to the spacing near the running total. Once the total is big enough that half the spacing exceeds the number being added, every addition rounds back to where it was:

import torch

for dt in (torch.float32, torch.bfloat16, torch.float16):
    acc = torch.tensor(0.0, dtype=dt)
    step = torch.tensor(1e-4, dtype=dt)
    for _ in range(10_000):                   # 10,000 x 0.0001 should be 1.0
        acc = acc + step
    print(f"{str(dt):15s} running sum = {acc.item():.6f}")

x = torch.full((10_000,), 1e-4, dtype=torch.bfloat16)
print(x.sum().item(), x.sum().dtype)          # torch.sum accumulates in float32 internally
torch.float32   running sum = 1.000054
torch.bfloat16  running sum = 0.031250
torch.float16   running sum = 0.250000
1.0 torch.bfloat16

bf16 gets stuck at 0.03125: there the spacing is 2^-5 × 2^-7 = 0.000244, half of which is bigger than 0.0001. fp16, with 3 more mantissa bits, gets stuck later, at 0.25. torch.sum on the same bf16 tensor returns 1.0, because PyTorch's reductions keep a float32 accumulator for bf16 and fp16 inputs and only round the final result. GPU matmuls do the same: tensor cores multiply bf16 inputs but accumulate in fp32. That is the general rule of mixed precision: store and multiply in low precision, add up in high precision.

TF32: faster fp32 matmuls (CUDA, Ampere and newer)

NVIDIA's tensor cores from Ampere (A100, RTX 30xx) onward can run fp32 matrix multiplies in TF32: each input is rounded to a 10-bit mantissa (fp16's precision) while keeping fp32's 8-bit exponent (its range), and products are accumulated in fp32. Inputs and outputs are still torch.float32 tensors; only the internal multiply is coarser. For neural network training the loss of precision rarely matters, and the matmuls run several times faster.

PyTorch leaves it off for matmuls by default (so fp32 means fp32), and on for cuDNN convolutions. Two equivalent ways to turn it on:

import torch

print(torch.get_float32_matmul_precision())       # 'highest' is the default
print(torch.backends.cuda.matmul.allow_tf32)      # False by default
print(torch.backends.cudnn.allow_tf32)            # True by default (convolutions)
torch.set_float32_matmul_precision("high")        # allow TF32 for fp32 matmuls
print(torch.backends.cuda.matmul.allow_tf32)      # True

"highest" means real fp32. "high" allows TF32 (or an equivalent bf16-based method) when the hardware has it, and is the same as setting allow_tf32 = True. "medium" allows bf16 internally. The PyTorch docs say this flag currently affects only CUDA; the lines above run anywhere, but on a Mac or a CPU they change nothing. If you see "TensorFloat32 tensor cores ... available but not enabled" in a warning on an NVIDIA GPU, this is the switch it means.

Mixed precision with torch.autocast

Mixed precision means running most of the arithmetic in a 16-bit format (half the memory traffic, much faster on tensor cores) while keeping the numerically sensitive parts in fp32. You could convert the model with model.to(torch.bfloat16), but then the weights themselves are bf16, and as Exercise 9.7 shows, small optimizer updates to bf16 weights get rounded away.

torch.autocast is the standard tool. Inside its with block, each operation is cast per a fixed list:

  • Lower-precision ops (matmul-like: linear, matmul, bmm, convolutions, and on CPU also scaled_dot_product_attention): inputs are cast to bf16/fp16, so the output is bf16/fp16.
  • fp32 ops (sensitive reductions and losses: cross_entropy, nll_loss, mse_loss, and on CUDA also softmax, log_softmax, layer_norm, sum, exp, log, pow and others): inputs are cast to fp32.
  • Everything else (relu, addition, indexing): runs in whatever dtype its inputs have; mixed inputs promote to the wider type.

The lists differ between devices; the AMP docs have them in full. Here it is on the CPU with bf16, which runs anywhere:

pythonautocast_cpu.py
import torch
import torch.nn as nn
import torch.nn.functional as F

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(16, 64), nn.ReLU(), nn.Linear(64, 27))
x = torch.randn(8, 16)
y = torch.randint(0, 27, (8,))

with torch.autocast(device_type="cpu", dtype=torch.bfloat16):
    h = model[0](x)                       # linear: autocast runs it in bf16
    r = model[1](h)                       # relu: not on any list, follows its input
    logits = model[2](r)
    probs = torch.softmax(logits, dim=-1)
    rms = F.rms_norm(logits, (27,))
    loss = F.cross_entropy(logits, y)     # on the CPU fp32 list
    print("linear  ", h.dtype)
    print("relu    ", r.dtype)
    print("logits  ", logits.dtype)
    print("softmax ", probs.dtype)
    print("rms_norm", rms.dtype)
    print("loss    ", loss.dtype)

loss.backward()                           # backward outside the autocast block
print("weight  ", model[0].weight.dtype)
print("grad    ", model[0].weight.grad.dtype)

with torch.no_grad():
    ref = F.cross_entropy(model(x), y)
print(f"fp32 loss {ref.item():.6f}   autocast loss {loss.item():.6f}")

Three things to notice. The parameters stay fp32: autocast casts a bf16 copy of each weight for the matmul (and caches it within the block), so the optimizer still updates fp32 master values, and gradients arrive in fp32. The loss is fp32 even though the logits are bf16. And on the CPU, softmax and rms_norm stay in bf16 because they are not on the CPU's fp32 list; under CUDA autocast, softmax would be fp32. The loss differs from fp32 in the fourth decimal: that is the bf16 rounding of the matmuls.

Call backward() outside the with block; the docs say backward under autocast is not recommended, and each backward op automatically runs in the dtype its forward op used. Apple's mps backend supports autocast too: in torch 2.8 on this laptop, torch.autocast(device_type="mps", dtype=torch.float16) (and bfloat16) turn a Linear's output into that dtype.

On a CUDA GPU: bf16

On Ampere and newer GPUs, bf16 autocast is the default recipe. It is the training loop from Chapter 8 with one with line added (needs a CUDA GPU):

model = MicroGPT().to("cuda")
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-3, betas=(0.85, 0.99))

    inputs = inputs.to("cuda", non_blocking=True)
    targets = targets.to("cuda", non_blocking=True)

        logits = model(inputs)
        loss = F.cross_entropy(logits.view(-1, VOCAB), targets.view(-1))
    optimizer.zero_grad(set_to_none=True)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    optimizer.step()
    scheduler.step()

fp16 and GradScaler

bf16 has fp32's exponent range, so gradients that fit in fp32 essentially never underflow in bf16. fp16 is different: its smallest value is about 6e-8, and gradients are often smaller, especially for activations deep in a network late in training. Those gradients become exactly 0 and the corresponding weights stop learning. You can see it on the CPU:

pythonunderflow.py
import torch

x = torch.tensor([3e-4, 5e-4], dtype=torch.float16, requires_grad=True)   # fp16 activations

def loss_fn(x):
    return ((x * x).float() * 1e-5).sum()     # the loss itself is fp32, as under autocast

loss_fn(x).backward()                         # true grad = 2 * x * 1e-5 = [6e-9, 1e-8]
print(x.grad)                                 # tensor([0., 0.], dtype=torch.float16)

x.grad = None
scale = 65536.0                               # GradScaler's default initial scale (2**16)
(loss_fn(x) * scale).backward()               # scale the fp32 loss, then backward
print(x.grad)                                 # tensor([0.0004, 0.0007], dtype=torch.float16)
print(x.grad.float() / scale)                 # tensor([5.9990e-09, 1.0004e-08])

Loss scaling is the fix: multiply the loss by a large constant S before backward(). By the chain rule every gradient is multiplied by S too, which lifts them out of the underflow zone. Then divide the gradients by S in fp32 before the optimizer uses them. The result above is the correct gradient to 3 digits, where the unscaled backward gave 0.

Choosing S by hand is fragile: too small and gradients underflow, too large and they overflow to inf. torch.amp.GradScaler adjusts it automatically. It starts at init_scale=65536; if any gradient comes out inf or nan, it skips that optimizer step and halves the scale (backoff_factor=0.5); after 2,000 clean steps in a row (growth_interval) it doubles it (growth_factor=2.0). The loop (needs a CUDA GPU):

scaler = torch.amp.GradScaler("cuda")
for inputs, targets in train_loader:
    inputs = inputs.to("cuda", non_blocking=True)
    targets = targets.to("cuda", non_blocking=True)
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        logits = model(inputs)
        loss = F.cross_entropy(logits.view(-1, VOCAB), targets.view(-1))
    optimizer.zero_grad(set_to_none=True)
    scaler.scale(loss).backward()        # backward of loss * S
    scaler.unscale_(optimizer)           # grads /= S in place, so clipping sees true values
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)               # skips optimizer.step() if any grad is inf/nan
    scaler.update()                      # adjust S for the next iteration
    scheduler.step()

Use bf16 when the hardware supports it (NVIDIA Ampere and newer, recent TPUs and CPUs) and skip the scaler entirely. fp16 plus GradScaler is for older GPUs such as V100 and T4. The old spelling torch.cuda.amp.GradScaler is deprecated in favour of torch.amp.GradScaler("cuda").

Memory math

How much memory does a model need? Start from bytes per parameter. tensor.element_size() gives the bytes per element of its dtype, so t.element_size() * t.numel() is the size of any tensor, on any device.

The extra 36 bytes are Adam's step counter: one 4-byte scalar tensor for each of the 9 parameter tensors. microgpt's whole training state is 67 KB. Now scale up to a 7-billion-parameter model:

  • Training with Adam: 7e9 × 16 = 112 GB. That does not fit on one 80 GB GPU even before activations, which is why large models are trained with the optimizer state and gradients sharded across GPUs (FSDP, ZeRO).
  • Inference weights in bf16: 7e9 × 2 = 14 GB. In int8 or fp8: 7 GB.

Activations are the other big term in training: every intermediate the backward pass needs is kept until backward runs. They grow with batch size × sequence length × layers × width, not with parameter count, so they have no per-parameter number. Autocast stores many of them in bf16, halving that part. Activation checkpointing (torch.utils.checkpoint) discards them and recomputes them during backward, trading compute for memory.

The KV cache

At inference, the dominant extra memory is the KV cache: for every layer and every past token, the model keeps that token's key and value vectors so it never recomputes them. microgpt's scalar gpt_step does exactly this with its key_cache and value_cache lists. Its size:

KV bytes = 2 (K and V) × layers × kv_heads × head_dim × seq_len × batch × bytes_per_value
def kv_cache_bytes(layers, kv_heads, head_dim, seq_len, batch, bytes_per_value):
    return 2 * layers * kv_heads * head_dim * seq_len * batch * bytes_per_value   # 2 = K and V

GiB = 2 ** 30
print(kv_cache_bytes(1, 4, 4, 16, 1, 4))                     # microgpt, fp32 -> 2048
print(kv_cache_bytes(32, 32, 128, 4096, 1, 2) / GiB)         # Llama-2-7B shape, bf16 -> 2.0
print(kv_cache_bytes(32, 8, 128, 4096, 1, 2) / GiB)          # same, 8 KV heads (GQA) -> 0.5
print(kv_cache_bytes(32, 32, 128, 4096, 1, 2) / 4096 / 2**20) # MiB per token -> 0.5

P = 7e9
print(P * 16 / 1e9, P * 2 / 1e9, P * 1 / 1e9)                # GB: train (Adam), bf16, 8-bit
# 112.0 14.0 7.0

microgpt (1 layer, 4 heads of size 4, 16 tokens, fp32) needs 2 KB. A Llama-2-7B-shaped model (32 layers, 32 KV heads of size 128) needs half a MiB per token: 2 GiB for one 4,096-token sequence, so seven such sequences (15 GB) already outweigh the 14 GB of bf16 weights. Grouped-query attention (GQA) shares each K/V head among several query heads; with 8 KV heads the cache shrinks 4×. This formula is the core of inference capacity planning, and Chapter 10 builds the cache itself.

Measuring what is allocated

On CUDA, PyTorch's caching allocator reports how much memory tensors currently hold and the peak since you last reset (needs a CUDA GPU):

torch.cuda.reset_peak_memory_stats()
loss = F.cross_entropy(model(inputs).view(-1, VOCAB), targets.view(-1))
loss.backward()
optimizer.step()
print(f"{torch.cuda.memory_allocated() / 2**20:.1f} MiB held by tensors now")
print(f"{torch.cuda.max_memory_allocated() / 2**20:.1f} MiB peak during the step")
print(f"{torch.cuda.memory_reserved() / 2**20:.1f} MiB reserved by the caching allocator")

The peak is what decides whether a step fits; it usually occurs during backward, when activations and gradients coexist. memory_reserved is larger, because PyTorch keeps freed blocks for reuse instead of returning them to the driver, which is why nvidia-smi shows more than memory_allocated. On a Mac, torch.mps.current_allocated_memory() plays the same role:

import torch

before = torch.mps.current_allocated_memory()
w = torch.empty(1024, 1024, device="mps")              # 1M float32 values
after = torch.mps.current_allocated_memory()
print(w.element_size() * w.numel(), after - before)    # 4194304 4194304
del w
print(torch.mps.current_allocated_memory() - before)   # 0

A first look at quantization

Quantization stores weights in fewer bits than bf16 to cut memory and memory bandwidth at inference. The simplest form is int8 with a scale: for each output row of a weight matrix, find the largest absolute value, map it to 127, and store round(w / scale) as an 8-bit integer plus one fp32 scale per row. To use the weight, multiply back: w ≈ q × scale. fp8 is the floating-point alternative: a cast to float8_e4m3fn.

pythonquant_teaser.py
import torch

torch.manual_seed(0)
w = 0.08 * torch.randn(64, 16)                         # like microgpt's mlp_expand_weights

# int8, symmetric, one scale per output row
scale = w.abs().amax(dim=1, keepdim=True) / 127        # (64, 1) fp32 scales
q = torch.round(w / scale).clamp(-127, 127).to(torch.int8)
w_int8 = q.float() * scale                             # dequantize to use it

w_fp8 = w.to(torch.float8_e4m3fn).float()              # fp8 e4m3: 3 mantissa bits
w_bf16 = w.to(torch.bfloat16).float()                  # bf16: 7 mantissa bits

print(q.dtype, q[0, :6].tolist(), f"scale={scale[0].item():.6f}")
for name, approx in (("bf16", w_bf16), ("int8", w_int8), ("fp8 e4m3", w_fp8)):
    err = (approx - w).abs()
    print(f"{name:9s} max abs error {err.max().item():.6f}  mean {err.mean().item():.6f}")
print(q.element_size() * q.numel() + scale.element_size() * scale.numel(),
      w.element_size() * w.numel())
torch.int8 [-68, -69, -15, -26, 51, 42] scale=0.001332
bf16      max abs error 0.000742  mean 0.000092
int8      max abs error 0.001249  mean 0.000328
fp8 e4m3  max abs error 0.015619  mean 0.001459

int8 with per-row scales is within 0.0013 of every weight, while storing 1,280 bytes instead of 4,096. A plain fp8 cast is coarser here: 3 mantissa bits means each value can be off by up to about 6% of itself. Real fp8 and int8 schemes add per-tensor, per-channel or per-block scales, quantize activations as well, and run matmuls directly in 8 bits on hardware that supports it. Libraries such as torchao package these recipes. This tutorial stops at the idea: fewer bits per weight, plus a scale to keep the range.

The order is tok, pos, qkv, proj, up, down, head. Embedding lookups are not on autocast's list, so they return fp32. A residual stream in fp32 is a nice side effect: the running sum keeps full precision.

EX 9.5 hard Decode bf16 bits by hand

Write decode_bf16(x) that converts x to bf16, reads its 16 bits with .view(torch.int16), extracts sign, exponent and mantissa with shifts and masks, and rebuilds the value with the formula from this chapter. Check it against PyTorch for 1.0, -6.5, 0.1, 3.14159, 1e-3 and 70000.

Show solution 
import torch

def decode_bf16(x):
    bits = torch.tensor(x, dtype=torch.bfloat16).view(torch.int16).item() & 0xFFFF
    sign = bits >> 15
    exponent = (bits >> 7) & 0xFF                # 8 bits
    mantissa = bits & 0x7F                       # 7 bits
    assert 0 < exponent < 255, "only normal numbers here"
    value = (-1) ** sign * 2.0 ** (exponent - 127) * (1 + mantissa / 128)
    return sign, exponent, mantissa, value

for x in (1.0, -6.5, 0.1, 3.14159, 1e-3, 70000.0):
    s, e, m, v = decode_bf16(x)
    stored = torch.tensor(x, dtype=torch.bfloat16).item()
    print(f"{x:>9}: sign={s} exp={e:3d} (2^{e - 127:+d}) mant={m:3d}  value={v:<12g} torch={stored:g}")

EX 9.7 medium Why the master weights stay fp32

Near 1.0 the bf16 spacing is 1/128 ≈ 0.0078 (and 1/256 just below 1.0), so subtracting 0.001 rounds straight back to 1.0. After 1,000 steps the bf16 weight has not moved at all, while fp32 has travelled the full distance. This is why autocast keeps parameters in fp32 and only casts copies for the matmuls, and why "classic" mixed precision kept an fp32 master copy of fp16 weights.

Recap

  • A tensor's device is where it lives; all inputs to an op must share it. Pick cuda, then mps, then cpu. tensor.to() returns a new tensor (reassign it); module.to() moves in place.
  • Mixing devices raises "Expected all tensors to be on the same device". .item(), .cpu() and .numpy() need the data on the host.
  • On CUDA, pin_memory=True + non_blocking=True make host-to-GPU copies asynchronous; GPU ops are asynchronous in general (Chapter 11).
  • Floats are sign / exponent (range) / mantissa (precision). fp32 1/8/23, fp16 1/5/10 (max 65,504), bf16 1/8/7 (fp32's range, eps = 1/128), TF32 1/8/10 inside tensor cores, fp8 e4m3 (max 448) and e5m2.
  • fp16 overflows past 65,504 and underflows below 6e-8; bf16 rounds 1 + 1/256 to 1. Long sums need fp32 accumulators, which PyTorch reductions and tensor cores use.
  • TF32 for fp32 matmuls: torch.set_float32_matmul_precision("high"), CUDA only, off by default.
  • torch.autocast runs matmuls in bf16/fp16 and sensitive ops in fp32, while parameters and gradients stay fp32. fp16 also needs torch.amp.GradScaler("cuda") to stop gradient underflow; bf16 does not.
  • Training with Adam ≈ 16 bytes/param plus activations; bf16 inference = 2 bytes/param; KV cache = 2 × layers × kv_heads × head_dim × seq_len × batch × bytes. Measure with element_size() * numel() and torch.cuda.max_memory_allocated().
  • Quantization stores weights in 8 bits (or fewer) plus scales, halving bf16's memory again.
